# iPhone 코드·에셋 심층진단 — 2026-11-16

아이폰 상점의 페이지 전환에서 새 아이콘의 GPU 준비가 빠지는 경로를 공통 C++ 화면 코드로 재현했다. 스테이지 로딩 그림과 정렬에도 최신 요구와 다른 구현이 남아 있다. 소스·번들이 같아도 기기별로 실행하는 화면 상태와 준비 순서가 달라진다. 현재 코드는 수정이 필요하다.

이번 작업은 조사다. 제품 소스·에셋·기기 앱·사용자 저장을 변경하지 않았다. 실제 사용자 저장의 같은 상품 페이지에서 GPU 예외를 다시 발생시키거나 Skyway의 실기기 연속 프레임을 계측하지 않았다. 아래 CPU 재현과 실제 기기 제보를 구분한다.

## 발견 1 — 상점 페이지의 새 아이콘을 GPU에 준비하지 않는다 · P1

**CPU 재현 확인.** `Sources/Core/UI/Screens.cpp:1204`의 Phone 페이지 버튼은 `stockWindow`/`inventoryWindow`를 바꾸고 `pageRebuild`를 켠다. 실제 HD 페이지 안의 작은 표시 페이지를 넘길 때는 `host.action`을 부르지 않는다. `Screens::input`은 자체적으로 `refresh`한다. 따라서 UI 자원 세대는 바뀌지만 GameSession의 `presentationRevision`은 바뀌지 않는다.

`Sources/Platform/Apple/HM2GameRuntime.mm:78`은 GameSession 화면 revision이 바뀌었을 때만 UI의 `appendPreparation`을 GPU에 제출한다. 82~91행의 자원 변경 분기는 UI 세대 변화를 감지하지만 `game->preparationFrame()`만 업로드한다. 새 UI 자원을 보존 목록에 넣는 것은 업로드를 대신하지 않는다.

912×420의 실제 Phone UI에서 첫 8상품은 `Icon10011.png`, 이후 상품은 실제 존재하는 `Icon10113.png`인 24상품 fixture를 만들었다. 처음 준비한 자원 집합을 유지하고 실제 다음 버튼 2106을 눌렀다. 결과는 다음과 같다.

```text
PHONE uiGeneration=1->3 hostActions=0 missing=Icon10113.png,
TABLET uiGeneration=1->1 hostActions=0 missing=
```

iPad는 같은 24상품을 처음부터 그려 아이콘을 준비한다. iPhone은 뒤쪽 표시 페이지에서 새 아이콘을 처음 요구한다. 같은 번들에서 차이가 나는 구체적인 이유다. fixture의 상품 순서는 재현용이며 사용자 저장의 실제 상품 순서를 읽었다고 주장하지 않는다.

GPU의 `HM2Renderer.mm:176`은 미준비 아이콘을 만나면 제보와 같은 문자열의 예외를 던진다. `HM2SourceView.mm:118`은 이 예외를 받으면 런타임을 해제하고 시스템 얼럿을 띄운다. 이 경로는 게임이 멈추는 현상을 설명한다. OS 크래시 로그를 확보하지 않았으므로 프로세스 크래시 종류는 미확정이다.

관련 시작점은 자원 수명 분리를 넣은 `9144809`와 Phone 내부 페이지를 추가한 `ca424ab`의 결합이다. 해당 원인이 이미 `Icon10113.png` 제보를 일으킨 바로 그 입력 순서였는지는 사용자 저장/페이지와 실제 GPU 검사로 최종 연결해야 한다.

**필요한 수정:** 화면 재구성과 자원 변경을 분리하되, UI 자원 세대가 바뀐 경계에서는 새 UI 준비 프레임도 GPU에 제출해야 한다. 매 프레임 로드·임의 아이콘 대체·예외 숨김으로 처리하지 않는다. 상점·인벤토리·장비/BOT 탭을 최초 진입의 차가운 캐시부터 검사한다.

## 발견 2 — 정식·치트의 자원 준비 절차와 검사가 갈라져 있다 · P1

`HM2ConcurrentRuntime.mm:89~109`도 정식 Runtime과 별도로 revision·UI generation·월드 자원·보존 목록을 관리한다. 같은 준비 누락 구조가 있다. 치트에서는 여러 독립 Session이 하나의 renderer를 공유하고 메뉴 예열·다른 Session의 사용 자원도 있다. 따라서 다른 조건이 먼저 올린 텍스처가 누락을 가릴 가능성이 있다. 이번에는 그 은폐가 실제 발생했다고 확정하지 않았다.

구체적인 검사 공백은 확인했다. `Apple/Tests/SessionRendererTests.mm:518` 부근의 메뉴 capture 함수는 매 캡처 직전에 `ui.appendPreparation`과 `renderer prepareFrame`을 직접 호출한다. 이 검사는 출력 그림을 볼 수 있지만 정식 Runtime이 준비를 빠뜨리는지는 검사하지 못한다. 24/25칸 fixture도 소수 아이콘을 반복해 뒤 페이지에서 처음 등장하는 자원 경계를 충분히 만들지 않는다. 공통 CPU 거래 검사 역시 GPU 업로드 집합을 검사하지 않는다.

**필요한 수정:** 제품·치트가 같은 자원 경계 계산을 사용하게 한다. 그림 검사와 별도로, 실제 `GameRuntime.input → synchronize → draw` 순서에서 페이지별 첫 아이콘·IconB 상세·탭 전환을 검사한다. 검사 도중 보조 `prepareFrame`을 호출해 제품 누락을 보충하지 않는다. 현재 78/78 통과는 발견 1의 반증이 아니다.

## 발견 3 — 스테이지 로딩이 Phone 그림·중앙 정렬을 유지한다 · P1

**코드 추적·공통 CPU 실행 확인.** `GameSession.cpp:180`은 기기 종류 대신 `display.enabled && display.compact`를 `MapLoading`에 전달한다. `MapLoading.cpp:5`는 true일 때 `PhoneMenu/StageClearBG.png`와 480×320 기준을 선택한다. `GameSession.cpp:721`은 그림을 화면 중앙 기준으로 cover한다.

```text
PHONE stageLoading=PhoneMenu/StageClearBG.png reference=480x320
TABLET stageLoading=StageClearBG.png reference=768x1024
```

최신 D08은 두 기기 모두 HD 그림·최상단 정렬이다. 이 소비 경로는 요구와 다르다. `b63f588`의 과거 Phone 그림 정책이 남아 있다. 메뉴 배경 36조건과 타이틀 그림 검사는 스테이지 간 로딩을 포함하지 않는다. 기존 MapLoading 검사도 기본 HD 인수만 확인한다.

**필요한 수정:** HD 자원 선택과 화면 위 정렬을 로딩 소비자까지 연결한다. fade 단계·맵 전환·저장/음향 사건은 유지한다. 작은 iPad 창에서도 Phone 그림을 고르지 않는지 확인한다.

## 발견 4 — 표시 정책에 타이틀 시간까지 섞였다 · P2

`MenuArtwork.hpp:21~25`는 위치/배율과 함께 `titleIn`, `episodeIn`, `prompt`를 반환한다. 현재 Phone은 7.2/8.7/11초, HD는 6.2/7.7/10초다. `Screens.cpp`의 타이틀 tick·입력 해금이 이 값을 소비한다. CPU에서도 Phone prompt 11, Tablet prompt 10을 확인했다.

[iPhone 개발 계약](iphone-development-contract.md)은 배치 변경 때문에 일반판 시간값을 섞지 않도록 정했다. 최신 디자인 정본의 Phone 배치 요구가 이 시간 차이까지 허용한 것으로 기록돼 있지는 않다. 현행 구현과 계약의 불일치다. `b63f588`에서 추가한 Phone 타이틀 계약과 `ca424ab`의 후속 표시 변경을 분리해 다뤄야 한다.

**필요한 수정:** 그림/배치 profile과 타이틀의 공통 시간 규칙을 분리한다. 10초/11초 해금 경계를 실제 입력과 음향 사건으로 검사한다. 사용자 최신 타이틀 구도 TODO와 시간 문제를 섞지 않는다.

## 발견 5 — 지형과 다른 레이어의 소수 좌표 처리가 다르다 · 원인 후보

`MapPreview.cpp:53`은 지형의 카메라 이동을 `round()`로 반올림한다. `PartSprites.cpp`, 월드 이미지·문·유닛과 `VisualLayer.cpp`는 소수 좌표를 유지한다. Phone에서는 이를 가변 `worldScale`로 다시 확대한다. Stage02_04의 카메라 x를 0.1씩 바꾼 CPU 프레임에서 지형과 부드러운 좌표의 상대 오차가 +0.5에서 약 -0.4로 바뀌었다. 같은 월드에 놓인 그림이 서로 다른 시점에 한 칸 이동할 수 있는 수학적 경로다.

그러나 이 반올림은 iPhone 도입 전에도 존재했다. 원본 HD의 fixed-position 복원 근거가 있는 처리다. 또한 배경 시차·Phone fillSurface의 배경 확대/위치 clamp·POT 투명 패딩과 GL_LINEAR도 구분해야 한다. 사용자가 지적한 특정 스테이지 레이어가 이 지형인지, 어느 자원이 움직이는지 아직 실기기 연속 프레임에서 식별하지 않았다.

**다음 확인:** 같은 저장·이동 입력·카메라/줌의 연속 프레임에 배경/지형/정적 오브젝트의 자원 ID·vertex·UV를 기록한다. 기기별 원본 렌더 변환과 비교한 뒤 반올림 단위를 결정한다. 전부 round하거나 에셋·좌표를 옮겨 현상을 덮지 않는다.

## 발견 6 — 필수 자원의 누락이 조용한 그림 생략으로 바뀐다 · P2

`PreparedTiles.cpp:29~31`은 파일이 없으면 null을 캐시에 넣는다. `Screens.cpp:268~275`는 null이면 이미지 생성을 건너뛴다. 없는 이름을 넣은 CPU 검사도 예외 없이 null을 반환했다. 선택적 배경과 필수 상품 아이콘을 구분하지 않는 경계다. 현재 1,548개 명세 자원의 실제 누락은 발견하지 않았다.

**필요한 수정:** 선택적 자원과 필수 참조를 구분하고, 상품/필수 UI 참조는 화면 진입 준비 단계에서 출처·ID와 함께 실패시킨다. 파일 해시뿐 아니라 테이블/아이템 ID → 준비 목록 → 실제 Frame의 참조 완전성을 검사한다. 원작에 의도적으로 없는 탄환 등의 예외는 기존 근거와 함께 보존한다.

## 구조 진단

별도 iPhone 게임 엔진이나 UIKit 인게임 버튼은 조사한 제품 소스에서 발견하지 않았다. GPU·HD 데이터·부품 reader·전투·진행·저장은 공통 코어를 사용한다. 금지 API 검색의 유일한 일치는 컨트롤을 만들지 않는다는 주석이었다. 이 검색만으로 모든 동작의 동일성을 판정하지 않는다.

문제는 공통 파일 내부의 책임과 상태가 겹치는 데 있다.

## 자동 검사와 문서 상태

이번 세션에서는 배경/화면/Phone 정책 훅이 실제로 호출됐다. 과거 문서의 “자동 호출 미확인”만으로 현재 상태를 설명하면 틀린다. 다만 결과는 배경·화면 `Captured executable is stale`, Phone 정책 `Stale candidate sources`의 ERROR다. 발동 확인과 현재 후보 검사 성공을 구분한다. 이 도구들은 읽기·수정·복구를 차단하지 않았다. stale 입력을 고치지 않고 같은 검사를 수동 반복하거나 과거 PASS를 현재 PASS로 바꾸지 않았다.

인계에는 과거의 “현재 작업”·“미설치”·“아직 구현 전” 문장이 여러 날짜로 누적돼 있다. 최신 상단과 TODO의 현행 요약을 읽어야 한다. 개발 계약·기술 문서의 옛 Phone 로딩 정책과 최신 HD 로딩 요구도 코드에서 일치하지 않았다. 다음 작업은 이 보고와 현행 TODO부터 시작하도록 인계 상단에 연결한다. 원문·실패·과거 커밋은 삭제하지 않는다.

허브의 최초 기능 변경 인계도 읽었다. 그 문서의 Unity 복구·잔여 32실패는 이 HM2의 신규 독립 이력과 다른 범위다. 해당 과거 SHA는 현재 Unity 분리 저장소에서 조회되지 않았다. 정상 부모를 추정하거나 과거 복구를 재실행하지 않았다.

## 수정과 후속 검사 순서

1. 상점 자원 준비 경계를 고치고 정식/치트 공통 경로에서 차가운 캐시의 전체 상품·인벤/장비/BOT·상세·거래를 검사한다. 실제 사용자 저장 사본의 `Icon10113.png` 상태와 연결한다.
2. 로딩의 HD 그림/최상단 정렬, 타이틀 시간 계약과 필수 자원 실패 정책을 수정한다. 기존 iPad·저장·전환 사건을 회귀 검사한다.
3. Skyway 연속 프레임에서 실제 레이어를 식별하고 원본 변환과 대조한다. 그 근거로 수정한다.
4. 전후 상태·페이지·배치·실제 Runtime/GPU/패키지의 연결 검사를 마친 후보로 하네스 입력을 갱신한다. 과거 실패는 남긴다.
5. 이후 실제 두 기기의 동일 조건 플레이·중단/복귀·발열/메모리 계측을 진행한다. 이번 CPU 성공으로 실기기/전 캠페인 완료를 선언하지 않는다.

이번에는 조사 문서·TODO·인계·검사 요약과 사이트 보고만 갱신한다. 게임 수정·새 앱 설치·게임 저장소 커밋/푸시·develop/main 병합은 수행하지 않는다.
