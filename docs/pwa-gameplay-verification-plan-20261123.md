# PWA 전장 하단 여백과 검증 개선 계획

## 확인한 결함

공개 정식 PWA v0.3의 Mac Chrome 1280×800 화면에서 Ruin Field 전장 아래로 이동하면 HUD 양옆 하단에 약 73픽셀의 검은 영역이 생긴다. 11월 22일 게임 화면의 원본 녹화와 공개용 MP4를 0.6초, 4.5초, 8.5초에서 비교했다. 두 파일 모두 왼쪽의 하단 여백은 위에서 727번째 줄에서 시작했고, 중앙에는 HUD가 있었다. 녹화는 게임 캔버스 전체를 담았다. 이 여백을 게시 전에 놓쳤다.

코드 작업 세션은 공개 v0.3(`bf1722ce`, 웹 빌드 `ee2005c12077937371acb21c`)과 로컬 치트 후보(`0b69513`, 웹 빌드 `2e5a212e7cd3d5ddccd21b8c`)를 Mac Chrome 158에서 실행했다. 공개판의 탭과 설치 앱, 치트 후보의 설치 앱에서 같은 73픽셀 여백을 재현했다. 후보의 기존 C++ 표시 검사는 통과했다. 조사 캡처와 픽셀 기록은 `.local/evidence/pwa-field-bottom.IkD4iu/`에 있다.

| 실행 사례 | 전장 진입 직후 HUD 양옆의 검은 행 |
| --- | --- |
| Mac 1280×800 공개 정식판과 로컬 치트 후보 | 73픽셀 |
| 좁은 Mac 912×420 치트 후보 | 38픽셀 |
| 가로 태블릿 1194×834 모의 설치 앱 | 76픽셀 |
| 세로 태블릿 1024×1366 및 834×1194 모의 설치 앱 | HUD가 지면 아래 영역을 덮어 연속 검은 행은 0픽셀 |
| 좁은 태블릿 504×834, 휴대폰 가로 912×420·915×412 모의 설치 앱 | 0픽셀 |

태블릿·휴대폰 결과는 Mac Chrome에서 기기를 모의한 결과다. 실물 iPhone·iPad·갤럭시와 Safari는 미검사다.

공개 v0.3의 소스 `bf1722ce`에서 데스크톱 카메라는 HD 하단 여유 94단위를 HUD 배율에 맞춰 유지한다. 전장 카메라가 맵 하단으로 내려가면 지형이 없는 영역에 WebGL의 검은 배경이 드러난다. 높이 800픽셀의 HUD 배율로 환산한 약 73픽셀이 녹화에서 측정한 높이와 일치한다. [카메라 설정](../Sources/Core/Simulation/CombatScene.cpp) · [카메라 하단 한계](../Sources/Core/Simulation/WorldNavigation.cpp)

치트판 브라우저 검사는 전장 진입 후 `validation-field` 캡처를 저장했지만 화면 요소를 검사하는 인자를 전달하지 않았다. 다른 화면에서도 가장자리 샘플은 높이 20%, 35%, 50%, 65%, 80%에 있었다. 이번 여백은 약 91%부터 시작했다. 코어의 전장 가장자리 검사는 912×420과 1280×360에서 `fillSurface=true`, `lowerOverscan=0`이라는 조건을 직접 넣었다. Apple 전장 GPU 검사는 상단 한 행을 판정한다. 1280×800 데스크톱 실행기의 실제 카메라 설정과 그린 프레임을 검사할 사례가 빠졌다. [브라우저 검사](../Web/tests/browser-smoke.mjs) · [전장 가장자리 검사](../tests/DisplayLayoutTests.cpp)

Mac mini 영상과 대표 프레임은 공개 README, 갤러리와 Sass 인계에서 내렸다. 원본 녹화, 게시본, 해시와 비교 프레임은 로컬 조사 자료로 보존했다. [영상 내림 PR #160](https://github.com/gelb2/HeavyMach2/pull/160) · [영상 교체 TODO](todo.md#남은-작업-순서)

## ProjectSendAddr에서 적용할 원칙

ProjectSendAddr의 2026년 11월 22일 회사 배치 설계 자아비판을 읽고 적용할 원칙을 정했다. 그 기록은 일부 호출 개선과 검사 통과 뒤에도 최종 결과 기준이 미달했고, 내부에서 정한 수치를 실측 근거 없이 사용했다고 설명한다. 헤비멕2에서는 **사용자가 보는 결과, 실제 실행 경로, 판정 조건**을 각각 확인한다.

| 가져올 원칙 | 헤비멕2에 적용하는 방법 |
| --- | --- |
| 사용자가 요청한 최종 결과로 판정 | 전장에 진입했다는 기록과 실제 전장이 마지막 행까지 올바르게 그려졌다는 결과를 따로 기록한다. 조작·소리·영상도 사용자가 보는 화면과 듣는 소리에서 확인한다. |
| 스스로 정한 조건을 확인 | 화면 크기, 판정에 사용할 픽셀, 반복 횟수는 실제 장애 조건과 기기 특성에 근거를 둔다. 부족한 조건은 개수로 덮지 않고 행으로 남긴다. |
| 가정과 실제 실행 경로를 대조 | 호스트가 넘긴 기기 분류와 화면 크기, `CameraPresentation` 출력, 공통 렌더러 입력과 최종 프레임을 연결한다. 검사에서 카메라 값을 직접 지정할 때도 정상 진입 경로의 별도 결과를 남긴다. |
| 후퇴를 보이면 기존 통과 범위까지 재검증 | 실패 화면에서 지형·HUD·조작·음향과 연관 검사를 다시 확인한다. 원인 수정 전후에 같은 저장·입력·화면 크기·판정 기준을 쓰고, 해상도나 빌드가 달라지면 해당 차이를 적는다. |
| 독립된 결과를 따로 남김 | 정식판과 치트판, 데스크톱과 모바일의 결과를 각각 기록한다. 연결되지 않은 실기기는 미검사로 남긴다. 반복 실패는 최초 조건과 증거를 남겨 원인을 확인한다. |

## 먼저 고칠 검증

1. **공개판과 치트 후보의 재현 화면을 기준으로 삼는다.** 확인한 1280×800 Mac Chrome 사례를 첫 회귀 입력으로 쓴다. Ruin Field의 실제 하단 경로, 확대 상태, 카메라 좌표와 HUD가 보이는 프레임을 남긴다. 브라우저 탭과 설치형 창을 나누고 각 실행의 소스·빌드·실제 캔버스 크기를 적는다.
2. **실패를 잡는 검사부터 추가한다.** 현재 브라우저 전장 시나리오에서 지도 상하좌우 끝까지 가고, 지형이 그려져야 하는 HUD 바깥의 네 가장자리와 마지막 픽셀 행을 검사한다. UI·지형 그림 자체의 검은 부분과 비어 있는 렌더 영역을 구별할 수 있도록 화면 지표와 카메라 투영 결과를 함께 사용한다. 구버전 프레임으로 이 검사가 실패하는 것을 확인한다.
3. **카메라와 지형 합성을 수정한다.** PWA가 공통 카메라에 지도 밖 이동을 제한하는 조건을 넘기는 방식부터 검증한다. 이 조건을 데스크톱과 PWA의 3:4 HD 경로에 함께 적용할 수 있는지 확인한다. 레터박스와 텍스처 늘리기는 금지한다. 원작 이미지의 비율과 샘플 좌표, HUD 배치, 표적·터치 판정, 카메라 이동과 공통 게임 로직을 기존 동작과 대조한다. 공통 코드 수정의 영향은 iPad 원본 대조 기준으로도 확인한다.
4. **같은 시나리오를 양쪽 빌드에서 다시 확인한다.** 데스크톱 기본 사례는 1280×800으로 유지한다. 기존 912×420·1280×360 검사에 폭이 다른 실제 창과 태블릿 세로·휴대폰 가로 사례를 연결한다. 기지에서 전장으로 진입하고, 가장자리로 이동한 뒤 확대·축소와 창 크기 변경을 반복한다. 수정 전후 이미지, 각 행의 결과와 실패 이유를 남긴다.
5. **공개 후보의 실제 화면을 확인한다.** 수정과 검사 결과를 대조한 뒤 배포 후보를 설치해 확인한다. 최종 영상은 공개판에서 다시 녹화한다. HUD 양옆과 맨 아래, 전체 프레임 크기, 게임 음향과 샘플 구간을 원본·인코딩 결과·GitHub 재생에서 확인한 뒤 README와 갤러리에 올린다.

## 작업에 적용할 순서

- 착수할 때 사용자 요청을 실행 조건과 관측 결과로 한두 문장에 적는다. 지형·HUD·입력·음향 등 영향받는 경로를 기존 문서와 코드에서 대조한다.
- 검사를 보여 줄 때 변경 전 실패와 변경 후 결과를 같은 조건에서 기록한다. 시뮬레이터·모의 브라우저·실제 기기·공개판의 결과는 실행 환경과 함께 쓴다. 문서 작업은 공개 링크와 표시 결과를 확인한다.
- 발표 전에 코드와 녹화가 요청을 충족하는지 다시 본다. 첫 검토로 판단이 어려우면 원작 동작 또는 실제 렌더링 로그와 대조하고, 관련 변경의 독립 검토에는 요구·코드·실행 증거를 넘긴다. 발견한 결함은 현재 결과와 남은 작업에 반영한다.

이번 계획의 첫 산출물은 **이전 빌드에서 실패하고 수정 후보에서 통과하는 전장 가장자리 검사와 짝지은 캡처**다. [현행 화면 기준](design-and-asset-rules.md) · [정식판과 치트판 검증 순서](validation-build.md)
