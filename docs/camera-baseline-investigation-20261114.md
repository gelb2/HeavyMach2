# iPhone 기본 줌이 과도하게 확대되는 원인

2026-11-14. 사용자는 전투·락온 줌은 동작하는 것으로 보이지만, 진입·대기 시 주변 전경이 적게 보이고 세밀한 조작을 강요받는다고 보고했다.

**복원판 iPhone에 추가한 화면 채움 배율과 대기 확대 계수의 곱셈을 원인으로 확인했다.** 같은 공통 코어를 실행하면 표적·이동 경로·입력이 없어도 확대된다. iPad 구성은 이 곱셈을 사용하지 않는다. 확인한 원본 HD 카메라·월드 표시 경로에도 이 계산은 없다. 이번에는 조사 도구와 기록을 추가했으며 게임 배율 수정·새 앱 설치는 하지 않았다.

## 실제 실행 결과

실제 `CombatScene`, `DisplayLayout`, `MapCamera`와 HD 준비 자원을 사용했다. 첫 전장Stage01_01·입구0·기본 장비·seed1·주인공 좌표(-275,-412)를 맞췄다. 조건별1,200tick 중0·1·60·120·300·600·1,200tick을 수집했다.

| 구성·시점 | 카메라 zoom 필드 | 최종 월드 표시 배율 | 보이는 월드 범위, HD 단위 |
|---|---:|---:|---:|
| iPhone Air 912×420, 진입 직후 | 1.784736 | 0.892368 | 1022×470.658 |
| 같은 iPhone, 약2초 게임 시간·120tick | 2.534987 | 1.267493 | 719.530×331.363 |
| 같은 iPhone, 약10초 게임 시간·600tick | 2.853002 | 1.426501 | 639.327×294.427 |
| 같은 iPhone, 약20초 게임 시간·1,200tick | 2.855566 | 1.427783 | 638.753×294.162 |
| iPad 1024×1366 · 상하 안전 영역20/24 | 1 | 1 | 1024×1322 |
| iPad Air13 구성1032×1376 · 상하20/24 | 1 | 1 | 1032×1332 |

마지막 세 행은 진입부터1,200tick까지 같은 값이다. 1032×1376은 전달한 검사 구성값이며 실제 iPad 화면을 이번에 다시 읽은 값은 아니다. 원본 HD 실행 결과와도 구분한다.

최종 표시 배율1은 HD 월드100단위를 화면100point로 그린다는 뜻이다. iPhone의 약20초 값에서는 같은100단위가142.778point를 차지한다. 같은 논리 거리의 그림이 iPad 구성보다 약42.8% 커진다. 실제 mm·픽셀 밀도 비교가 아니다.

iPhone은 진입 직후보다 길이가 약1.6배 확대되고 보이는 월드 면적은 약60.9% 줄어드는 방향으로 수렴한다. HUD·안전 영역 가림을 별도로 빼지 않았으므로 실제 조작 가능한 시야는 더 작다. 맵 밖 배경·가장자리 영역도 포함할 수 있다. 표시 범위를 모두 이동 가능한 지형이라고 해석하지 않는다.

동일한 iPhone 무입력 조건을 일시정지/진행 상태로 각각 실행했다. 경로0·표적0·위치·HP256은 모두 유지됐고 두 조건의 줌 결과는 같았다. 진행 조건은 월드 시간이 약19.92초까지 증가했다. 일시정지 검사 때문에 생긴 확대가 아니다. 확대 기능만 끈 진단 구성에서는 최소 채움 배율1.784736을 유지했다.

## 계산과 변경 이력

`CombatScene.cpp`의 `updateDisplay`와 `DisplayLayout::worldScale`이 다음 값을 결합한다.

```text
채움 배율 fit = 긴 화면변 / (1022 × 0.5)
목표 zoom = fit × clamp(2 − max(|표적차x|/360, |표적차y|/240), 1, 1.6)
현재 zoom += (목표 zoom − 현재 zoom) / 100
최종 월드 표시 배율 = 0.5 × 현재 zoom
```

표적과 경로가 없으면 차이는0이므로 계수는1.6이다. 912point 화면에서fit은 약1.784736, 목표zoom은 약2.855577, 최종 표시 배율은 약1.427789다. 화면이 넓다는 이유로 확대 기준 자체가 올라가고 그 위에 대기 확대가 붙는다. iPad는compact=false·focusZoom=false여서zoom1·월드 배율1이다.

- `7622bd1`: 작은 화면에 일반판의 거리 기반 목표1..1.6을 연결했다.
- `64ebe70`: 검은 여백 방지를 위해 유한 맵1022단위와 화면 긴 변에서 최소 줌을 계산했다. 넓은 iPhone에서는 최소값이1.6보다 커서 줌 변화가 막혔다.
- `9144809`: 줌 변화를 복구하려고 목표1..1.6에 채움 배율을 곱했다. 현재의 대기 과확대가 생긴 변경이다.

현재 설치된 정식판 게임 코드`bc3323a`와 조사한 카메라·배치·맵 표시·경계 처리4파일의 바이트가 같다. 미커밋 foreground/음향 후속 코드가 만든 카메라 차이는 아니다. 기존 검사는fit..fit×1.6 범위와 줌 변화는 확인했지만 대기 시야의 원작 적합성을 확인하지 못했다. 그 검사 통과를 기본 줌 적합성으로 해석하지 않는다.

## 원본과의 차이

원본 일반판2.0.1과 HD1.0.3의 기존 REA 의사 코드·ASM10파일을 해시로 다시 확인했다. 원본 IPA·실행파일은 외부로 전송하지 않았다. [원본 카메라 조사](iphone-universal-native-followup-20261113.md)와 [로직 비교](standard-hd-logic-differences-20261113.md)를 재사용했다.

| 대상 | 확인한 동작 | 근거와 한계 |
|---|---|---|
| 원본 일반판 | 0x57124는 무표적·무경로에서 목표1.6을 계산한다. 0x5af50은 차이/100으로 접근하고 작은 차이 확정 분기도 있다. 0x5a418은 배율로 카메라 경계를 계산한다. | 정적 분석. 복원판의 화면 긴 변 채움 배율을 다시 곱하는 계산과 다르다. |
| 원본 HD | processCamera 0x11cac는 표적/경로 중점·위치 추적·경계·배경 시차를 처리한다. drawVisual 0x3a39c는 월드 layer를 그린다. 이 경로에 일반판 방식의 줌 곱셈이 없다. | 정적 분석. HD 전체의 모든 간접 변환을 새로 전수 실행한 결과는 아니다. |
| 기존 HD 포팅판 | 내부 화면768×1024, 출력 fit을 거쳐 표시한다. | [기존 측정](reference-display-measurement-results-20261110.md). 이번에 원본을 다시 실행하거나 같은 저장의 신규 캡처를 만들지는 않았다. |

일반판 월드의 일부 단위는HD의0.5이며 화면은480×320이다. 원본 일반판의zoom1.6과 복원판 최종 표시1.4278을 같은 수치로 직접 비교하지 않는다. 이번에는 공통HD 단위에서 복원판 iPhone/iPad 차이와 추가 확대 계산의 출처를 확인했다. 같은 장비·프레임·줌의 원본 출력 픽셀·실물 크기 대조는 남는다.

## 수정 방향과 통과 기준

1. 화면 채움과 전투 카메라 확대를 분리한다. 검은 레터박스 금지를 이유로 대기 월드 배율에 화면 긴 변을 곱하는 정책을 수정한다.
2. 일반판의 실제 시야·그림 크기를 기준으로 작은 화면의 기본 배율·최대 확대를 정한다. 원본480×320을 현재 화면에 폭맞춤해 유닛 전체를 키우지 않는다. iPad의HD 월드 단위·기존 저장·공격·충돌·사거리·진행 규칙은 유지한다.
3. HUD·입력 역변환과 월드 표시를 공통 코드에서 연결한다. iPhone 전용 게임 소스·에셋·UIKit 인게임 UI를 추가하지 않는다.
4. 배율을 낮출 때 유한 맵 경계·배경 시차·가장자리 샘플링을 함께 검사한다. 기존MapPreview의 배경 채움/CLAMP_TO_EDGE는 이미 있지만 넓은 시야에서 자연스러운 표시까지 검증했다고 간주하지 않는다. 이동 가능한 지형을 임의 생성하지 않는다.
5. 진입·무표적 대기·근/원거리 락온·경로 진행/종료·정지/재개를 여러 화면 크기의 동시 치트에서 검사한다. 최종 배율·시야·주인공/HUD 가림·입력 왕복·경계 전투를 함께 확인한다. 새 구현값에 맞춰 검사 기준을 무조건 넓히지 않는다.

최종 배율은 아직 수정·채택하지 않았다. 조사만 요청받은 이번 작업에서 앱·사용자 진행·게임 자원을 변경하지 않았다. 실제 조작감 개선과 발열/foreground 정지 해결도 완료로 보고하지 않는다.

## 재현 도구와 근거

`tools/probe_camera_zoom.cpp`는 실제 공통 코어에 연결하는 오프라인 측정 도구다. 기존CPU 텍스트 검사host를 사용하므로 원본 폰트/GPU/음향·실기기 성능 측정에는 사용하지 않는다. 사용자 세이브 입력·저장 경로는 없다.

```sh
cmake --build build/core --target HeavyMach2Core -j 4
c++ -std=c++20 -O2 -ffp-contract=off -fno-fast-math -ISources -Itests tools/probe_camera_zoom.cpp build/core/libHeavyMach2Core.a -o .local/evidence/camera-baseline-20261114/probe_camera_zoom
.local/evidence/camera-baseline-20261114/probe_camera_zoom .local/prepared/HD
```

[49표본·소비 소스 해시·원본 근거ID](evidence/camera-baseline-20261114.json)를 보존한다. 첫 실행은world text host 누락으로 실패했고 기존CPU text host를 명시해 수정한 뒤49표본을 수집했다. 첫 실패와 최종 출력은로컬`.local/evidence/camera-baseline-20261114/`에 보존한다.
