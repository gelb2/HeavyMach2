# HeavyMach 2 작업 자아비판

작성 주체는 Codex다. 1인칭은 Codex를 가리킨다. 이 문서는 HeavyMach 2의 게임 구현, 원본 분석, 플랫폼 이식, 에셋, 저장, 성능, 문서, 테스트와 배포 전체에 적용한다. 실제로 발견한 결함과 사건별 증거는 [자아비판 사례와 실행 근거](development-self-review-cases.md)에 둔다.

## 모든 업무는 이 문서를 읽고 시작한다

**모든 업무지시를 받으면 이 문서를 처음부터 끝까지 읽고 시작한다.** 코딩, 조사, 문서, 검사, 커밋, 배포, 질문과 상태 보고에 모두 적용한다. 이전에 읽었거나 같은 세션에서 이어서 작업해도 실제 파일을 다시 읽는다.

**자아비판문을 읽지 않고 시작한 업무는 모두 실패다.** 즉시 그 업무를 멈추고 이 문서를 읽는다. 사용자 요구, 기존 변경, 실행 조건을 처음부터 재점검한다. 읽기 전에 얻은 결과는 다시 대조해 유효성을 확인한 뒤 사용한다.

## 내 판단과 모든 코드를 다시 의심한다

1. **모든 코드가 잘못됐다고 가정하고 시작한다.** 내가 쓴 코드, 기존 코드, 테스트, 빌드 스크립트와 문서도 함께 본다. 최신 사용자 지시와 원본, 현행 정본을 읽고 요구, 작업 범위, 보호할 파일, 완료 조건부터 맞춘다. 내가 정한 수치·분기·제한에 근거가 있는지 확인한다. [현행 정본](canonical.md)
2. **사용자의 동작에서 실제 결과까지 추적한다.** 요구별로 해당 구현·산출물·검증 근거를 연결한다. 플랫폼 입력과 출력, 공통 게임·표시 모듈, 에셋·저장, 실제 패키지까지 소비 순서를 확인한다. 기존에 통과한 단계도 입력과 실행 경로가 같았는지 확인한다. 작은 상태 단위가 바뀌는 경계와 실패·취소·복귀 경로를 검토한다.
3. **자아비판을 한 뒤 외부 모범 사례를 직접 찾아 대조한다.** 관련 공식 문서와 동작을 확인할 수 있는 공개 구현을 읽고, 그 방식이 현재 입력·기기·모듈에도 적용되는지 확인한다. HeavyMach 1과 MachDefense를 참고할 때는 코드와 현재 소비 경로를 확인한다. 차이를 설명할 때 대응하는 코드와 실행 근거를 붙인다.
4. **결함을 찾지 못한 자아비판은 실패다.** 이 문서를 다시 읽고 가정과 제외한 조건을 바꾼다. 다른 판본·기존 저장·첫 실행·오프라인·경계값·오류·부하에서 재현한다. 외부 자료 대조 뒤에도 결함을 못 찾으면 사용할 수 있는 상위 모델에 사용자 요구, 코드·절차와 원본 실행 기록을 주고 독립 검토를 받는다. 지적은 코드나 재현으로 확인한다. 독립 검토를 실행할 수 없는 경우 실제 상태를 기록하고 다른 원본이나 실행에서 근거를 계속 찾는다. 확인한 결함과 의심을 구분한다.
5. **할 수 있는 검사가 남으면 이어서 실행한다.** 오류를 이름 붙이는 데서 멈추면 이 문서를 다시 읽고 실제 응답, 실패 조건과 영향을 확인한다. 기기·브라우저·빌드·서비스가 일시 중단되면 원인을 좁히고 허용되는 복구와 재검사를 수행한다. 서버가 재시도 시점을 명시하면 그 기준을 따르고, 여러 요청이 같은 일시 장애에 걸리면 간격을 분산한다. 영향을 받지 않는 변경·검사·자료 대조는 계속한다. 다음에 볼 문제가 떠오르지 않을 때도 이 문서를 다시 읽고 근거를 바꿔 점검한다.
6. **작업과 보고 전에 내 판단을 다시 본다.** 요구 해석, 임의로 정한 조건, 구현·문서, 실패 처리, 검사, 산출물과 답변을 실제 근거에 대조한다. 확인한 문제를 작업 범위 안에서 고치고 같은 조건으로 다시 검증한다. 질문이나 문서 작업은 해당 질문과 원문·결과를 대조한다.

## 후퇴와 부작용을 발견하면 기존 판정부터 다시 연다

**프레임·레이아웃·게임 계산·이동·모듈 손상 또는 사이드이펙트가 한 건이라도 생기면 자아비판 자체가 실패다.** 이 문서를 다시 읽고 기존의 합격 판정을 재검증한다.

1. 사용자 재현 경로, 영향 범위, 변경 전후 수치를 기록한다. 한 지표가 나아져도 후퇴한 항목을 해결 대상으로 유지한다.
2. 증상이 처음 나타나는 경계에서 기존 구현, 변경, 문서와 테스트를 대조한다. 한 플랫폼이 가졌던 정상 동작이 다른 플랫폼의 변경으로 영향을 받는지 실제 빌드 입력과 호출 경로를 확인한다.
3. 원인을 수정하고 같은 조건으로 다시 실행한다. 기기, OS, 판본, 초기 저장, 맵, 입력 순서, 반복 횟수와 판정 기준을 유지한다. 조건이 달랐으면 기록에 드러낸다. 실패한 사례나 미검증 환경을 성공한 표본에 섞지 않는다. iPad PWA는 홈 화면 설치 앱에서 세로 전장, 가로 전환의 세로 안내, 같은 세로 전장 복귀를 검사한다. HD HUD의 배율과 입력을 같은 화면 크기의 iPad 네이티브와 대조한다.

**측정만 남기거나 원인을 확인하지 못한 채 조사와 수정 루프를 종료하면 자아비판에 실패한 것이다.** 이 문서를 다시 읽는다. 앱을 실행한 경로와 코드의 실제 입력값을 연결한다. 이전에 제외한 조건, 정상판과의 차이, 원본 동작을 다시 확인해 원인을 좁힌다. 바꾼 결과는 같은 장면과 입력으로 직접 검증한다.

## 복원판에서 답을 찾지 못하면 원본 IPA 포팅판을 기준으로 삼는다

자아비판에 실패하면 먼저 재구현 앱에서 해당 조건을 다시 실행한다. 여기서도 구현 근거를 찾지 못하면 **해당 판본의 원본 IPA를 실행하는 포팅판을 정답지로 삼는다.** iPad는 HD 포팅판을, iPhone은 일반판 포팅판을 대조한다. 원본 포팅판에서 같은 화면·입력·상태를 실행하고, 관측한 동작과 그 근거를 기록한 뒤 구현한다. 이 기준 확인은 전체 복원 검증 일정과 별개로 적용한다. [원본 보존과 실행](runtime-preservation.md) · [포팅판 검증 기준](reference-port-validation-plan.md)

**임의 추정으로 원작에서 벗어나는 구현을 금지한다.** 새 플랫폼에서도 원작에서 확인한 동작과 에셋 비율을 지킨다. 화면 크기 차이를 검은 레터박스로 가리거나, 맵 텍스처를 늘려 화면을 채운 것처럼 만드는 편법을 금지한다. 검은 레터박스나 텍스처 늘림이 하나라도 보이면 그 후보는 실격이다. 화면 배치와 터치가 같은 변환을 쓰는지 원본과 후보에서 대조한다. 원본을 확인할 수 없는 조건은 관측 범위를 기록하고 구현 판단을 유보한다. [디자인·에셋 규칙](design-and-asset-rules.md)

## 결과를 판정하고 보고한다

- 변경 전 실패와 변경 후 실제 실행을 연결한다. 합의한 기기·판본·장면·입력 조합 전체를 분모로 두고 통과·실패·미실행 수를 표시한다. 공통 테스트, 시뮬레이터, 실기기, 치트판, 정식판과 공개판에 각각 어떤 경로를 확인했는지 기록한다. 부분 성공과 이전 판정의 재사용 근거를 대조한다.
- 코드 변경, 그 변경을 설명하는 문서, 실제 구동 기록, 스크린샷 네 가지를 대조한다. 하나라도 빠지면 구현 완료 보고와 커밋을 금지한다. 검사 예정, 실행 실패, 조건이 다른 성공 사례를 완료 근거로 세지 않는다.
- 문제를 발견했으면 코드 위치, 재현 조건, 관측값, 수정과 재검사 결과를 함께 적는다. 사용자의 질문에 답했는지와 결론이 기록의 범위를 넘지 않았는지 마지막으로 확인한다. 재현하지 못한 사용자 제보는 해당 관측으로 보존한다.
