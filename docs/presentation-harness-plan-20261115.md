# 디자인·에셋 로컬 하네스와 강제 실행 계획

> 기존 하네스와 검사 훅을 제거했다. 이 문서는 당시 기록이며 새 하네스의 설치 또는 실행 지침으로 사용하지 않는다.

## 실제 실행 상태 — 2026-11-15 후속

현재 대화의 네이티브 훅에서 금지 파일 차단, 허용 파일 수정, 실제 패치 실패, native transcript를 읽는 실패 복구, 복구 후 후속 수정을 확인했다. 외부 폴더에서 시작한 세션의 local 도구 호출을 건너뛰던 분기를 제거했다. 상세 원인·실패 기록·남은 검증은 [훅 연결·실패 복구 기록](harness-runtime-repair-20261115.md)을 따른다. 아래의 구현 전·미실행 표현은 최초 계획 작성 시점의 기록이다. 게임 화면 개선과 전체 시각 검사 완료를 뜻하지 않는다.

## 최초 계획의 범위

[디자인·에셋 정본](design-and-asset-rules.md)을 로컬 검사와 완료 판정에 연결하는 계획이다. 이 Mac의 파일 변경 감지·Git 훅·빌드/설치 전 검사로 구성한다. 서버를 추가하거나 GitHub 요금제를 바꾸는 작업은 필요하지 않다. 게임 구현과 강제 훅은 아직 추가하지 않았다.

사용자 요청은 다음 세 가지다. 레터박스 금지의 실제 검사·성공/실패 기준, iPhone/iPad 원본 배경의 실제 소비 검사·성공/실패 기준, 해당 영역을 작업할 때 검사가 자동으로 발동하는 방법이다. 원작 자원·진행 저장을 보존하고 기존 공통 C++ 게임 스택을 유지한다. Python/Node는 기존 오프라인 검사 역할이다.

## 설계 정정 — 에이전트 훅과 커밋 전 입증

### 빠진 이유와 현재 사실

앞선 계획은 작업 시작을 checkout/merge와 파일 변경 감시에 연결했다. 에이전트가 사용자의 요청을 받고 첫 수정 도구를 실행하는 시점, 그때 적용한 규칙과 실제 수정 결과를 연결하는 절차를 빠뜨렸다. Git 훅을 설정한 것과 에이전트 하네스가 작업 전에 개입하는 것을 혼동한 설계 누락이다.

2026-11-15 확인 결과, 허브와 분리 전 폴더의 `.codex/hooks.json`은 `{"hooks":{}}`이고 HeavyMach2에는 해당 파일이 없다. 허브의 `context_guard_hook.py`도 빈 응답만 출력하는 폐기된 훅이다. 이를 재사용하거나 폐기된 자동 새 채팅/강제 인계 기능을 되살리지 않는다. 설치된 CLI는 0.167.0-alpha.3.2다. 이 값으로 현재 대화를 처리하는 런타임 버전이나 실제 훅 발동까지 확인했다고 주장하지 않는다.

OpenAI 공식 문서에서 작업 요청·도구 실행 전후·작업 종료 이벤트와 명시적 도구 차단을 확인했다. 프로젝트 훅의 신뢰 설정과 실행 경로별 지원 차이가 있고, 훅 오류/시간 초과가 도구 실행을 허용할 수 있다. 따라서 설정 파일 존재, 훅 스크립트 수동 실행, CLI 버전만으로 강제 실행을 입증할 수 없다. [공식 Hooks 문서](https://learn.chatgpt.com/docs/hooks)를 근거로 하되 실제 현재 런타임의 시험 결과를 별도로 남긴다.

### 1. 작업 시작에 붙이는 에이전트 훅

구현 위치는 HeavyMach2 전용 `.agents/harness/`와 `.codex/hooks.json`으로 계획한다. 다른 두 게임과 분리 전 폴더는 수정하지 않는다. 현재 대화는 분리 전 폴더에서 시작했으므로 HeavyMach2 안에 훅 파일만 만들면 현재 세션에도 적용된다고 가정하지 않는다. HeavyMach2를 실행 루트로 사용한 경우와 외부 cwd에서 이 저장소를 대상으로 도구를 사용하는 경우를 나누어 검사한다. 외부 cwd 지원은 사용자 수준의 범위 제한 디스패처로 계획하며, 실제 대상 realpath가 HeavyMach2일 때만 관여한다. 사용자 수준 설정 변경은 구현 단계의 명시한 변경 목록에 포함하며 기존 notify·다른 프로젝트 훅을 보존한다. 이번 계획 작성에서 설정을 설치하지 않는다.

| 에이전트 이벤트 | 계획한 동작 | 남길 근거 |
| --- | --- | --- |
| `SessionStart` | 현재 실행기의 이벤트 지원·훅 소스/신뢰·저장소 경계를 확인한다. | 런타임 식별, 설정/스크립트 해시, 실제 발동 ID |
| `UserPromptSubmit` | 사용자 요청과 기존 미완료 범위를 연결한다. 관련 규칙 본문·기기별 에셋 표·금지사항·필수 검사 목록을 모델 컨텍스트에 넣는다. | 세션/턴/작업 ID, 요청 해시, 주입한 내용과 정본 해시 |
| `PreToolUse` | 파일을 바꾸기 전에 실제 대상 경로와 영향을 분류한다. 시작 기록·현재 규칙·변경 허용 범위가 없으면 명시적으로 거부한다. 커밋/설치/완료 게시 도구도 별도로 검사한다. | 도구 호출 ID, 입력 해시, 수정 전 파일 해시, 허용/거부 이유 |
| `PostToolUse` | 실제 종료 상태와 변경 파일을 다시 읽는다. 예상 밖 변경·빠진 전후 기록을 검출하고 이전 PASS를 만료시킨다. | 수정 후 해시, 종료 상태, 재검사 범위, 전후 연결 |
| `Stop` | 요청이 상태 보고인지 완료 보고인지 구분한다. 실패·미실행 상태를 완료로 기록하지 못하게 한다. 상태 보고·오류 보고·사용자 중단을 막아 무한 작업시키지 않는다. | 작업 상태, 검사 결과 ID, 미완료 목록 |

요청 문장의 키워드만으로 분류하지 않는다. 요청에는 ‘계속해’만 있어도 앞선 작업 범위를 이어받고, 경로/의존성으로 적용 규칙을 확인한다. 첫 수정에서는 넓게 분류하고 실제 변경으로 좁힌다. 단순 조회에는 제품 GPU 합격을 요구하지 않는다. 규칙 주입 기록은 내용을 전달했다는 증거이며 모델의 이해나 준수를 증명하는 기록으로 부르지 않는다.

### 2. 도구 우회·고장 처리

`apply_patch`, 셸의 파일 쓰기, 코드 실행 안의 중첩 도구, 파일을 바꾸는 MCP 등 현재 제공 경로를 실제로 목록화한다. matcher에 도구 이름 몇 개만 넣고 전체 적용이라고 보고하지 않는다. 입력의 cwd·절대경로·`..`·심볼릭 링크·이름 변경·삭제·새 파일과 간접 소비를 해석해 저장소 경계를 확인한다. 파일명만 바꾼 새 UI도 분류한다.

임의 셸/동적 스크립트의 모든 동작을 문자열 검사로 알아낼 수 있다고 가정하지 않는다. 보호 영역 수정은 경로/입력을 받는 제한된 로컬 실행기로 연결한다. 해석할 수 없는 쓰기 명령은 허용하지 않고 구조화한 수정 경로로 다시 실행하게 한다. 기존 범용 대화형 셸에 `write_stdin`으로 새 명령을 보내는 경로는 보호 작업에 사용하지 않는다. 입력이 필요한 승인된 빌드/검사 프로세스와 범용 셸을 구분하고 세션 연결도 기록한다. 중첩 도구와 재사용 세션이 실제로 관측되는지는 고장 시험 전까지 미확정이다.

예상한 검사 실패는 지원되는 명시적 deny 응답으로 반환한다. 예외·잘못된 JSON·시간 초과를 거부 응답과 혼동하지 않는다. 정상 훅 경로 외에 제한된 수정 실행기와 Git/빌드 gate도 자기 기록을 검사한다. 훅이 고장 나 직접 수정이 실행됐더라도 근거 없는 변경은 `UNATTESTED`로 표시하고 커밋/설치 합격을 주지 않는다. **이 사후 탐지는 ‘첫 수정 자체를 막았다’는 뜻이 아니다.** 그 경로의 사전 차단 시험에 실패하면 작업 시작 강제 연결은 미완료로 남긴다.

훅 신뢰 등록을 몰래 바꾸거나 신뢰 우회 옵션을 사용하지 않는다. 정의가 신뢰되지 않았거나 현재 세션이 변경된 훅을 로드하지 않았다면 `HOOK_NOT_ACTIVE`다. 실제 활성화와 로딩을 검증한 뒤 보호 작업을 시작한다. 이 단계는 별도 네트워크 서버 없이 현재 Mac에서 수행한다.

### 3. 발동과 작업 결과를 잇는 기록

한 작업에 시작 기록 하나와 수정 도구별 전후 기록을 남긴다. 로컬 경로는 `.local/evidence/presentation-harness/<work-id>/`로 계획한다. 원시 사용자 대화·비밀값·IPA·저장 원본을 Git이나 보고 사이트로 복사하지 않는다.

필수 연결은 `작업 시작/요구 원문 고정 → 규칙 주입 → 도구 실행 전 허용 → 실제 수정 후 해시 → 같은 후보의 동시 치트/시뮬레이터 → 실제 화면·원문 대조 → 불일치 원인 분석/수정·재검사 → 커밋 대상 트리`다. 시각만 비교하지 않고 이벤트 순서·세션/턴/도구 ID와 파일 내용으로 잇는다.

- `start.json`: 저장소 realpath·브랜치·시작 HEAD·기존 dirty 목록/해시·작업 범위·정본/훅/실행기 해시.
- `events.jsonl`: 실제 이벤트 ID·호출 순서·도구/입력 해시·허용/거부·전후 파일 해시·종료 상태. 훅 처리기가 생성하며 모델이 성공 로그를 직접 작성하는 경로는 허용하지 않는다.
- `requirements.json`: 작업 전 사용자 요구 원문/해시·적용 규칙·판정 항목/분모와 실제 의존성, 기기/기지/화면/상태 목록. 전체 기지는 런타임/데이터 열거 결과와 대조한다. 간단한 검사만 늘려 일치율을 부풀리지 않는다.
- `verification.json`: 기존 6절의 실제 검사·바이너리·캡처/자원 근거와 필수 조건별 결과. 프로그램이 만들고 검사 로그/파일과 재대조한다.
- `visual-review.json`: 같은 후보의 실제 캡처/동작과 요구 원문의 대응, 실제 이미지 열람 근거·항목별 충족/미충족/미확인·일치율·금지사항/필수 기능 판정·불일치 원인. 자동 수치 결과와 직접 화면 관찰을 별도 필드로 남긴다.
- `gate.json`: 검사한 Git stage 트리·입력 명세·시작/실행 기록·검사 결과의 연결, 최종 허용/거부 이유.

작업 시작 전에 있던 사용자 변경은 기저 목록으로 보존한다. 이를 이번 에이전트 훅이 감독한 변경으로 소급해 표시하지 않는다. 다른 세션이나 외부 편집기가 같은 파일을 바꾸면 충돌/미연결 변경으로 표시하고 실제 작성 범위와 검사 대상을 다시 정한다. 실패 근거를 지워 연속된 성공 기록처럼 만들지 않는다.

로컬 로그/해시는 우발적 누락과 오래된 근거 재사용을 검출한다. 같은 사용자 권한으로 임의 명령을 실행할 수 있는 환경에서 모델이 모든 파일·훅을 악의적으로 변조하는 행위를 막는 독립 보안 증명은 아니다. 해시 연결이나 같은 권한의 서명 키를 변조 불가능한 증명으로 설명하지 않는다. 이번 계획은 정상 작업 경로의 자동 개입과 독립된 단계별 재검사를 목표로 한다.

### 3-1. 커밋 검사 전에 실제 화면과 요구 원문 대조

이 단계는 기록 생성 뒤, 다음 커밋 대상 검사와 최종 차단 판정 전에 반드시 수행한다. 구현 중 기능별 포팅판/빌드를 반복하는 절차를 다시 도입하지 않는다. 전체 구현과 동시 치트 조건을 갖춘 동일 후보를 최종 묶음에서 실행하며 실패 수정 뒤 관련 재검사는 허용한다.

1. 작업 전 요구 원문·정본 해시와 항목별 판정 조건을 고정한다. 원문의 최신 정정과 화면별 예외를 보존한다. 요구를 요약하는 과정에서 누락하거나 약화하지 않는다.
2. 같은 후보의 치트빌드를 시뮬레이터에서 실행한다. 실제 게임 renderer·자원·상태로 허브 전수와 관련 상세/버튼/구매/임무 조건을 동시에 검사한다. 서로 배타적인 화면을 한 Session에 겹치지 않는다.
3. 실제 실행 화면을 원래 비율/해상도로 캡처하고 이미지 열람 도구로 직접 본다. 원문과 화면의 그림 출처·비례·전체 표시·버튼 위치·잘림/겹침·숫자를 항목별로 대조한다. 정적 목업·캡처 파일 존재·CPU PASS는 직접 관찰을 대신하지 않는다.
4. 버튼의 표시 위치를 실제로 눌러 선택/상세/구매·판매/수락·완수·보상/복귀와 상태 변화를 검사한다. 이미지를 보고 기능/코드 누락까지 없다고 판정하지 않는다. 전체 시나리오는 동시 치트가 수집하고 직접 화면/입력 확인을 그 결과에 연결한다.
5. `일치율 = 충족한 적용 요구 항목 수 / 작업 전에 고정한 적용 요구 항목 수 × 100`으로 기록한다. 미확인·일부 충족·근거 누락은 0으로 둔다. 모든 적용 항목과 기기/기지/화면별 실패를 공개하며 쉬운 캡처/테스트 수로 분모를 부풀리지 않는다. 자동으로 산출하지 못한 시각 판정은 판단 근거와 관찰자를 남긴다. 원문이 의미하는 유사도를 임의 픽셀 점수로 바꾸지 않는다.
6. **90% 미만이면 탈락**하고 에셋 출처/선택 → reader/아이콘/타일 → 실제 텍스처 소비 → 배치/입력 → 공통 코드/이벤트/기능 누락을 추적한다. 실패 조건에서 수정·재검사할 범위를 기록한다. 90% 이상이어도 레터박스·기기 그림 오류·필수 기능 누락 등 정본 위반은 탈락이다. 충족하지 못한 필수 요구를 나머지 10%로 면제하지 않는다.

현재 소스에서는 `GameSession.cpp`가 아이템의 `iconImage()`를 ItemView로 넘기고 `Screens.cpp`가 `entry.icon`을 그린다. Apple 준비 자원 루트는 HD이며 Phone 메뉴 준비 목록에는 상품 아이콘이 없다. 이는 정적 경로 조사이고 실제 앱 텍스처/화면 합격이 아니다. 구현 검사는 HD ItemCode → 아이콘 파일/타일 → 준비/번들 SHA → 실제 텍스처를 연결한다.

기기별 배치/상품 정책은 다음과 같다.

| 대상 | iPhone 검사 기준 | iPad 검사 기준 |
| --- | --- | --- |
| 허브·사령부·상점 배경/버튼 배치 | Phone 원본의 구도와 버튼 위치·상호 관계를 참고하고 공통 표시/입력 변환에 연결 | HD 원본과 기존 iPad 기준 유지 |
| 상품/보유 아이템 이미지·데이터 | HD 원본 이미지/타일·HD 게임 데이터 | 같은 HD 원본 이미지/타일·HD 게임 데이터 |
| 상품/인벤/기능 수량 | HD 수량 유지. Phone 그림의 칸수에 맞춰 기능/품목 축소 금지 | 기존 HD 수량 유지 |

Phone 배치 참고와 HD 상품/게임 데이터 사용은 서로 다른 책임이다. Phone 메뉴의 기능 수량이나 좌표를 화면 크기와 무관하게 그대로 복사하지 않는다. 기기별 배치 정책만 공통 모듈에서 선택하며 기기별 별도 게임 로직·UIKit UI를 만들지 않는다. 세로 스크롤·레터박스·임의 잘림으로 수량 차이를 감추지 않는다.

### 4. 커밋 직전 실제 검사 순서

Git pre-commit은 아래 판정을 호출하는 마지막 연결이다. 에이전트 `PreToolUse`도 커밋 명령 전에 같은 판정을 호출한다. 기존 IPA·비밀정보 검사는 유지한다.

1. **대상 고정:** Git index의 경로·blob·모드/심볼릭 링크와 `git write-tree` 결과를 읽는다. 작업 폴더가 다르면 그 결과를 대신 쓰지 않는다. 컴파일/실행의 소스는 이 stage 스냅샷과 같은 검사용 후보로 연결한다. 원본/준비 자원 등 Git 밖 입력은 별도 SHA 명세로 고정한다.
2. **작업 전 개입 확인:** 해당 세션/턴의 실제 시작·규칙 주입·도구 전후 이벤트가 있는지 검사한다. 현재 index의 변경마다 기존 dirty 또는 해당 이벤트를 연결한다. 사후에 수동 생성한 start 파일, 빠진 중간 이벤트, 불일치한 전후 해시는 거부한다.
3. **설정 일치 확인:** 실제 로드한 훅·현재 스크립트·정본·분류표·검사 목록이 기록과 같은지 확인한다. 하나라도 바뀌면 관련 PASS를 만료시킨다. 훅 자신이나 검사 기준 변경도 보호 대상이다.
4. **누락 확인:** 현재 stage의 변경과 소비 의존성에서 필수 검사 집합을 다시 계산한다. 에이전트가 고른 목록만 믿지 않는다. 여섯 기지×두 기기×허브/사령부/상점과 해당 상태를 요구하며, 새 기지/상태 누락도 거부한다. 실제 영향 범위에 따라 전장/HUD/정비 등도 포함한다.
5. **실행·실물 대조 결과 재검증:** 종료 코드·원본 로그·캡처·자원 출처·관측값과 `visual-review.json`의 원문/항목/일치율을 다시 읽는다. 같은 후보의 실제 화면 열람·입력 결과가 없으면 NOT_RUN이다. 일치율 90% 미만, 검은 여백, 잘못된 기기 그림, 누락/가림, 미실행/오류/만료가 하나라도 있으면 실패다. 90% 이상이나 `PASS` 문자열·실행 횟수로 필수 요구 위반을 면제하지 않는다.
6. **후보 일치 확인:** stage 소스/검사, 준비 자원, 빌드 설정·실행파일 SHA/UUID, 검사 입력이 정확히 같은 후보인지 검사한다. 근거 파일은 로컬에 두고 그 근거를 설명하는 문서 때문에 소스 지문을 순환 참조하지 않게 한다. 문서라고 해서 정본·검사 기준 변경까지 제외하지 않는다.
7. **실행 중 변경 확인:** 로컬 수정 실행기끼리 작업 잠금을 사용하고, 검사 시작/끝 및 커밋 직전에 stage/의존 파일 해시를 재확인한다. 변화가 있으면 `STALE`로 거부한다. 외부 프로세스와의 완전한 원자성을 가정하지 않는다. post-commit에서는 실제 커밋 트리와 승인한 트리를 대조해 불일치 시 푸시·완료 자격을 철회한다. 자동 reset/rollback은 하지 않는다.

논리 판정은 `현재 훅 활성 + 작업 전 기록 연결 + 필수 검사 누락 없음 + 같은 stage/후보의 실제 검사 합격 + 검사 뒤 변경 없음`이 모두 참일 때만 `COMMIT_ALLOWED`다. `HOOK_NOT_ACTIVE`, `UNATTESTED`, `FAIL`, `NOT_RUN`, `ERROR`, `STALE`이면 차단한다.

문서만 바꾼 이번 계획 커밋에는 훅/GPU 검사가 이미 존재하는 것처럼 요구하지 않는다. 문서 정합성·원본 보존·기존 Git 검사를 적용하고 구현 상태를 false로 남긴다. 사용자가 명시한 미완료 보존 커밋은 앞선 PENDING 규칙을 따르며, AI가 자의적으로 완료 gate를 면제하지 않는다.

### 5. 실제 발동·차단의 인수 검사

실제 현재 런타임으로 저장소 전용 임시 파일/fixture를 사용한다. 훅 처리기를 직접 호출한 단위 검사만으로 이 표를 통과시키지 않는다. 제품 소스·원본·저장에는 고장 입력을 적용하지 않는다.

| 시험 | 반드시 관측할 결과 |
| --- | --- |
| 요청 후 첫 보호 파일 수정 | 요청/규칙 주입·Pre 이벤트가 파일 수정 전에 존재하며 Post와 같은 호출 ID로 연결됨 |
| 시작 기록 없이 수정 | 실제 도구가 거부되고 파일 바이트가 그대로임 |
| 외부 cwd/중첩 코드 실행/다른 도구/심볼릭 링크 | 실제 보호 경로에 같은 검사가 적용됨. 관측 못 하는 경로는 미지원으로 막음 |
| 재사용 대화형 세션에서 쓰기 시도 | 허용된 한정 프로세스 외의 보호 파일 수정 거부, 누락 시 강제 연결 불합격 |
| 신뢰 안 된 훅·정의 변경·재시작 전 미로딩 | 활성으로 보고하지 않음. 작업 시작과 완료 gate 실패 |
| 훅 crash/시간 초과/응답 오류 | 실제 도구 실행 여부를 기록. 사전 차단 실패를 숨기지 않으며 미연결 변경의 커밋 gate는 반드시 거부 |
| 훅 발동 기록만 있고 시각 검사는 없음 | NOT_RUN·커밋 거부 |
| 캡처는 있으나 실제 열람/원문 대조·버튼/상태 근거 없음 | NOT_RUN·커밋 거부 |
| 원문 대조 일치율 89% | 탈락·에셋 출처/소비부터 코드/기능 누락 조사 |
| 95%이나 레터박스 또는 필수 구매 기능 누락 | 정본 위반 FAIL·커밋 거부 |
| HD 상품 그림 대신 Phone 그림 사용, 버튼은 HD 배치 잔류 | 에셋 출처/Phone 배치 기준 불일치 FAIL |
| 옛 PASS/다른 stage/다른 바이너리/빠진 상태 결과 | STALE 또는 누락 FAIL·커밋 거부 |
| 3개 실패 예시만 검사하고 나머지 기지 누락 | 전수 행렬 누락·커밋 거부 |
| 검사 후 소스·정본·검사·자원 중 하나 변경 | 근거 만료·커밋 거부 |
| 정상 fixture를 훅→수정→실제 검사→stage로 전달 | 같은 트리만 허용. 이어 실제 임시 커밋 트리 일치까지 확인 |
| 상태 보고·실패 보고·사용자 중단 | 사실을 그대로 보고하며 계속 작업을 강제하지 않음 |

이 인수 검사와 기존 7절의 검출기 고장 검사를 모두 통과한 뒤에만 ‘해당 영역 작업 시작에 하네스가 강제로 발동하며, 커밋 전에 실제 작업/검사 근거를 대조한다’고 보고한다. **현재는 설계 보강이며 에이전트 훅 설치·실제 발동·인수 검사는 모두 미실행이다.**

현재 이 전수 화면 검사는 **계획/미실행**이다. 실제로 수행한 것은 기지 테이블·자원 참조 조사다.

## 현재 확인한 빈틈

- HeavyMach2의 `.githooks/pre-commit`은 IPA·gitleaks, `pre-push`는 IPA·브랜치 흐름·gitleaks·LFS만 검사한다. `core.hooksPath=.githooks`는 설정돼 있지만 화면·에셋 합격 여부를 검사하지 않는다.
- 허브의 `.agents/harness/cli.mjs`는 선택한 검사 명령을 실행하는 공통 진입점이다. HeavyMach2의 시각 정책·에셋 대응·최신 실행 근거를 강제하지 않는다. `doctor` 성공은 설치 구성 검사이며 게임 합격이 아니다.
- `DisplayConfiguration::surface()`는 짧은 변 600 미만으로 `compact`를 정한다. `menu::phone()`은 그 값을 사용한다. 따라서 창 크기만으로 기기 원본을 고르는 현재 연결은 A04의 기기 종류/창 조건 분리 검사가 필요하다.
- `tools/prepare_phone_menu_assets.py`는 승인 원본 SHA와 준비 자원 바이트를 검증한다. 실제 Frame이 어느 자원을 그렸는지, 기기별 화면이 요구를 충족하는지까지 판정하지 않는다.
- `tools/test_apple_parallel.py`는 같은 빌드의 두 시뮬레이터를 함께 실행한다. 성공 종료만으로 검은 여백·그림 선택·버튼 접근성 합격을 판단할 수 없다.
- 철회한 메뉴는 큰 검은 영역을 원본 패널로 채운 상태였다. 숫자 검사 통과와 시각 합격을 혼동했다. 이 상태를 반드시 거부하는 실패 예시를 하네스에 넣는다.

## 1. 관련 영역을 자동으로 찾는 방법

새 진입점은 HeavyMach2 안의 `.agents/harness/cli.mjs`로 계획한다. 공유 허브나 다른 두 게임 저장소는 수정하지 않는다. 하네스의 변경 경로·규칙 매핑은 정본 ID를 참조한다.

| 변경 범위 | 반드시 포함할 검사 |
| --- | --- |
| `Sources/Core/UI/**`, `Presentation/DisplayLayout*`, `MenuArtwork*`, `MenuGridLayout*`, `HUDLayout*` | 전체 화면/레터박스·비례·스크롤·실제 버튼/그리드·HUD·기기별 그림 |
| `MapPreview*`, `CameraPresentation*`, 월드/입력/Scene·Session의 표시 소비 | 전장 전체 출력·줌·맵/포털·입력 역변환·iPad 회귀와 관련 UI |
| `Sources/Assets/**`, `PreparedTiles*`, `SharedAssetPreparation*`, 자원 reader/exporter·준비 스크립트 | 출처/형식/바이트·조립·실제 소비·캐시/준비·패키지 |
| 플랫폼 renderer/runtime·기기 표시 메타데이터·Xcode 자원/빌드 설정 | 논리/실제 drawable·배율·기기 선택·최종 번들·GPU 캡처 |
| 위 검사의 테스트·정본·하네스·훅 | 검사 약화/누락·실패 예시 탐지·발동 경로 자체의 검사 |

이름 변경·삭제·새 파일과 간접 소비도 포함한다. 분류하지 못한 Core/자원/renderer 변경은 검사 없음으로 통과시키지 않고 넓은 관련 범위로 분류한다. 코드 주석에 화면 이름을 적는 방식으로만 탐지하지 않는다.

## 2. 자동 발동과 차단 지점

파일 감시는 이 저장소만 대상으로 하는 로컬 프로세스로 계획한다. 로그인 시 시작하고 종료 시 다시 시작하도록 사용자 영역의 `launchd`에 연결한다. HTTP 포트나 네트워크 서버는 만들지 않는다. 기존 Node의 파일 감시를 사용하고, 이벤트가 합쳐지거나 빠질 가능성에 대비해 시작 시와 각 gate에서 실제 파일 해시·Git 변경 목록을 다시 대조한다. `.local/evidence`, 빌드 출력, `.git`은 감시에서 제외하고 실제 준비 자원 `.local/prepared/HD`는 포함한다. 원본 IPA가 있는 개인 폴더 전체를 감시하지 않는다.

감시 프로세스가 없거나 죽었으면 로컬 작업 진입점·Git/빌드 gate가 이를 감지해 다시 시작하고 전체 관련 범위를 스캔한다. 단순히 프로세스 PID가 있다는 이유로 검사 완료로 보지 않는다. 이 자동 시작·복구도 구현 후 고장 검사 대상이다. 현재는 설치하거나 실행하지 않았다.

| 시점 | 로컬 연결 | 실행/차단 동작 |
| --- | --- | --- |
| 요청 수신·첫 보호 도구 실행 전 | 에이전트 `UserPromptSubmit`·`PreToolUse` | 위 설계 정정의 규칙 주입·시작 기록·실제 경로 분류를 실행하고 기록 없는 수정을 거부한다. |
| checkout/merge 직후 | 기존 post-checkout/post-merge와 `preflight` | 기저/범위·훅·정본 해시를 다시 확인한다. 에이전트 작업 시작 훅을 대신하지 않는다. 기존 Git LFS 훅을 보존한다. |
| 관련 파일 저장 | 기본 Node 파일 감시와 변경 해시 비교 | 정적 검사·기기별 자원 대응·금지된 변경을 자동 확인하고 영향 범위를 기록한다. 이전 성공을 즉시 만료시킨다. 매 저장마다 시뮬레이터/포팅판을 실행하지 않는다. |
| 검사용 빌드 직전 | Xcode 공통 pre-build action과 CMake 검사 대상 | 변경 감지·형식·출처·원본 경계·검사 목록을 확인한다. 잘못된 그림·빠진 명세 등 빠르게 확인 가능한 위반은 빌드 전에 실패시킨다. |
| 전체 구현 후 최종 검사 | `verify` 명령 | 같은 후보를 재사용해 CPU·동시 치트·양쪽 Native/GPU·실제 버튼·자원·패키지를 한 묶음으로 검사하고 결과를 남긴다. |
| 커밋 직전 | 기존 pre-commit에 `gate --staged` 추가 | 작업 폴더와 stage의 차이를 구분한다. 관련 변경의 실제 검사 근거가 없거나 현재 stage와 다르면 성공 커밋으로 넘기지 않는다. |
| 푸시 직전 | 기존 pre-push에 `gate --range` 추가 | 푸시할 커밋/트리와 근거를 다시 대응한다. 소스·규칙·자원·기기 행렬이 다르면 과거 PASS 재사용을 거부한다. |
| 정식 패키징·설치·보고 게시 직전 | 공통 로컬 `release/install/report` 진입점 | 정확한 산출물 SHA/UUID·전체 필수 검사·실제 캡처의 합격을 확인한다. 누락/실패면 정식 설치와 완료 게시를 중단한다. |

검사용 후보를 만드는 단계와 검증이 끝난 정식 산출물을 설치하는 단계를 분리한다. 아직 빌드되지 않아 GPU 검사를 못 했다는 이유로 검사용 빌드까지 영원히 막는 순환 의존성을 만들지 않는다. 검사용 후보는 미검증 위치에 두며 정식 설치본으로 표시하지 않는다.

기본 흐름에서 `SKIP_*`, 빈 성공 파일, 오래된 로그, 말로 한 “확인했다”를 근거로 받지 않는다. 사용자가 직접 지시한 미완료 작업 보존 커밋은 `PENDING` 상태를 명시하며 완료/병합/정식 설치 자격을 주지 않는다. AI가 임의로 이 예외를 선언해 통과시키지 않는다.

Git 훅은 로컬 명령에 연결되는 장치이며 Git 자체가 우회 옵션을 제공한다. 그러므로 “어떤 명령을 고의로 실행해도 OS 보안 장벽처럼 막는다”고 주장하지 않는다. 이 계획의 필수 사항은 정상 작업·빌드·커밋·푸시·정식 설치 경로에 자동 발동을 붙이고, 훅 설정 누락도 검출하며, 실행 기록 없는 완료 보고를 막는 것이다. [Git 훅 공식 설명](https://git-scm.com/docs/githooks)을 따른다. 별도 서버 구성은 이번 범위에 넣지 않는다.

## 3. 레터박스·늘림 검사

### 검사 절차

1. 현재 소스의 실제 `Screens/GameSession/Frame`과 기존 renderer를 사용한다. 정적 목업만 검사하지 않는다.
2. 화면 크기·방향·safe area·논리 Frame·drawable 픽셀 크기·contentsScale·실행파일 UUID를 함께 기록한다. 1배 캡처와 실제 고해상도 출력을 구분한다.
3. 화면 전체를 대상으로 배경 그림의 사각형·클립·UV·원본 픽셀 대응과 기능 UI 영역을 수집한다. “불투명 quad가 덮었다”만으로 전체 화면 표시를 인정하지 않는다.
4. 실제 PNG에서 고정된 검은 띠/면 후보를 찾고 원작 그림의 검은 부분·전환 연출·그림자와 구분한다. 원본 그림 출처와 대응 좌표가 없는 검은 면을 정상 그림으로 판정하지 않는다.
5. 검은 패널을 여백 채움으로 쓰는 실패 예시를 별도로 거부한다. 이름을 `panel`로 바꾸거나 몇 개 문구/버튼을 얹어도 예외로 만들지 않는다.
6. 허브6곳과 사령부/상점의 진입·선택·상세·확인/취소·페이지 상태를 전부 수집한다. 전장의 대기·이동·경로·락온/해제·공격·줌·맵 경계도 영향을 받은 경우 포함한다.
7. 배경 변환·입력·원래 데이터의 전후 값을 비교한다. 검사에서 버튼을 먼저 reveal하거나 맵/포털을 옮겨 합격 조건을 만들지 않는다.

### 성공과 실패

| 항목 | 성공 | 실패 |
| --- | --- | --- |
| 출력 영역 | 선언한 실제 화면 전부에 정상 콘텐츠가 그려짐 | 비율/safe area 때문에 상하/좌우 빈 띠·면이 남음 |
| 원본 검은색 | 실제 사용한 원작 그림/UV에서 같은 검은 부분이 대응됨 | clear 색·추가 패널·빈 슬롯 외곽을 그림이라고 주장함 |
| 패널 | 원작/현행 요구에 맞는 기능 영역과 배치가 증명됨 | 남는 공간을 검은 패널로 덮은 철회 예시와 같은 상태 |
| 비례 | X/Y가 같은 비율이며 원본 픽셀/UV 대응 유지 | 비등방 스케일·끝 픽셀 연장·중복 배경 |
| 허브/사령부/상점 | 삽화 전체·모든 필수 버튼에 세로 이동 없이 접근 | cover로 자르고 스크롤, contain 뒤 검은 여백, 누락/가림 |
| 실제 판정 | 원본 PNG·기하·자원·입력을 함께 확인 | CPU PASS, HTTP200, screenshot 존재만으로 시각 합격 |

검출기의 밝기·색차 허용치는 실제 원작 그림과 실패 예시로 결정해 고정해야 한다. 임의의 검은 픽셀 비율 하나로 판정하지 않는다. 숫자 기준을 아직 검증하지 않았으면 `UNVERIFIED`이며 합격으로 기록하지 않는다. 경계 커버리지는 native 픽셀 중심의 포함 여부로 검사하고, 허용치는 기록된 rasterization 오차에만 한정한다. 넓은 검은 여백을 “오차”로 허용하지 않는다.

필수 결과값은 `unmapped_canvas_pixels=0`, `filler_panel_pixels=0`, `nonuniform_scale_violations=0`, `edge_replication_commands=0`, `required_content_clipping=0`, `required_button_failures=0`, `asset_source_mismatches=0`으로 계획한다. 각 픽셀이 원작 그림 또는 요구된 실제 기능 UI의 어느 부분에 대응하는지 설명되지 않으면 빈 화면으로 취급한다. 원본 패널 파일을 사용했다는 사실만으로 여백 채움을 승인하지 않는다. 내용·입력으로 정한 기능 영역 밖의 검은 면은 filler로 분류한다. 성공 영역 마스크를 넓혀 철회된 검은 면을 새로 허용하는 변경은 검사 약화로 검출해야 한다. 이 결과값을 실제로 산출하는 관측기와 검출기는 아직 구현 전이다.

### 반드시 거부할 실패 예시 — 전수 검사 범위와 별개

- 철회한 Phone 허브의 검은 좌우 영역.
- 철회한 Phone 사령부의 검은 좌우/하단 패널과 원본 그림 축소 배치.
- 철회한 Phone 상점의 검은 여백·추가 슬롯 배치.
- 지형의 검은 대각선이 논리 해상도에서는 안 보이고 Retina 출력에서만 생기는 상태.
- 원본 그림의 실제 검은 부분을 레터박스로 오판하는 검사기 자체의 오류.

철회 예시는 `.local/evidence/experimental-hud-implementation-20261114/`의 원본 캡처와 롤백 보존 문서에서 가져온다. 테스트가 필요하다고 제품 코드를 과거 실패로 되돌리지 않는다. 실패 예시를 의도대로 거부하고 정상 원작 그림을 허용하는 검출기 검사부터 통과해야 한다.

## 4. iPhone/iPad 에셋 검사

### 검사 절차

1. 정본의 화면별 기기 대응표를 로컬 출처 명세와 연결한다. 기기 종류는 창 크기·방향과 별도로 입력한다. 이 연결은 공통 C++ 표시 정책이 소유한다.
2. 원본 IPA/자원은 로컬 읽기 전용으로 해시를 확인한다. 준비 자원의 실제 인코딩·픽셀 크기·Retina wrapper·출처 SHA를 검사한다.
3. 실제 runtime 자원 읽기와 준비·Frame의 texture identity를 관측해 어떤 그림을 썼는지 남긴다. 파일 경로 문자열만 검사하지 않는다.
4. 허브 배경·선택 강조·시설/길 버튼이 같은 판본/장면 변환을 소비하는지 검사한다. 사령부/상점의 목록·상세·입력·실제 동작도 연결한다.
5. 최종 정식·치트 패키지의 파일과 runtime에서 사용한 자원을 대조한다. 예열 뒤 draw/drag에서 자원 읽기·디코드·업로드가 불필요하게 늘지 않는지 확인한다.

| 조건 | 성공 | 실패 |
| --- | --- | --- |
| iPhone 허브/사령부/상점 | Phone 원본 명세·실제 바이트·Frame 소비가 모두 일치 | HD 그림/위조 경로/임의 fallback |
| iPad 같은 화면 | iPad/HD 원본과 실제 소비 일치 | 좁은 iPad 창·방향 변경 때문에 Phone 그림 사용 |
| 공통 전장/유닛/HUD/아이템 | 두 기기에서 같은 HD 게임 자원과 reader/조립 경로 | Phone 전용 게임 데이터·임의 C++ 조립·게임 규칙 분기 |
| 제목/스테이지 로딩 | 양쪽 모두 HD 그림·최상단 정렬 | 일반판 배경으로 단순 일괄 치환 |
| UI와 게임 수량 | HD 24상품/25인벤 등 원래 기능 유지 | 배경의 칸수에 맞추려고 데이터/기능을 줄임 |
| 실제 파일 | 원본 해시·준비 해시·번들·실제 텍스처 일치 | 확장자/이름만 맞고 내용이 다른 그림 |

## 5. 검사 행렬과 실행 순서

- 먼저 정적 검사, 출처/형식 검사, C++ Frame/입력/데이터/회귀 검사로 전체 구현을 진행한다.
- 전체 구현과 동시 치트 구성이 갖춰진 뒤 같은 후보 빌드를 재사용해 양쪽 시뮬레이터의 최종 묶음을 실행한다. 원작 포팅판을 기능마다 번갈아 실행하지 않는다.
- iPhone 가로 표본은 667×375, 852×393, 912×420을 포함한다. 이것은 화면 형상 표본이며 특정 실기기 전체 검증을 뜻하지 않는다. 실제 native 대표 대상과 drawable 배율도 기록한다.
- iPad 세로는 768×1024와 1024×1366 표본을 포함한다. 좁은 iPad 창·안전영역·방향 메타데이터의 자원 선택은 별도 공통 CPU 검사로 확인한다. 미지원 방향을 실행 완료라고 쓰지 않는다.
- 각 프로필에서 정상 장면의 실제 버튼 중심을 누른다. 구매/판매·돈/인벤, 수락/완수/보상, HUD 수치·마커·선택·이동·저장/재시작과 기존 iPad 상태/저장을 비교한다.
- 여러 경험치·진척도·아이템·목표 조건의 독립 Session을 같은 프레임에서 실행한다. 원작에서 동시에 열 수 없는 메뉴를 한 Session에서 강제로 겹치지 않는다.
- 실패를 수정하면 영향받은 관련 검사와 캡처를 다시 실행한다. 수정 없이 같은 성공 숫자를 반복 수집하거나 실패 로그를 지우지 않는다.
- 실제 기기 발열/메모리/OS 복귀는 사용자 허용 범위의 후속 검사다. Simulator 결과로 실기기 해결을 대신하지 않는다.

## 6. 결과 기록과 완료 판정

실행 근거에는 최소한 다음을 넣는다.

- 검사 실행 ID·시작/종료·명령·실제 return code와 로그.
- 현재 코드/검사/정본/훅 내용 해시, stage 또는 후보의 트리 해시. HEAD 이름만 같다고 통과시키지 않는다.
- 준비 자원/원본 출처 명세 해시와 실제 소비한 그림 목록.
- 빌드 설정·실행파일 SHA/UUID, 실제 기기 종류/화면/방향/safe area/drawable 크기.
- 필수 규칙 ID와 시나리오별 결과, 원본 PNG 경로·해시·크기, 실제 버튼/기하/UV/자원 관측.
- 결함·불일치·미실행 사유, 다시 실행해야 할 관련 범위.

결과 상태는 `PASS / FAIL / NOT_RUN / ERROR / STALE`로 나눈다. `NOT_RUN`, `ERROR`, `STALE`은 완료 판정에서 실패로 취급한다. 규칙 하나라도 필수 조건을 만족하지 못하면 전체 완료는 false다. 자동 검사와 시각 판정은 별도 필드이며 둘 다 필요하다. 컴파일 성공·일부 CPU 통과·과거 iPad 기록을 전체 합격으로 끌어올리지 않는다.

보고서 생성기는 이 기록에서 실제 검사한 항목만 쓴다. 결과물·규칙별 상태표·원본 캡처를 함께 제공한다. 근거를 다시 읽지 않고 “문제없음/완료”를 적는 수동 결론을 통과 근거로 받지 않는다. 의도나 말투를 판정하는 장치라고 부르지 않으며, 지시가 결과에서 빠졌을 때 성공 처리할 수 없게 만드는 검사다.

## 7. 하네스 자체의 필수 검사

| 고장/우회 입력 | 하네스가 보여야 할 결과 |
| --- | --- |
| 관련 파일 변경 후 예전 PASS 제시 | STALE·현재 stage/후보/산출물 차이를 표시하고 차단 |
| 미실행·빈 결과·캡처 없음·검사 프로세스 오류 | NOT_RUN/ERROR·차단 |
| `PhoneMenu/`에 HD 그림을 넣고 파일명만 맞춤 | 출처/바이트 불일치 FAIL |
| iPad 프로필에서 창 폭만 줄임 | HD 그림 유지. Phone 전환이면 FAIL |
| 검은 패널에 버튼 몇 개를 추가해 빈 여백을 가림 | 레터박스 금지 FAIL |
| 원본 그림 속 검은색/그림자 | 대응 출처/좌표로 구분해 잘못 거부하지 않음 |
| 배경만 정상, 버튼은 화면 밖/자동 reveal 후에만 입력 | 실제 표시/직접 입력 FAIL |
| 검사 기준·검사 목록·훅 자체를 같은 변경에서 약화 | 정책 변경으로 분류하고 예전 성공을 만료. 무관 변경으로 제외하지 않음 |
| 파일 이름 변경·코드 이동·새 자원 추가 | 영향 범위를 다시 계산. 검사 누락으로 통과하지 않음 |
| stage와 작업 폴더 또는 검사용/정식 바이너리가 다름 | 실제 대상 불일치 FAIL |
| 커밋·푸시·정식 설치 경로에서 훅을 호출하지 않음 | 경로 연결 검사 FAIL. 강제 완료로 보고하지 않음 |
| 감시 프로세스 종료·로그인 재시작·이벤트 누락 | 로컬 자동 시작/복구·전체 변경 재스캔. 검사하지 않은 변경은 과거 PASS 유지 금지 |

## 8. 구현 순서와 완료 조건

1. 정본 ID·기기/화면 자원 대응표·영향 경로와 실패 예시를 고정한다.
2. 현재 런타임의 에이전트 훅 로딩·신뢰·실제 경로 지원부터 임시 fixture로 확인한다. 요청/도구 전후 훅과 제한된 수정 실행기, 로컬 `preflight/verify/gate`·파일 변경 감지·기록 해시/만료 처리를 만든다.
3. 실제 Frame/자원 관측과 C++ 검사, 원본 PNG 기반 시각 검출기를 만든다. 실패 예시가 실제로 실패하는지 먼저 확인한다.
4. 같은 후보의 동시 치트·두 Native 대상·패키지·실제 입력 결과를 한 실행 기록에 연결한다.
5. 기존 LFS/IPA/gitleaks/브랜치 검사를 보존하며 Git 훅·빌드 전·정식 설치/보고 경로에 연결한다.
6. 위 고장 입력을 실제로 주입해 자동 발동·차단을 검증한다. 그 뒤에만 “하네스 강제 실행 구현 완료”라고 보고한다.

현재는 계획·정본 작성 단계다. 게임 구현 재개, 훅 활성화, 검사 합격, 정식 앱 설치나 develop/main 병합으로 보고하지 않는다.
