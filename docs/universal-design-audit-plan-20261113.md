# 일반판·HD판 전수 비교와 유니버설 설계 기준

## 이번 요청과 현재 범위

사용자는 실제 iPad 플레이에서 크래시, 보행 애니메이션 이상, 무기 오작동, BOT가 죽지 않는 현상을 발견하지 않았다고 밝혔다. 이 관측을 현재 iPad 플레이의 기준으로 보존하고, iPhone까지 같은 복원 앱에서 지원하기 위한 원본 차이 조사를 진행한다. 모든 지역·조건을 자동 검사한 결과로 바꾸어 쓰지 않는다.

2026-11-13 최신 지시: 일반판 iPhone과 HD iPad의 차이를 전수 조사해 유니버설 설계 계획을 보강한다. iPhone 전용 에셋 묶음이나 별도 게임 소스를 만들지 않는다. HD 자원 한 벌, 공통 reader·파츠 조립, 같은 C++20 게임 코어·UI·그래픽·음향·저장 경로를 사용한다.

이 문서는 조사 범위와 설계 확정 조건이다. 원본 앱의 모든 실행 상태를 확인했거나 유니버설 구현을 완료했다는 보고가 아니다. [패키지 비교](universal-package-differences-20261113.md), [네이티브 로직 비교](standard-hd-logic-differences-20261113.md)의 실제 결과와 함께 읽는다.

## 비교할 판본과 원인 구분

주 비교는 일반판 2.0.1과 HD 1.0.3이다. 둘은 기기용 제품뿐 아니라 버전도 다르다. 일반판 1.0.0·1.1.0·1.3.0과 HD 1.0.0을 통제 비교에 포함한다. 여섯 IPA의 해시는 [원본 명세](source-provenance.json)에 고정한다.

차이는 다음 중 하나로 기록한다.

| 분류 | 판정 근거 |
| --- | --- |
| 동일 | 파일 바이트·정규화한 데이터·함수의 조사 범위가 무엇인지 표시한다. 같은 파일 해시를 게임 전체 동일성으로 확대하지 않는다. |
| 기기 표시 차이 | 화면 크기·방향·투영·배율·HUD·터치 변환의 실제 소비 경로가 확인된 항목. |
| 게임 규칙 차이 | 무기·이동·선택·명중·AI·생성·임무·진행·저장 결과를 바꾸는 차이. |
| 버전 영향 가능 | 같은 계열의 다른 버전에서도 차이가 있거나, 기기 차이로 원인을 분리할 근거가 부족한 항목. |
| 실행기 문제 | 원본 처리와 호환 호스트의 구현·오류를 구분할 근거가 있는 항목. |
| 미확정 | 함수 대응·단위·호출 순서·실행 관측이 부족한 항목. 다음에 확인할 주소·분기·입력을 명시한다. |

원작 소스코드는 확보하지 못했다. 바이너리·심볼·RTTI·Objective-C 정보·호출부·데이터·실행 관측을 근거로 비교한다. 파일 이름·함수 이름·CPU 명령 차이만으로 기능의 유무나 소스 분리를 단정하지 않는다.

## 전수 목록과 닫을 범위

| 조사 범위 | 전수 목록 | 확정에 필요한 근거 |
| --- | --- | --- |
| 패키지 | 모든 비디렉터리 ZIP 항목, 이름·크기·해시·중복 경로 | 여섯 원본의 해시 전후 일치와 미분류 항목 수 |
| 앱 설정 | 모든 plist·기기 family·방향·실행파일·아키텍처·의존 라이브러리 | 실제 설정값과 실행 중 소비 구분 |
| 그림 | 모든 PNG/CgBI/JPEG·크기·프레임·색/알파 관련 형식·공통 decoder 준비 픽셀 | 동일/상이/한쪽 전용, 이미지 크기와 게임 크기 구분. 파일 alpha 경계를 조립·충돌 경계로 대체하지 않음 |
| 조립·맵 | 모든 MCB 청크·모델·참조·파츠·접합점·게이트·스포너 | reader와 런타임 소비, 원본 바이트 보존 |
| 테이블·콘텐츠 | 모든 TBLE/TBL·필드·행·ID·주석·한국어/영어 대응 | 전수 파싱 결과와 실제 유효/비활성 행의 소비 |
| 코드 | 분석기가 식별한 두 실행파일의 함수 몸체·외부 함수·thunk·클래스/타입과 메타데이터에서 추가 발견한 진입점 | 전체 인덱스, 확정 대응/후보/미대응을 별도 집계. 식별 목록을 원본의 모든 함수가 증명된 목록으로 표현하지 않음 |
| 화면·카메라 | 초기화·투영·시야·배율·추적·흔들림·제한 | 호출부·부동소수 연산·같은 조건의 실행 결과 |
| 입력·UI | 테이블 버튼과 코드 생성 버튼·동적 ID·화면·팝업 | 그림 위치, 실제 hit 영역, 입력 우선순위·해제·취소 |
| 전투·활성화 | 선택·사거리·탄환/직접/범위 피해·AI·BOT·재생성 | 화면 안/가장자리/밖, 갱신 순서와 결과 |
| 임무·성장 | 모든 임무·수락·생성·달성·보고·보상·해금 | 원본 데이터→실제 상태 변화→저장 |
| 시간·난수·저장 | 시간 자료형·틱·RNG 소유권/호출·저장 형식/시점 | 같은 시작 상태의 사건 순서·파일 결과·실패 복구 |
| 음향 | 모든 음원·형식·ID·재생/중첩/중단·BGM | API와 실제 소비 순서, 장치/캐시 수명·출력 관측 |
| 시스템·비용 | 앱 수명·OS 입력·외부 서비스·메모리·프레임 | 원작 기능과 현대 호스트 연결을 분리한 관측 |

함수 주소 전체를 목록에 넣은 사실과 모든 함수의 의미를 대조한 사실을 구분한다. 모든 항목을 위 표의 범위에 배정하고 누락·미해석·미대응 수를 남긴다. 유니버설 설계에 영향을 주는 미확정 항목은 구현 전에 닫는다. 유한한 검사로 가능한 모든 상태 조합을 증명했다고 쓰지 않는다.

## 기존 근거의 재사용과 추가 조사

- [여섯 판본 조사](ipa-version-audit.md), [기존 패키지 비교](evidence/standard-hd-package-metadata.json), [표시 표본 측정](reference-display-measurement-results-20261110.md), [첫 실행 대조](reference-comparison-results-20261110.md)를 재사용한다.
- HD의 전체 함수 어셈블리·의사 코드, 일반판의 기존 REA snapshot, 원본 해시가 맞는 분석을 우선 읽는다. 디컴파일 결과를 원본 소스라고 부르지 않는다.
- 일반판은 C++ RTTI와 주소 기반 함수, HD는 Objective-C 메서드가 남아 있다. 이름이 다르거나 없어도 실제 함수·필드·호출 관계로 대응한다.
- 버전 통제 비교는 차이의 가능한 원인을 좁힌다. 같은 버전의 두 제품 소스가 없으므로 원작자의 개발 의도를 확정한 것으로 쓰지 않는다.
- 새 확인이 필요한 실행은 정적 목록을 모은 뒤 시나리오 묶음으로 수행한다. 일반판은 자기 iPhone 포팅판, HD는 자기 iPad 포팅판을 사용한다. HD를 iPhone에 띄워 일반판 표시 기준으로 사용하지 않는다.
- 원본 IPA·실행파일·전체 디컴파일·전체 복호 테이블·사용자 저장은 외부 서비스에 전송하지 않는다. 문서에는 필요한 수치·ID·필드·주소·해시와 미확인 범위만 남긴다.

## 유니버설 설계를 막는 핵심 질문

1. **일반판 카메라 배율:** 표적과 이동 경로에 따라 배율이 바뀌는지, 어떤 변수·단위·프레임에서 갱신되는지 확인한다. 과거 표본의 메크 크기를 고정 phone 배율로 쓰지 않는다.
2. **HD의 표시와 전투 연결:** `isInScreen`·현재 카메라 overlap·갱신된 캐시를 구분한다. 탄환·직접 피해·범위 피해·BOT·지상/항공 AI·선택 해제·재생성의 예외를 모두 나눈다.
3. **화면 확대에 따른 규칙 변화:** 시야를 넓히면 활성화·충돌·재생성·난수 소비가 달라지는지 확인한다. 같은 코어라는 이유만으로 다른 시야의 전투 결과가 모두 같다고 주장하지 않는다.
4. **HD 합성 화면의 가로 배치:** 도움말·상점·슬롯·전환 그림에는 서로 다른 원본 크기가 있다. 같은 HD 그림을 사용하면서 가독성·잘림·입력 영역을 만족할 표시 방법을 정한다. iPhone 전용 이미지를 만들거나 잘라 별도 파일로 저장하지 않는다.
5. **게임 수식과 표시 수식:** 레이더의 월드 좌표 변환, 스폰 거리, 카메라 여유, 문 전환 phase/tick·저장/음향 사건을 화면 폭·높이로 일괄 치환하지 않는다.

일반판의 카메라 배율과 HD의 카메라 처리가 다르다는 발견은, 원작 일반판의 모든 장면을 고정 축소율 하나로 맞출 수 없음을 뜻한다. 일반판 자동 줌을 iPhone 전용 게임 로직으로 복사하지 않는다. 현재 채택 기준은 HD 게임 규칙과 공통 코어다. 원작 일반판과 똑같은 줌 동작까지 추가로 재현할 필요가 생기면, 공통 카메라 기능의 확장으로 별도 설계하고 HD 기준 유지와 달라지는 동작을 명시한다.

시야 설계 후보는 다음 기준으로 비교한다.

| 후보 | 확인할 문제 |
| --- | --- |
| 기존 HD 세로 화면 전체를 등비 fit | 입력 진단에는 쓸 수 있으나, iPhone 가로의 전장·HUD 최종 구성을 충족하는지 별도 판단한다. |
| 기기 화면에 맞춰 원본 분기별 카메라·활성화 관계를 보존하는 공통 규칙으로 계산 | 보이는 적의 조작 가능성, 달라지는 활성화·피해·재생성 시점을 기록한다. 공격·actor마다 확인한 예외를 유지하며, 모든 대상에 새 공통 `inScreen` 조건을 씌우지 않는다. iPad 기준 구성은 현재 동작을 유지해야 한다. |
| 표시만 넓히고 전투 범위를 기존 HD에 고정 | 새로 보이는 적을 선택·명중할 수 없는 구간이 생기는지 검사한다. 그 문제가 남는 구성을 채택하지 않는다. |

## 공통 코드·자원 경계

| 영역 | 유지할 것 | 보강할 연결 |
| --- | --- | --- |
| 자원 | 동일한 HD 명세·파일·reader·파츠 조립 | 원본 그림의 표현 방식만 공통 출력에서 계산 |
| 게임 | 같은 월드 데이터·무기·임무·시간·난수·저장 형식 | 조사로 확정한 공통 카메라/활성화 계약 |
| 호스트 | 같은 Objective-C++ Apple 호스트 | bounds·pixel scale·safeAreaInsets·방향을 공통 코어에 전달 |
| 화면 | 같은 C++ GPU UI·버튼·도움말·전환 | 유효 영역·월드 배율·HUD/패널 anchor와 변환을 한곳에서 계산 |
| 입력 | overlay→UI→world의 기존 순서 | 표시와 같은 변환의 역변환, 퀵아이템까지 일관 적용 |
| 치트 | 같은 Session·Screens·렌더·음향 | 각 시나리오 자체에 실제 화면 구성을 적용하고 같은 구간에 실행 |

현재 월드 프레임은 이미 카메라 viewport 크기를 받아 출력할 수 있다. 병목은 HD 기본값과 고정 UI 배치를 바꿀 공통 화면 구성 입력이 없다는 점이다. 여러 HD 시나리오를 작은 칸에 모아 그린 치트 화면의 폭만 바꾸는 것을 실제 iPhone 배치 검사로 취급하지 않는다.

## 실행·설계 확정 순서

1. 현재 iPad 정식판의 소스·자원·저장·표시·입력·치트 검사 기준을 보존한다.
2. 위 전수 목록과 차이 대장을 작성하고, 화면·입력·카메라·전투 결합의 필수 미확정을 해소한다. 필요한 원작 실행은 조건을 묶어 수행한다.
3. 같은 HD 에셋과 공통 코어를 사용하는 화면 구성 계약을 확정한다. 최초 목표는 iPhone 가로·iPad 세로다. 전체 임무·캠페인 검사는 별도 남은 범위로 유지한다.
4. 공통 화면 구성·출력·입력 연결을 구현한다. 게임 기능 하나마다 포팅판으로 왕복하는 절차는 반복하지 않는다.
5. 시나리오별 실제 iPhone/iPad 구성을 넣은 동시 치트와 iPad 회귀를 수행한다. 작은/큰 iPhone·좌우 가로·안전 영역·전체 메뉴와 화면 경계를 검사한다.
6. 시뮬레이터의 정상 플레이·저장·음향·입력 검사를 통과한 뒤 실제 기기에 설치해 확인한다. 저장을 백업하고 같은 앱 ID로 갱신한다.
7. 마지막 일괄 대조에서 원본·정식판·치트판의 상태·자원·음향·진행·저장을 확인한다. 추가 방향과 Android·웹/PWA·Mac·Tauri는 후속 단계다.

이번 조사는 게임 코드·기존 사용자 원고·원본 IPA를 변경하지 않는다. 조사 완료, 설계 확정, 구현 완료, 시뮬레이터 확인, 실기기 설치와 배포를 각각 보고한다.
