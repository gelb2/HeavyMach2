# iPad·iPhone 월드와 HUD 규칙 비교

두 설치본 모두 월드를 그린 뒤 HUD를 덮는다. iPad의 월드 출력에서 HUD 높이를 뺀 별도 전장 창을 만드는 구조는 확인되지 않았다. 하단 포털의 차이는 카메라가 허용하는 하단 여유와 월드 이동 입력 하한에서 확인했다.

**현재 iPhone에서 HUD 분리·이동 기능을 제거하는 결정은 보류한다.** 이 기능을 제거해도 고정된 하단 이동 입력 제한이 남는다. 먼저 실제 HUD의 표시/입력 영역과 월드 이동 입력 제한의 관계를 고쳐야 한다. 이번 작업에서는 조사 도구와 기록만 추가했다. 게임·포털·뷰포트·에셋을 수정하거나 새 앱을 설치하지 않았다.

iPhone HUD를 위로 옮기거나 기능 자체를 제거해도 현재CombatScene의 하단 75 제한은 그 움직임을 따라가지 않는다. CameraPresentation의 Player 보호도 사용자가 옮긴 HUD 대신 기본 HUD 경계를 사용한다. 따라서 HUD 그림·버튼 위치와 월드 입력/Player 보호 기준이 완전히 한 규칙으로 묶여 있지 않다.

현재 공통 코드의 iPad 표본도 월드를 안전 영역 전체1024×1322에 그리고 HUD를 그 위에 덮는다. HUD 높이를 뺀 전장 창이 아니다. 하단 여유94를 유지한다. 이 새 구성과 실제11/12 iPad 설치본은 구분한다. 앞선120/92조건 보존 검사의 기준도 카메라 수정 전 공통 코드bfde129이며, 실제11/12 설치본의 모든 표시 크기가 같다는 증거로 확대하지 않는다.

## 원본 HUD와 동적 크기의 의미

기존REA출력의HD GuiGame::init0x29c9c와Phone0x2e480의pseudo/assembly4파일을 다시 읽고 해시를 확인했다. 원본은 각 판본의 부모·자식 위치와 버튼 bound를 명시해 HUD를 만든다. Phone과HD의 구조·무기 버튼 크기는 서로 다르다. 이 근거를 현재 복원판의 화면별0.75배/편집 기능을 원작 기능이라고 부르는 데 사용하지 않는다.

원작 게이지 값에 따른 폭 변화, 슬라이드·눌림 애니메이션, 전체 게임 프레임의 균일 확대와 HUD전체/입력영역의 반응형 확대는 구분한다. 이번에 재확인한 원본 생성 경로만으로 모든 런타임 노드가 동적으로 늘어나는지 전수 판정하지 않는다. 원본 동적 HUD 재조사 TODO는 남긴다.

## 판단과 다음 수정 기준

1. HUD 분리·이동 제거는 보류한다. 해당 기능을 빼도 하단 고정 이동 입력 제한은 남는다. 현재 문제를 그 기능의 존재 때문이라고 판단할 근거가 없다.
2. 다음 수정 계획은 실제 HUD 표시·버튼 입력·월드 이동 입력 하한·기존 월드 터치 소유권을 공통 코드에서 함께 정리하는 것이다. 단순히하한을0으로 바꿔 HUD 버튼 뒤로 이동 명령이 새는 구현도 피한다. 이번 조사에서 제품 수정은 하지 않았다.
3. 현재 뷰포트·맵 에셋·포털 위치/좌표는 유지한다. iPad의 94단위 여유를 그대로 iPhone에 복사하면 맵 밖 노출 문제가 다시 생길 수 있으므로 해결책으로 채택하지 않는다.
4. 같은 7포털의 실제 이동·진입, 전체 82포털의 기하/입력 검사, HUD 기본/이동/재실행과 원래 버튼 기능을 수정 후 합격 기준으로 삼는다. iPad 기존 조건도 보존한다.
