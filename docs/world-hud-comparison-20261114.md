# iPad·iPhone 월드와 HUD 규칙 비교

원본 HD1.0.3·iPhone2.0.1과 두 복원 설치본 모두 월드를 그린 뒤 HUD를 덮는다. iPad의 월드 출력에서 HUD 높이를 뺀 별도 전장 창을 만드는 구조는 확인되지 않았다. 하단 포털의 차이는 카메라가 허용하는 하단 여유와 월드 이동 입력 하한에서 확인했다.

**현재 iPhone에서 HUD 분리·이동 기능을 제거하는 결정은 보류한다.** 이 기능을 제거해도 고정된 하단 이동 입력 제한이 남는다. 먼저 실제 HUD의 표시/입력 영역과 월드 이동 입력 제한의 관계를 고쳐야 한다. 이번 작업에서는 조사 도구와 기록만 추가했다. 게임·포털·뷰포트·에셋을 수정하거나 새 앱을 설치하지 않았다.

## 원본 HD와 원본 iPhone 확인

**원본 두 판본도 전체 화면에 월드를 그리고, 그 위에 하단 HUD를 겹친다. HUD 높이를 제외한 별도 월드 뷰포트를 만들지 않는다.** 하단 전체 폭을 차지하는 HUD, 월드 이동 입력 하한, 카메라 하단 여유를 함께 사용한다. 확인한 판본은 **HD1.0.3·일반판 iPhone2.0.1 armv7**이다. 아래 값은 원본 실행파일·어셈블리·자원 바이트의 정적 분석 결과이며, 이번 작업에서 원본 앱을 새로 실행한 결과는 아니다.

HD는 원본 GuiGame::init의 CFString이 실제로 GameUI_BG.png인지 확인하고, 어셈블리의 배치 상수384·128을 원본 Mach-O literal과 대조했다. 일반판은 GameUI_BG/@2x의 PNG 헤더와 Retina reader·그리기 경로, 부모/자식 위치, 카메라 영향 해제를 함께 확인했다. 파일 픽셀 크기와 게임 논리 크기를 구분했다.

HD HUD 하단94행의72,192픽셀 중69,955개는 알파255,2,237개는 부분 투명, 완전 투명 픽셀은0개다. HD 역시 하단94 전체를 완전 불투명한 직사각형이라고 표현하지 않는다.

iPhone의 하단40 여유와 HUD높이64는 서로 다른 값이다. 원본 수식대로면 지형 바깥의 하단40이 HUD 아래에 놓인다. 원본 Retina HUD의 해당80픽셀 행은76,800픽셀 모두 알파255다. 기본 HUD의 해당40행은19,200픽셀 중558픽셀이 알파240..254이고 나머지는255다. 따라서 기본/Retina가 모두 완전 불투명하다고 일반화하지 않는다. 이것은 로컬 PNG 알파 분석이며 실제 원본 실행의 최종 합성 화면 측정은 아니다.

**현재 복원 iPhone의 문제에 그대로 적용할 수 있는 결론은, 카메라 하단 여유와 HUD의 폭·입력 하한을 함께 맞춰야 한다는 것이다.** 원본 HD는 HUD가768폭을 채우고, 원본 iPhone은480폭을 채운다. 현행 복원 iPhone은912폭 중 중앙576폭의 HD HUD를 사용한다. 이 상태에서 HD의94 하강만 복사하면 양옆 빈 영역이 드러난다. 앞선 시뮬레이터 결과와 모순되지 않는다.

이 조사로 월드 뷰포트를 HUD만큼 줄이는 변경을 채택하지 않는다. 원본의 서로 다른 HUD를 확인했다는 이유로 iPhone 인게임 자원이나 게임 코어를 별도로 도입하지도 않는다. 현재 포털 좌표·에셋 크기·검은 여백 금지 조건을 보존한 수정 계획은 여전히 필요하다. 원본 HUD의 모든 동적 갱신과 모든 버전의 런타임 상태를 전수 검증한 결과로 확대하지 않는다.

Phone1,077개 export 본문의 SHA를 확인하고 직접 viewport/scissor/ortho 호출을 검색했다. 선택 경로의 pseudo/assembly38파일도 manifest SHA·Evidence ID와 대조했다.
