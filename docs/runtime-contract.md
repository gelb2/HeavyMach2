# HeavyMach 2 시간·저장·음향·인게임 표시 계약

상태: 2026-11-10 사용자 지시와 [세 작품 스택 대조](technology-stack-review-20261110.md)에 따른 구현 기준이다. 복원 코어·앱에서 통과한 결과가 아니다.

## 공통 실행 구조

HeavyMach 1·MachDefense와 같은 C++20 게임 코어, Objective-C++ Apple 연결, OpenGL 계열 GPU 표시, OpenAL 효과음, NDK Android, Emscripten/WebAssembly 웹/PWA, Tauri2 호스트를 사용한다. Kotlin·JS·Rust는 기존 플랫폼 호스트 역할에 한정한다. Python은 분석·오프라인 자원 준비·검사 도구에 한정한다. 다른 런타임·게임 엔진을 편의상 추가하지 않는다.

원작별 데이터 reader·파츠 조립·게임 규칙·시간·난수·저장·음향 호출을 복원한다. HD의 Objective-C 메시지 구조를 공통 C++로 옮길 때도 확인한 상태 전이와 호출 순서를 보존한다. 원본 소스나 기존 두 게임 전체 소스를 그대로 쓰는 작업이라고 보고하지 않는다.

## 시간과 프레임

- HD `renderScene 0x299c`의 게임 시간 증가·tick·drawVisual·swapBuffers를 출발점으로 삼는다. 시간 자료형·상수와 실제 소비자를 연결하고 HeavyMach 1의1/60 double 상수를 대입하지 않는다.
- 음향 재생, 파일 읽기·쓰기, UIKit 레이아웃, OS 세션 활성화의 완료 대기로 전투 프레임을 막지 않는다. OS 작업 완료가 늦어도 상태·요청 순서를 임의로 뒤집지 않는다.
- 비활성·잠금·오디오 중단·GPU 소실·종료를 구분한다. 앱 복귀 때 지난 시간을 한꺼번에 진행하거나 오래된 입력·소리를 몰아서 재생하지 않는다. HD의 중단 함수와 현대 복귀 어댑터를 각각 대조한다.

## 저장

- 사격·탄약 소비·피격·아이템/EXP 변화는 우선 메모리 상태 변경이다. 해당 사건마다 새 DB·파일 쓰기를 추가하지 않는다. 모든 tick·draw에서 dirty 상태를 저장하는 경로도 만들지 않는다.
- HD `saveDataFile 0x17580`과 실제 호출 지점을 목록으로 만든 뒤 파일 저장 이벤트를 연결한다. 저장 길이28204바이트·바이트 변환·슬롯·미해석 바이트·원자 쓰기를 검증한다. 일반판 저장 길이를 HD에 대입하지 않는다.
- 원작 저장 함수의 난수 호출과 게임 난수의 관계를 확인한다. 암호화 편의나 병렬 처리 때문에 난수 순서를 바꾸지 않는다. 저장 내용을 먼저 해석하지 않고 두 포팅판 저장을 서로 복사하지 않는다.
- 게임 코어의 저장 요청과 플랫폼의 실제 완료를 구분한다. 웹/PWA도 메모리 복사만으로 영구 저장 성공을 반환하지 않는다. 기존 두 작품의 플랫폼 저장 연결을 참고하되 같은 슬롯 수·파일 포맷을 가정하지 않는다.
- 실패·손상·저장 충돌에서 사용자 저장을 초기화하지 않는다. 일반/치트 저장을 분리하고 실제 쓰기 계수·원자 교체·재시도·재실행 복구를 검사한다. DB를 계측 로그 저장소로 사격 경로에 추가하지 않는다.

## 효과음·BGM

- HD `SoundManager`와 하위 OpenAL/AudioQueue 경로를 따른다. 효과음 이름/ID·위치·gain·루프·동시 재생·같은 source 재시작을 소비 코드에 연결한다. HM1의 mono16 제한·거리 상수, MachDefense의 위치 수식을 HM2에 복사하지 않는다.
- 조사한 HD 일반 효과음의 위치 설정→stop→play 순서를 유지한다. MachDefense의 stop→gain/위치→play 구현은 그대로 복사하지 않는다. 공통 스택·객체 수명 재사용과 원작별 재생 순서·루프 분기를 구분해 검사한다.
- 컨텍스트·음원 데이터·source/buffer 준비와 재생을 분리한다. 활성 전투의 반복 사격에서 생성·해제·파일 재읽기·디코드를 반복하지 않는다. 필요 음원은 원작의 준비/캐시 조건을 확인해 예열하고, 예열이 재생 순서나 시간·난수 상태를 바꾸지 않게 한다.
- HD의8/16비트·모노/스테레오·각 샘플레이트를 보존한다. MachDefense의 PCM 형식 처리와 OpenAL 수명 구조를 재사용 기준으로 삼는다. 디코딩하기 편하게 원본을 일괄 변환하지 않는다.
- Apple 효과음을 AVAudioPlayer/AVAudioEngine·시스템 효과음으로 대체하지 않는다. BGM은 HD 원본에서 확인한 AudioFile/AudioQueue 경로를 복원한다. 장치·중단 연결에 쓰는 OS 오디오 세션은 효과음 재생기와 구분한다.
- 활성 전투 중 재사용, 배경 진입 시 정리, 복귀 시 장치 재개를 따로 검사한다. context가 존재하거나 play 호출 수가 증가했다는 사실만으로 출력 성공을 판정하지 않는다. 출력 샘플 진행·실제 소리·지연과 게임 프레임을 확인한다.
- 웹은 기존 Emscripten OpenAL API 연결을 사용한다. 그 아래 WebAudio 출력과 브라우저 활성화 제약을 플랫폼에서 처리하며, 사격마다 AudioContext를 만들거나 닫지 않는다. Android·Tauri에서도 같은 음원 요청 순서·수명 계약을 검증한다.

## 그래픽·버튼·입력

- 메크·파츠·탄환·배경·HUD·인게임 버튼·글꼴은 원작 자원과 공통 GPU 표시 명령으로 그린다. 버튼 상태·입력 판정도 공통 게임 코드에 둔다. UIKit UIButton/UILabel·웹 DOM 버튼·Android View로 인게임 요소를 별도 재개발하지 않는다.
- UIKit/AppKit·Android·브라우저는 창·표면·터치/키보드·안전 영역·OS 텍스트 입력·클립보드 등의 연결을 맡는다. 이름 입력 등 필요한 OS 필드는 허용하되 게임 버튼의 모양·동작을 플랫폼 컨트롤에 넘기지 않는다. 검증 패널도 정식 게임 UI의 대체 구현으로 쓰지 않는다.
- 프레임 중 자원 재읽기·텍스처 재업로드·뷰/컨텍스트 재생성을 반복하지 않는다. 크기/방향/GPU 상태가 변한 때의 재준비는 별도 사건으로 계측한다. HUD·버튼도 월드와 같은 출력에서 프레임 시간을 측정한다.
- 화면 표시와 입력 역변환을 연결한다. HD의 선택 반지름·탄환 boundRect·카메라 표시 여부 조건은 [포팅판 대조 결과](reference-comparison-results-20261110.md)를 따른다.

## 구현별 합격 근거

각 모듈에 원작 함수·데이터 → 새 소비 코드 → 회귀 검사 → 실제 앱 관측을 연결한다. 예열 뒤 연사·피격·전장 이동·HUD 조작에서 실제 저장 쓰기와 음원/텍스처/뷰 생성 계수를 기록한다. 프레임 시간과 음향 지연은 같은 시뮬레이터·기기·장면의 기준값과 비교하고 수치를 측정한 뒤 보고한다. 원본 기준이 없는 지연·프레임 예산을 임의로 합격값으로 만들지 않는다.

동일 코어의 일반/치트 앱을 구분하고, 먼저 iPhone 가로·iPad 세로의 시뮬레이터 검증을 마친다. 그다음 기기 검사와 추가 방향·플랫폼 확장을 진행한다. 빌드 성공·검사 성공·직접 플레이·원작 동등성·배포를 각각 보고한다.
