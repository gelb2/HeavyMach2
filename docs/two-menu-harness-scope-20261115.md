2026-11-15 최신 사용자 지시를 적용한다. 두 하네스는 독립적으로 실행하고 판정한다. 각자 정한 조건을 100% 충족해야 통과한다. 아래 설계와 실제 실행 상태를 구분한다.

- 근거는 `.local/evidence/menu-background-20261115/final/`, `.local/evidence/menu-asset-check/`, `.local/evidence/menu-screen-check/`에 보존했다. 실패를 삭제하거나 기준을 완화하지 않았다.

## 1. 에셋 하네스

### 검사하는 영역

허브 Base001~006·사령부·상점의 배경을 고르는 순간부터 실제 배경 자원을 읽어 화면에 사용하는 경로다. iPhone은 일반판, iPad는 HD판 원본 배경인지 확인한다. 버튼 배치·상품·무기·오디오·게임 규칙 검사는 포함하지 않는다.

읽을 입력은 다음과 같다. 이 목록은 수정 금지나 명령 차단 목록이 아니다.

- `docs/source-provenance.json`: 승인 원본의 위치와 해시.
- `docs/evidence/hub-artwork-census-20261115.json`: 실제 기지별 원본 참조. 배경에 해당하는 자료만 사용한다.
- `.local/prepared/HD/manifest.json`, `.local/prepared/HD/PhoneMenu/manifest.json` 및 해당 배경 파일: 원본과 준비 자원의 대응.
- 검사 후보의 앱 번들 안 해당 배경 파일과 실제 배경 선택·사용 관측: 다른 판본·같은 이름의 다른 바이트를 구분한다.
- 원본 IPA는 해당 파일을 로컬 읽기만 한다. 외부 전송·수정·재패키징은 하지 않는다.

현재 관련 소비 코드는 `Sources/Core/Presentation/MenuArtwork.hpp`, `Sources/Core/UI/Screens.cpp`의 기지·사령부·상점 배경 생성 부분, `Sources/Core/Session/GameSession.cpp`의 기지 배경 참조다. 준비 경로는 `tools/prepare_phone_menu_assets.py`, `tools/prepare_hd_assets.py`다. 이 소비 관계를 변경할 때 에셋 검사를 자동 호출한다. 같은 파일의 무관한 함수 변경까지 전체 저장소 감시로 확대하지 않는다.

### 쓰기·차단·코드량

- 실행 중 수정할 제품 파일: 0개. `Sources/`, `Apple/`, 원본·준비 에셋을 고치지 않는다.
- 출력: `.local/evidence/menu-asset-check/<run-id>/`에 해당 실행의 입력 식별·실제 사용 배경·비교 결과만 생성한다. 과거 실행은 덮어쓰지 않는다.
- 차단할 파일·일반 명령: 0개. 불일치는 이 하네스의 `FAIL`이며 파일 편집·스태시를 금지하는 상태가 아니다.
- 새 검사 스크립트 예상: 40~70줄. 자동 호출 연결은 별도 10~20줄 예상이다. 아직 작성·계수하지 않은 설계 추정이다.
- 실제 사용 배경 관측을 기존 검사에서 제공하지 못하면 작은 검사 연결이 추가로 필요하다. 그 추가분도 새 코드 총량에 포함한다. 이를 제외한 채 전체 구현이 100줄 미만이라고 확정하지 않는다.

## 2. 화면 하네스

### 검사하는 영역

동일한 세 화면의 실제 시뮬레이터 출력에서 검은색으로 빈 곳을 메웠는지, 원본 에셋 밖을 가장자리 픽셀 늘림·반복으로 덮었는지만 검사한다. 기기별 배경의 파일 출처나 에셋 하네스의 결과는 읽지 않는다. 원작 그림 안의 검은색을 땜질로 판정하지 않는다.

입력은 이 하네스가 실행한 후보·기기·기지·화면의 실제 캡처와 원본 그림 비교 자료다. 캡처를 직접 열어 두 금지사항을 판정한다. 캡처 파일 존재나 검은 픽셀 비율 하나로 통과시키지 않는다. 원본 크기·비율·바이트를 유지한다.

관련 소비 경로는 `Sources/Core/UI/Screens.cpp`의 해당 배경 표시, `Sources/Core/Presentation/DisplayLayout.cpp`와 `DisplayLayout.hpp`의 해당 화면 변환이다. 실제 배경 출력에 영향을 주는 공통 렌더 경로 변경도 이 화면 결과를 재확인한다. 렌더러 전체를 상시 감시하거나 전투·HUD 기능 검사를 추가하지 않는다.

### 쓰기·차단·코드량

- 실행 중 수정할 제품 파일: 0개. 배경·뷰포트·지형·HUD를 고쳐 검사에 맞추지 않는다.
- 출력: `.local/evidence/menu-screen-check/<run-id>/`에 캡처·실행 식별·직접 열람 근거·두 금지사항의 판정만 생성한다. 에셋 하네스의 출력은 읽거나 수정하지 않는다.
- 차단할 파일·일반 명령: 0개. 문제 화면은 이 하네스의 `FAIL`이며 수정을 계속할 수 있어야 한다.
- 새 캡처 호출·증거 확인 스크립트 예상: 30~60줄. 자동 호출 연결은 별도 10~20줄 예상이다. 아직 작성·계수하지 않은 설계 추정이다.
- 이 예상은 기존 캡처 도구와 직접 화면 검수를 사용하는 범위다. 모든 시각 패턴을 자동 해석하는 새 이미지 판별 엔진의 코드량이 아니다. 필요한 캡처 시험 추가분도 실제 총량에 포함한다.

## 4. 강제 실행과 독립성

각 하네스는 자기 소비 경로를 작업할 때 요구를 전달하고 관련 검사를 자동 호출한다. 실패·미실행·오류는 각각 그대로 보고한다. 훅 오류·누락 기록·범위 변경을 이유로 파일 작업을 봉쇄하지 않는다. 한 하네스의 실행·결과·고장이 다른 하네스의 실행 조건이 되어서는 안 된다.

통과는 해당 하네스의 모든 적용 항목을 확인하고 충족한 경우뿐이다. 미확인은 미통과다. 미통과 결과를 완료·시각 합격이라고 보고하지 않는다. 현재 요청은 두 작은 검사와 자동 호출의 범위 정의이며 기존 전역 명령 차단기·Git 검사 훅 재설치를 뜻하지 않는다.

## 5. 실제 코드량 보고 기준

구현 후 검사 스크립트·자동 호출 코드·신규 테스트/관측 연결·설정·매핑 데이터를 파일별로 계수한다. 새 함수를 다른 파일로 빼서 100줄 제한을 충족했다고 표시하지 않는다. 기존 재사용 도구의 이름과 변경 유무도 별도로 적는다. 현재 확인으로 각 핵심 스크립트의 소규모 구현은 가능하지만, 자동 호출과 누락된 실행 증거 연결까지 포함한 전체 신규 코드가 각각 100줄 미만이라고 확정할 근거는 아직 없다.

## 6. 실패 후 폴백

폴백은 검사·원인 수정 경로를 전환하는 절차다. 게임의 배경을 자동 대체하거나 제품을 자동 롤백하는 기능이 아니다. 두 하네스에 자동 수정기·명령 차단기를 추가하지 않는다.

| 결과 | 후속 행동 |
| --- | --- |
| 에셋 FAIL | 잘못 사용한 기기·기지·화면, 기대 원본과 실제 파일·해시를 남긴다. 공통 선택·준비·패키지 중 불일치가 시작된 곳만 수정한다. 파일 이름 변경이나 다른 그림 fallback으로 숨기지 않는다. |
| 화면 FAIL | 실제 원본 크기 캡처와 검은 땜질·끝 픽셀 늘림 위치를 남긴다. 해당 배경의 합성·변환 원인을 수정한다. 검은 패널을 다른 색으로 바꾸거나 캡처 편집으로 통과시키지 않는다. |
| 하네스 ERROR/NOT_RUN | 제품 FAIL과 구분한다. 기존 도구로 원본·실제 사용 자원 또는 실제 시뮬레이터 화면을 직접 대조하고 근거를 남긴다. 하네스를 고칠 때까지 자동 실행 검증은 미완료다. 직접 대조 결과를 자동 검사 통과라고 기록하지 않는다. |

각 경우에도 코드 수정·조회·백업·스태시·검사 실행·하네스 제거는 허용한다. 원본·사용자 저장·이전 실패를 보존한다. 알려진 정상 결과는 비교 기준으로만 사용하며 현재 수정 후보의 합격으로 가져오지 않는다.

## 7. 폴백 후 재검증 순서

1. 실패 항목을 고정한다. 에셋 검사는 기대 원본·기기·기지·화면, 화면 검사는 검은 땜질 없음·끝 픽셀 늘림 없음이 기준이다. 수정 도중 통과 기준을 완화하지 않는다.
2. 수정 전에 원인·수정 대상·예상 결과를 짧게 기록한다. 원인이 미확정이면 추정이라고 쓰고 이를 구분할 조사부터 한다. 같은 파일을 다시 저장한 것을 원인 수정으로 취급하지 않는다.
3. 수정 후보의 소스·입력 자원·실행 앱을 식별한다. 이전 후보의 성공 기록·캡처를 새 후보의 결과로 사용하지 않는다.
4. 에셋 하네스는 해당 후보에서 실제 사용한 배경과 원본 대응을 다시 검사한다. 화면 하네스는 해당 후보를 시뮬레이터에서 다시 실행·촬영하고 직접 대조한다. 서로의 결과를 실행 조건으로 삼지 않는다.
5. 실패가 난 사례부터 확인하고, 같은 선택/표시 코드를 사용하는 기기·기지·세 화면으로 확인 범위를 넓힌다. 공통 코드 변경이면 여섯 기지×두 기기×세 화면의 해당 배경 결과를 한 묶음으로 대조한다. 무관한 전투·오디오 전수 검사로 확대하지 않는다.
6. 해당 하네스의 모든 적용 항목이 확인·충족되어야 100% 통과다. 이전 실패와 새 결과를 연결하고, 미확인·ERROR·NOT_RUN은 통과 수에 넣지 않는다.

## 8. 같은 잘못의 반복 방지

- 각 하네스가 자기 결과 폴더에만 실패 항목·실패 형태·입력/후보 식별·원인·수정 대상·재검증 결과를 남긴다. 다른 하네스의 기록이나 공용 전역 잠금을 만들지 않는다.
- 동일 입력·동일 후보·동일 실패를 원인 수정 없이 재실행해 토큰·빌드·캡처만 소비하지 않는다. 새 증거를 수집하기 위한 실행은 조사 목적과 구분할 가설을 명시한다.
- 수정 후보가 달라도 같은 실패 형태가 다시 나오면 같은 해결책을 중단한다. 실패 위치만 바꾸는 수치 조절·검은 패널·끝 픽셀 늘림을 반복하지 않는다. 실제 소비 경로와 첫 불일치 지점을 다시 조사한 뒤 다른 근거 있는 수정안을 정한다.
- 과거 실패를 작은 회귀 사례로 보존한다. 에셋 검사는 잘못된 판본/바이트의 임시 입력을 계속 거부해야 한다. 화면 검사는 보존한 실제 실패 캡처가 여전히 실패로 판정되는지 확인한다. 실제 제품·원본을 실패 상태로 되돌려 시험하지 않는다.
- 화면 판정은 실패 예시를 사람이 직접 대조하는 경우와 자동 검출을 구분한다. 원작 그림 안의 정상 검은 부분을 잘못 거부하는지도 확인한다. 이 범위 때문에 새 범용 이미지 판독기를 만들지 않는다.
- 정상으로 만들기 위해 대응표·검사 항목을 실패 결과에 맞춰 바꾸지 않는다. 사용자 수정이나 실제 원본 근거로 기대값이 바뀌면 변경 이유·이전 기준을 보존하고 관련 결과를 새로 검사한다.
- 재발 시 중단하는 것은 같은 수정 접근이다. 파일 수정·스태시·하네스 복구를 중단시키는 도구 차단으로 구현하지 않는다. 고정 재시도 횟수만으로 필요한 원인 수정 후 재검사를 영구 금지하지 않는다.
- PASS는 이 두 배경 검사 범위에서만 유효하다. 전체 게임 복원·설치·배포 완료로 확대 보고하지 않는다.
