# iPhone 공통 개발 기준·계획·금지사항

이 문서는 사용자가 정한 범위와 이번 조사에서 발견한 구현 제약을 한곳에 보존한다. 시작 위치는 [iPhone 인계](../HANDOVER-IPHONE-UNIVERSAL.md), 사실과 미확정은 [추가 조사](iphone-followup-investigation-20261113.md)에서 읽는다. 아래 인터페이스·검사 계획은 구현 완료 보고가 아니다.

## 유지할 제품 기준

| 구분 | 기준 |
| --- | --- |
| 게임·콘텐츠 | HD판의 게임 규칙·무기·SP·인벤토리·임무·시간·난수·저장을 같은 코어에 둔다. |
| 자원 | 같은 HD 명세·그림·음원·공통 reader·파츠 조립을 두 기기에서 사용한다. |
| 표시 | iPhone은 일반판, iPad는 HD판의 실제 표시 크기·비례·선명도와 대조한다. 원본 좌표 단위·줌 상태를 함께 읽는다. |
| 방향 | 먼저 iPhone 가로·iPad 세로. 이후 두 기기 모두 가로·세로로 확장한다. |
| UI | 같은 C++ GPU 화면·버튼·문구·입력 경로를 사용한다. 한국어를 유지한다. HUD는 우선 하단 중앙 고정 배치 계획을 따른다. |
| 보존 | 현재 iPad 동작·사용자 저장·원본·실패 근거·사용자 문서를 보존한다. |
| 검증 | 정식판·치트판은 같은 게임 코드를 사용한다. 치트는 여러 조건을 같은 프레임에 실행한다. |

일반판과 HD는 버전도 다르다. 발견한 차이를 원작자의 기기별 의도로 단정하지 않는다. 두 원작의 모든 게임 규칙을 동시에 그대로 재현한다고 주장하지 않는다. 일반판 동작을 새로 채택할 필요가 생기면 공통 기능의 명시적 확장으로 따로 기록한다.

## 표시 크기와 좌표 설계

1. 이미지 픽셀 수, HD 월드 단위, UI 배치 단위, 화면 point, drawable pixel을 구분한다. HD 그림의 픽셀 수를 곧바로 오브젝트 크기로 쓰지 않는다.
2. 메크·무장·탄환·이펙트·그림자·이동 마크·지형·게이트는 같은 월드 표시 변환을 사용한다. 파츠별 임의 보정을 추가하지 않는다.
3. HUD·상점·인벤토리·임무창·도움말·팝업은 월드 줌과 별도로 배치한다. 생성 좌표와 이후 갱신 좌표에 같은 구성을 전달한다.
4. 호스트는 실제 bounds·pixel scale·안전 영역·방향을 공통 코어에 전달한다. 구체적인 새 타입 이름과 API는 구현 시 정하며, 아직 코드에 존재한다고 쓰지 않는다.
5. 표시와 입력에 같은 변환과 역변환을 사용한다. OS 입력→공통 화면→overlay/UI→월드의 좌표 소유자를 명시하고, renderer 변환과 카메라 역변환을 중복 적용하지 않는다.
6. 버튼뿐 아니라 도움말·아이템 선택/끌기·퀵아이템·이동 경로·적 선택·공습/수리 좌표까지 연결한다. 입력 우선순위·누름/이동/해제/취소·멀티터치 소유권을 유지한다.
7. 기존28×31·46×53 같은 표본은 보존하되 고정 기기 배율로 쓰지 않는다. 장비·적 ID·방향·애니메이션 프레임·표적/경로·현재/목표 줌을 묶은 원작 장면과 연결한다.
8. 넓어진 화면에서 메크·HUD를 함께 확대하지 않는다. 검증한 표시 크기를 유지하며 전장 시야와 패널 배치를 계산한다. 보이는 적의 선택·명중·AI·재생성이 화면과 어긋나지 않아야 한다.

| 타이틀 대기는 일반판11초·HD10초 | 배치 변경 때문에 일반판 시간값을 섞거나 타이틀 전환·입력 해금 시점을 바꾸지 않는다. |
| 효과음 캐시·source 준비와 일반 재생 경로가 구분됨 | 예열·cache miss와 매 발사 재생을 구분한다. 기존 재생 수명·중첩·중단을 조사하지 않고 다른 프레임워크로 대체하지 않는다. |

## 구현과 검사 순서

1. **조사 마감:** 카메라/투영/역변환, 화면 판정과 전투 결합, 전체 UI 입력 경로, 저장·시간·음향 사건을 근거와 연결한다. 미확정은 정적 추적 가능·원작 실행 필요·제품 채택 결정으로 나눈다.
2. **표시 기준 확정:** 같은 조건의 원작 메크·적·지형·HUD 크기와 카메라 상태를 기록한다. 원작 일반판은 iPhone 구성, HD는 iPad 구성에서 확인한다. 일반판의 알려진 검은 지형 오류를 정상 기준에 포함하지 않는다.
3. **공통 화면 구성 연결:** 호스트→Session/카메라/Screens/도움말/퀵아이템/전환의 소비 경로를 연결한다. iPad 기준에서는 기존 표시·입력 결과를 유지한다. 초기화·화면 변경 시 필요한 자원을 준비하며 매 프레임 다시 읽지 않는다.
4. **공통 iPhone 배치 구현:** 월드 표시, HUD·패널·합성 화면, 표시와 입력의 역변환을 한 묶음으로 구현한다. 원작 코드 분석은 재사용하고 기능 하나마다 포팅판을 열어 왕복하지 않는다.
5. **치트 구성:** 각 독립 Session 자체에 실제 iPhone 가로 또는 iPad 세로 구성을 넣는다. 외부 모음 화면의 폭만 바꾸지 않는다. 실제 화면 좌표의 자동 입력도 같은 배치를 사용한다.
6. **동시 검사:** 이동·조준·발사·피격·BOT·아이템 획득·성장·임무·메뉴·저장 조건을 같은 프레임 구간에 실행한다. 서로 배타적인 화면은 독립 상태로 실행하고 해당 게임 상태의 pause 규칙을 유지한다.
7. **정식판·시뮬레이터 확인:** 한국어 메뉴·보통 진행·장착·임무·저장/재실행·음향과 기기별 표시/입력을 확인한다. 작은/큰 iPhone, 양쪽 가로 방향, 비대칭 안전 영역과 현재 iPad 기준을 포함한다.
8. **최종 일괄 대조·실기기:** 필요한 원작/정식/치트 일괄 대조를 마친다. 시뮬레이터 검사 통과 후 저장을 백업하고 실기기에서 확인한다. 설치·develop/main 병합·릴리스는 각각 결과와 승인 범위를 구분한다.

원작 실행에서만 알 수 있는 항목을 임의 구현으로 채우지 않는다. 해당 항목의 시작 상태·입력·기대 관측·필요한 원작 구성을 먼저 적고 묶어서 확인한다. 모든 캠페인 검사를 iPhone 화면 기반 구현의 선행 조건으로 추가하지 않으며, 기존 미해결 퀘스트 TODO도 삭제하지 않는다.

같은 HD 규칙을 사용해도 표시 범위가 다르면 활성화·명중 후보·재생성·난수 소비가 달라질 수 있다. 기기 간 모든 전투 상태 hash가 무조건 같아야 한다는 기준을 만들지 않는다. 같은 카메라·시작 상태의 회귀와, 확장한 시야에서 원본 분기대로 발생하는 차이를 나눠 기록한다. 기존 전투 영역을 고정해 바깥의 보이는 적을 선택·명중할 수 없게 만드는 방식으로 수치만 맞추지 않는다.

## 하면 안 되는 것

다음은 기존 사용자 지시와 이번 조사에서 확인한 제약이다.

- iPhone 전용 에셋 묶음·별도 게임 코어·유닛별 C++ 정의/조립/그리기 우회를 만들지 않는다.
- 파일 확장자만 바꾸거나 원작 데이터를 임의 JSON·다른 형식으로 위장하지 않는다. 원본·신규 유닛 모두 같은 reader·파츠 조립·애니메이션·공격·패키징을 사용한다.
- 화면에 맞추려고 월드의 충돌 반경·이동 속도·사거리·피해·SP·인벤토리 용량·임무 조건을 기기별로 바꾸지 않는다.
- 모든768/1024/60 같은 수치를 화면 크기로 일괄 치환하지 않는다. 카메라 여유·레이더 월드 변환·스폰 거리·전환 시간에는 서로 다른 의미가 있다.
- HD 세로 화면을 통째로 가로에 넣은 출력만으로 iPhone 배치 완료라고 보고하지 않는다. 원작과 다른 표시 크기·누락·가독성·터치 어긋남을 숨기지 않는다.
- 매 사격·피격·획득·프레임마다 DB/파일을 쓰지 않는다. 예열과 재생을 구분하지 않고 오디오 context/source/buffer를 매번 만들거나 해제하지 않는다.
- 효과음을 AVAudioPlayer/AVAudioEngine으로 임의 대체하지 않는다. 원작 BGM AudioQueue와 OS 장치 연결은 별도로 보존한다.
- UIKit으로 인게임 그래픽·HUD·버튼을 만들지 않는다. 기존 OS 입력·시스템 이름 입력·확인창과 게임 화면을 구분한다.
- Python/Ruby 게임 런타임·Three.js·새 게임 엔진을 추가하지 않는다. 기존 분석용Python, Apple호스트Objective-C++, 후속 플랫폼의 기존 어댑터 역할을 혼동하지 않는다.
