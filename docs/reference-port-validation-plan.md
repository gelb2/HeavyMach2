# HeavyMach 2 일반판·HD판 포팅 앱 검증 계획

상태: 승인된 복원 목표를 위한 추가 계획. 포팅 앱 구현·빌드·기기 설치·플레이는 아직 하지 않았다. 일반판2.0.1과 HD1.0.3을 우선 조사 후보로 두며, 실행 검증 전 최종 기준 판본으로 확정하지 않는다.

## 1. 순서와 비교 대상

HeavyMach 1의 [최초 복구 이력](heavymach1-history-review.md)은 원본 IPA 호환 앱을 먼저 실행하고 이를 새 소스 복원판의 비교 기준으로 보존했다. HeavyMach 2는 iPhone용 일반판과 iPad용 HD판이 별도 출시됐으므로 비교 기준도 두 개를 만든다. 여기서 두 플랫폼은 두 기기용 원작 판본을 뜻하며, OS가 완전히 다른 두 게임 엔진이라는 뜻은 아니다.

원본 일반판 → 일반판 포팅 비교 앱 → 유니버설 복원 앱의 iPhone 구성.

원본 HD판 → HD판 포팅 비교 앱 → 유니버설 복원 앱의 iPad 구성.

일반판 포팅 앱을 iPad에서 확대 실행한 결과를 HD판의 검증으로 대신하지 않는다. HD 에셋을 일반판 코드에 먼저 끼워 넣어 HD 원작이 동작한 것처럼 취급하지 않는다.

## 2. 앱과 저장 공간

아래 이름·bundle ID는 계획값이며 아직 Xcode target이나 서명 프로필을 만든 것은 아니다.

| 앱 | 원본/코드 | 주 검증 기기 | 계획 bundle ID | 역할 |
|---|---|---|---|---|
| HM2 Reference Phone | 일반판 원본 실행파일·자원 + 호환 실행기 | 실제 iPhone | `com.gelb2.heavymach2.reference.phone` | 원작 일반판 동작과 표시 기준 |
| HM2 Reference HD | HD 원본 실행파일·자원 + 호환 실행기 | 실제 iPad | `com.gelb2.heavymach2.reference.hd` | 원작 HD판 동작과 표시 기준 |
| HM2 Restored | 새 공통 코어 + 판본별 검증된 구성 | iPhone·iPad | `com.gelb2.heavymach2.restored` | 최종 유니버설 일반 앱 |
| HM2 Validation | Restored와 같은 코어 + 조건 설정 도구 | iPhone·iPad | `com.gelb2.heavymach2.validation` | 회귀 조건 반복·계측 |

포팅 앱 두 개는 원본 게임 계산을 원본 바이너리가 수행한다. 복원 앱 두 개는 새 소스로 게임을 수행한다. 폴더·번들 ID·저장 컨테이너·로그·화면 표시명으로 구분한다. 최종 유니버설 앱은 하나이며, 기준 포팅 앱은 내부 검증용으로 남긴다.

두 포팅 앱은 같은 버전의 호환 실행기 소스를 공유할 수 있지만, 게스트 기기 종류·화면/배율·원본 입력·경로는 판본별 설정으로 분리한다. iPad 호스트 창 크기만 바꾸는 것으로 게스트가 iPad라고 인식한다고 가정하지 않는다.

기기별 현재 서명·설치 한도를 확인한다. 네 앱을 한 기기에 동시에 설치할 수 있다고 전제하지 않으며, 기존 HeavyMach 1·MachDefense·사용자 앱을 삭제해 자리를 만들지 않는다. 설치 충돌은 빌드/서명/실행 문제로 분리해 기록한다. 정상 저장은 백업하고 검사 앱에는 복사본만 사용한다.

## 3. 입력·실행기 적합성부터 확인

### 원본 판본 고정

- [외부 원본 명세](source-provenance.json)의 일반판4개·HD2개를 보존한다.
- 우선 일반판2.0.1과 HD1.0.3을 조사한다. 앞선 로컬 패키지 검사에서 일반판2.0.1은 ARMv6/ARMv7 두 slice, HD1.0.3은 ARMv7 하나였고 검사한 slice의 cryptid는0이었다. 이는 실행 성공을 뜻하지 않는다.
- 실제 선택한 slice·실행파일 해시·IPA 해시·앱 버전·기기 종류·최소 OS를 매 실행에 기록한다. 일반판을 ARMv6으로만 실행한 결과로 ARMv7 HD 동작을 추정하지 않는다.
- 이전 일반판1.0/1.1/1.3과 HD1.0은 변화 원인 분리에 사용한다. 같은 버전 숫자라고 출시 내용이 같은 것으로 취급하지 않는다. 잘 실행되는 구버전으로 바꾸면 기준 변경과 빠진 기능을 명시한다.

패키지 관측 근거: [일반판·HD판 메타데이터](evidence/standard-hd-package-metadata.json). 파일 비교와 실행 관측의 범위를 구분한다.

### 실행기 후보와 미확인 항목

HeavyMach 1 최초 커밋은 MoleWorld touchHLE 포크 `ebf9433e2bfd32071545bf49484b1345d15522a3`와 Rust CPU 인터프리터·SDL을 고정했다. 이는 재사용 검토의 출발점이며 HeavyMach 2 적합성이 확인된 버전은 아니다.

2026-11-09에 읽은 [touchHLE upstream](https://github.com/touchHLE/touchHLE)은 iPhone/iPad의 초기 iOS 앱을 지원 대상으로 설명하지만 대부분 앱이 동작하지 않는다고 명시한다. [공식 FAQ](https://touchhle.org/faq.html)는 iOS 호스트를 공식 지원하지 않는다고 설명한다. [MoleWorld 포크](https://github.com/moleworld-dev/MoleWorld-5.5.0-touchHLE-offline)는 iOS arm64용 no-JIT 인터프리터 경로를 설명한다. 세 설명을 HeavyMach 2 실행 성공으로 합쳐 해석하지 않는다.

| 확인 대상 | 조사/실행할 내용 | 통과 근거 |
|---|---|---|
| CPU | ARMv7·Thumb/Thumb-2·VFP 등 실제 사용 명령과 ABI. 실제 slice별 실행 | 미구현 명령과 비정상 종료 위치, 수정 전후 회귀. 무시하고 진행한 명령0 |
| 시스템 API | 두 바이너리의 import·ObjC selector·실제 호출 API, 파일·시간·음향·입력 | 미구현 API 목록과 실제 호출 경로. 필수 API를 빈 성공 반환으로 대체하지 않음 |
| iPad 게스트 | idiom·UIScreen bounds/scale·회전·UIView/터치·앱 전용 설정 | 게임이 읽은 반환값과 좌표/화면 결과. 실제 HD 코드 분기 확인 |
| 그래픽 | 실제 EAGL context/API 버전, framebuffer/renderbuffer, viewport, 투영·텍스처 로딩 | 호출/출력 관측. 일반판에 `.vsh/.fsh`가 있다는 사실만으로 실행 중 GLES2 사용을 확정하지 않음 |
| 자원 | CgBI/표준PNG·JPEG·음원·MCB·테이블의 실제 reader | 확장자뿐 아니라 헤더·디코드 결과·참조 경로 대조 |
| OS 호스트 | 현재 iOS/iPadOS의 scene·창·방향·중단/재개·서명 | 각 실제 기기에서 설치와 사용자 입력. 시뮬레이터 성공과 구분 |

지원 부족이면 HeavyMach2 전용 checkout에서 호환 계층을 수정하고 양쪽 판본을 회귀 검사한다. 특정 게임 주소를 건너뛰거나 원작 전투 코드를 복원 코드로 바꿔 포팅 성공을 만들지 않는다. 원본 실행이 막히면 원인과 다음 지원 구현을 기록한다. 가능한 정적 분석은 계속하되 해당 판본의 원작 동작 검증은 미완료로 둔다. 필요할 때 확보 가능한 구형 원기기의 관측은 별도 근거로 추가한다.

## 4. 파일과 빌드 격리

계획 경로:

- `Compatibility/`: HeavyMach2용 실행기 고정 명세·호스트 설정·패치·빌드 도구. 원본 IPA와 풀린 원본 실행파일은 넣지 않는다.
- `.local/compat-source/`, `.local/toolchain/`: 이 저장소 전용으로 준비한 의존성·캐시. HeavyMach1/MachDefense checkout을 수정하거나 그 소스 경로로 링크하지 않는다.
- 외부 `Documents/Codex/HeavyMach2/ReferenceBuilds/`: 원본을 포함하는 로컬 포팅 앱 번들·패키징 임시 자료. 저장소 밖의 별도 출력 경로다.
- `Sources/`, `Resources/`, `tests/`: 복원 소스·관리할 자원 명세와 검사. 원작 IPA를 실행하는 코드와 최종 복원 코드를 섞지 않는다.
- `.local/evidence/phone/<run>/`, `.local/evidence/hd/<run>/`: 로그·캡처·계측·저장 복사본. 원본 IPA는 여기에 복사하지 않는다.

모든 도구는 입력/출력 경로를 검증한다. 원본은 읽기 전용이며 패키징 전후 해시를 대조한다. 재패키징·서명하는 것은 외부 경로의 파생 호스트 앱이다. 원본 IPA 자체를 수정하지 않는다.

원본이 포함된 비교 앱은 로컬 빌드·로컬 기기 설치만 한다. Git/LFS/Actions artifact/릴리스/보고 사이트에 올리지 않는다. 외부 원본이 없는 CI에는 synthetic fixture로 검사 가능한 도구만 넣고 비교 앱 빌드를 성공한 것으로 표시하지 않는다.

## 5. 두 포팅 앱 각각의 완료 조건

| 단계 | 일반판/iPhone | HD판/iPad | 완료 조건 |
|---|---|---|---|
| P0 입력 확인 | IPA·실행파일·slice·자원 해시 | 동일 항목을 HD 입력으로 기록 | 판본과 실제 실행 입력이 일치 |
| P1 빌드 | 전용 일반판 호스트 | 전용 HD 호스트 | 새 출력 경로에서 컴파일·링크·패키징·서명 검사. 로그 보존 |
| P2 실행 | iPhone에서 일반판 분기 | iPad에서 HD 분기 | 설치→타이틀→메뉴→실제 플레이 진입. 각 기기에서 확인 |
| P3 기본 플레이 | 원작 지원 조작·이동·공격·피격·아이템·강화/성장 | HD의 같은 기능 목록을 별도 조사해 실행 | 입력 결과와 실제 상태 변화. 지원하지 않는 기능은 임의 추가하지 않음 |
| P4 진행·저장 | 클리어/실패·다음 구간·종료 후 재실행·저장 복구 | HD에서 같은 경계 확인 | 저장 파일·필드·쓰기 시점·재시작 상태를 관측 |
| P5 화면·음향 | 타이틀·메뉴·플레이·효과·결과·전환 | HD의 독자 이미지·배치 포함 | 원본 실제 자원·좌표·비례·음향 누락 검사 |
| P6 안정성 | 같은 장면의 프레임 간격·메모리·자원 수명·전경/배경 | 같은 절차를 iPad에서 별도 측정 | 크래시/누적 누수/시간 점프의 조사와 수정. 수치는 측정 후 기록 |

P0~P6의 공통 최소 관측을 마친 판본만 그 범위의 비교 기준으로 고정한다. 전체 캠페인·모든 유닛/무기·드문 분기는 목록을 열거해 후속 범위를 계속 추적한다. 첫 스테이지 성공으로 전체 원작 검증 완료라고 하지 않는다.

포팅판 자체의 화면 오류도 원작처럼 복제할 위험이 있다. 원본 자원·바이너리의 좌표/렌더 호출과 대조하고, 확보한 당시 영상/화면이나 구형 원기기 관측을 출처와 함께 보조 사용한다. 출처 없는 임의 화면을 정답으로 삼지 않는다.

## 6. 비교 자료와 수용 기준

각 기록에는 판본/IPA/slice 해시, 실행기 commit·patch 해시, 호스트 빌드, 기기/OS, 언어, 화면 방향, 게스트 논리 크기·framebuffer·최종 출력 크기, 저장 복사본 해시, 장면/시점/입력, 결과·실패·미검사를 포함한다.

- 일반판/HD판의 논리 해상도와 화면 배율은 실제 실행과 코드에서 측정한다. HeavyMach1의480×320이나 추정한 HD1024×768을 먼저 상수로 정하지 않는다. `@2x` 후보의 실제 선택 경로도 기록한다.
- 배경·기체·각 부품·무장·발사점·이펙트·HUD별로 이미지 픽셀 크기, 논리 표시 크기, 피벗·소켓, 회전·레이어·UV·필터·알파를 분리해 기록한다.
- 전투는 동일한 지원 조건의 초기 저장·기체·무기·적·장면·입력 시점을 맞춘다. 직접 관측 가능한 HP·탄약·위치·상태·이벤트를 비교한다. 의미가 확인되지 않은 원작 메모리를 임의 조작해 동일 조건이라고 하지 않는다.
- 난수·타이머를 안전하게 통제하지 못하면 프레임 전체 픽셀 일치를 요구하거나 달성했다고 보고하지 않는다. 정적 장면의 기하/픽셀, 동적 사건의 수치·순서·시간 범위를 나누고 통제하지 못한 조건을 남긴다.
- 출력 크기를 맞춘 뒤 비례·좌표를 비교한다. 비교 이미지를 임의로 늘이거나 자르면서 차이를 숨기지 않는다. 동적 요소 마스크와 수치 허용오차는 검사 전에 근거를 정한다. 새 실패를 덮기 위해 허용오차를 늘리지 않는다.
- 디코드 픽셀·자원 바이트의 동일성, 화면 기하의 동일성, OS/GPU 출력의 색/보간 차이는 다른 검사다. 단순 스크린샷 유사도 하나로 모두 통과시키지 않는다.
- 성능은 같은 실제 기기·장면·입력·기록 길이·열 상태로 비교한다. 시뮬레이터 FPS를 실기기 성능으로 환산하지 않는다.

## 7. 복원판과 대조하는 네 가지 구성

| 기준 | 후보 | 필수 비교 |
|---|---|---|
| 일반판 포팅 앱 / iPhone | 유니버설 일반 앱 / iPhone 구성 | 원작 표시·입력·전투·진행·저장·성능 |
| HD판 포팅 앱 / iPad | 같은 유니버설 일반 앱 / iPad 구성 | HD 표시·기하·터치·전투·진행·저장·성능 |
| 일반판 포팅 앱 / iPhone | 유니버설 치트 앱 / iPhone 구성 | 지원 조건을 맞춘 반복 검증. 치트 입력이 실제 공통 코어를 호출하는지 확인 |
| HD판 포팅 앱 / iPad | 같은 유니버설 치트 앱 / iPad 구성 | HD 조건에서 같은 검증. 폰 검사 통과로 대체하지 않음 |

치트 앱의 설정 성공과 실제 이동·발사·명중·소비·성장을 구분한다. 일반 앱에는 치트 기능과 검사 저장을 넣지 않는다. 가능하면 원본 비교 앱은 무개조 입력으로 유지하고, 계측이 필요하면 관측 패치와 기능 변경을 분리해 기록한다.

두 판본 사이에서는 파일/규칙 차이를 분류한다. 현재 같은 MCB3개, 다른 테이블59개, PNG 차이를 화면용·게임 규칙용·언어/문구·버전 변화·미확인으로 조사한다. 공유 코어는 이 대조 후 같은 동작이 확인된 범위만 맡는다. 특히 iPhone에서 iPad로 같은 진행을 옮길 때 기체/아이템/미션 ID와 저장 의미가 같다고 미리 가정하지 않는다.

## 8. 구현 단계와 종료 기준

| 순서 | 산출물 | 다음 단계 기준 |
|---|---|---|
| R0 | 위 이력 검토·두 판본 계획·TODO | 이번 문서 보완 범위. 앱 검증 완료가 아님 |
| R1 | 판본별 실행기 적합성 조사·고정 입력·필수 API 목록 | CPU/게스트 기기/그래픽 경로와 미지원 항목이 명확함 |
| R2 | 일반판/HD판 포팅 앱·P0~P6 결과 | 각각의 실제 기기 비교 기준 확보. 실패한 판본은 별도 미완료 |
| R3 | reader·파츠·좌표·렌더·시간·저장 계약과 함수 대응표 | 원본 주소/데이터→새 구현→검사를 연결할 수 있음 |
| R4 | 공통 코어 + 일반판/HD 표시 구성 + 일반/치트 앱 | 네 구성 비교와 모든 원작 자원 참조·부품 조립 검사 |
| R5 | 유니버설 통합·현대 화면 크기·회전·창 변화 대응 | 각 원작 기준 유지, 기기 간 선택/자원 혼입0, 화면 확장과 전투 활성 조건 분리 |
| R6 | 독립 빌드·패키지 검사·정식 기기 검증 | 두 IPA·원본 ARM 실행파일·호환 실행기·다른 게임 checkout 접근 없이 복원판 빌드/실행 |

R6에서는 원본을 삭제하는 대신 접근 불가능한 별도 빌드 환경을 사용한다. 앱에 필요한 이미지·음향·게임 데이터는 출처·권리·배포 범위를 명시한 자원 명세로 준비한다. IPA/원본 실행파일은 어떤 Git 저장소나 원격 배포 산출물에도 넣지 않는다. 새 clone의 필요한 자원 준비와 실제 빌드 입력을 대조한다. 이 단계의 자원 관리 결정 전에는 독립 빌드 완료라고 하지 않는다.

이번에는 R0만 작성했다. R1 이후 구현·원작 실행·기기 설치는 TODO에 남긴다.
