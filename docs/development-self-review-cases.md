## 프레임과 이동, 입력 어댑터

iPhone 시뮬레이터에서 한 점 또는 여러 점으로 경로를 교체한 뒤 점프가 간헐적으로 실패했다. Apple 어댑터가 UIKit의 미세한 좌표 차이를 이동으로 넘겼고, 같은 캔버스 위치에서도 첫 탭 기록이 지워졌다. 기존 치트 입력은 UIKit 원시 좌표를 지나지 않아 이 경로의 판정에 사용할 수 없었다. 수정 뒤 각 기기의 두 경로 교체 조건을 다섯 번씩 실행해 iPhone과 iPad에서 각각 10회 통과했다. 치트 검사에서는 점프 한 번과 SP 100 소비를 확인했다. [재현·수정·판정](iphone-module-audit-20261118.md)

Skyway는 실제 기지 버튼으로 게이트 1에 진입해 300프레임씩 캡처했다. iPhone 배경 이동 최대값은 3.170pt에서 0.000031pt로 줄었다. iPad에서는 비교한 프레임 0과 170의 RGB 픽셀이 수정 전후 각각 일치했다. 물리 iPhone의 반복 손 입력 성공률과 연속 GPU 프레임은 당시 확인 범위에 남았다. [프레임 측정과 한계](iphone-module-audit-20261118.md#wasteland-base에서-skyway로-나간-뒤의-떨림)

## iPad PWA 재설치와 배포 검증

아래에서 1인칭은 이 실행과 보고를 수행한 Codex를 가리킨다. 표에서 쓰는 자료 폴더는 프로젝트 로컬 `.local/evidence/ipad-pwa-hotfix.BdRMxq/`다. 2026년 11월 23일 조사 시점 공개판은 v0.5였다. 후속 워커 후보는 로컬 설치에서 검증했다.

### 내가 잘못 처리한 부분

1. **재설치가 실패한 기록을 첫 보고에서 빠뜨렸다.** v0.5의 공개 파일 17개가 해당 배포 산출물과 일치했고 iPad 9의 새 아이콘이 기본 상태 막대를 쓴 것은 확인했다. iPad Air 13의 재설치에서는 같은 하단 띠가 남았다. 나는 먼저 성공한 경로를 중심으로 결론을 내렸고, 사용자는 실패를 다시 지적해야 했다. 설치 직전에 Safari가 실제로 제공한 HTML과 설치 직후 iPadOS가 기록한 상태 막대를 함께 판정했어야 했다.
2. **서비스 워커의 준비와 활성화를 같은 단계처럼 다뤘다.** 서버의 새 파일 배포, Safari 탭을 제어하는 워커, 홈 화면 아이콘에 기록된 설정은 각자 갱신 시점이 있다. 공개 주소의 해시만 확인하면 Safari가 오래된 HTML을 제공하는 경로를 놓친다. v0.3 탭을 열어 둔 상태에서 v0.5를 제공하니 설치 주소에 쿼리를 붙여도 반투명 상태 막대 지정이 남았다. [PWA 릴리스](https://github.com/gelb2/HeavyMach2/releases/tag/v0.5) · [공개 패키지](https://gelb2.github.io/HeavyMach2/build.json)
3. **검사 코드의 대기 자체도 틀렸다.** 첫 회귀 검사에서 비동기 조건의 실제 값을 기다리지 않고 새로고침했다. 당시 기록들을 대조해 워커가 활성화됐다는 증거가 없음을 확인했다. 조건의 실제 값을 반복 읽도록 검사 코드를 고친 뒤 새 시작 페이지와 오프라인 실행을 확인했다. 검사 성공 여부에는 이미지에 붙인 이름이나 테스트 종료 코드만 쓰지 않는다. 앱이 실제로 설치 상태였는지, 어느 버전이 요청을 처리했는지, 캡처에 기대한 장면이 있는지를 확인한다.
4. **최신 레퍼런스의 설치 진입점을 먼저 확인하지 않았다.** HeavyMach 1의 WASM PR에서 게임 문서만 보면 반투명 설정이 있다. 현재 공개판의 홈 화면 추가는 그 게임 문서를 iframe에 넣는 바깥 시작 페이지에서 진행한다. MachDefense는 시작 페이지에서 워커 갱신을 요청하고 활성화 뒤 다시 연다. 재설치 검사를 설계할 때 두 구현의 현재 공개 경로를 먼저 읽었어야 했다. [HeavyMach 1 현재 시작 코드](https://github.com/gelb2/HeavyMach/blob/e3b54774a76823300e786e85fd0a1dc8e6097e44/Distribution/Web/pwa/host.js) · [MachDefense 현재 시작 코드](https://github.com/gelb2/MachDefense/blob/3f38bd161d159f4a369fa1555a7a38e3ca4e8456/Distribution/Web/app.js#L59)

### 결함별 코드 근거와 수정 판정

#### 1. 탐색 요청이 이전 설치 문서를 계속 받았다

`Web/Shell/sw.js`는 웹 탐색 요청을 활성 캐시의 `index.html`로 연결한다. v0.5 워커가 설치 후 대기하는 동안 해당 요청은 v0.3 워커가 처리할 수 있다. 설치 아이콘을 다시 만들 때 Safari가 이 문서를 열고 있으면 그 문서의 상태 막대 설정이 사용된다. 재현에서는 열린 탭이 있을 때 쿼리 변경만으로 메타 태그가 사라지지 않았다. 사용자의 물리 iPad에서 어느 요청이 해당 HTML을 받았는지는 이 시험으로 특정할 수 없다.

후속 패키저는 이전 공개판의 게임·런타임 파일 목록, 길이, SHA-256을 대조한다. 워커는 확인된 기존 캐시의 자원을 재사용하고 새 문서를 준비한 뒤 활성화한다. 합격 조건은 이전 탭을 유지한 채 다음 탐색에서 새 문서를 받고, 기존 런타임으로 오프라인 실행을 계속할 수 있는 것이다. WASM 해시가 다른 명세를 패키저가 거부하는 검사도 실행했다. 코드 위치는 `619d423`의 `Web/Shell/sw.js` 설치·활성화·탐색 처리와 `Web/package.py`의 `--compatible-with` 비교다. [Chrome 팀의 설치·대기·활성화 설명](https://web.dev/articles/service-worker-lifecycle) · [서비스 워커 표준의 skipWaiting](https://w3c.github.io/ServiceWorker/#service-worker-global-scope-skipwaiting)

#### 2. 검사에서 대기 조건을 실제로 확인하지 않았다

첫 검사는 비동기식 판정 결과를 기다리지 못한 채 브라우저를 새로고침했다. 진단 로그에는 이전 캐시들이 남았고, 읽은 HTML의 `black-translucent`가 여전히 참이었다. `619d423`의 `Web/tests/installation-update.mjs`에서 상태를 반복 조회해 대기 워커가 없고, 새 워커가 활성 상태로 해당 탭을 제어하며, 예상 캐시만 남았을 때 다음 입력을 수행한다. 그 뒤 응답의 태그 수와 실행 결과를 검사한다. 조건을 계속 충족하지 못하면 제한이 끝났을 때 실패 이유를 기록한다. [Playwright의 반복 확인 예시](https://playwright.dev/docs/test-assertions#expectpoll)

#### 3. 설치 안내와 게임 실행 화면을 같은 진입점으로 판단했다

HeavyMach 1은 설치에 쓰는 바깥 문서와 버전별 게임 문서를 따로 제공한다. MachDefense는 실행 전에 워커 갱신을 요청하고 대기 워커의 활성화와 문서 재탐색을 처리한다. 두 공개판에서 각각 시작 HTML, JavaScript, 스타일 파일 세 개를 소스와 해시로 대조했다. HeavyMach 2에서도 실제 설치 문서, 새 아이콘의 상태 막대 값, 게임 하단을 각각 확인한다. 게임 캔버스 크기만 늘려도 해결된다는 가정은 같은 iPad의 시험 페이지에서 기각됐다. 전체 높이 1,366으로 요소를 키운 상태에서도 웹 표시 영역은 1,334였다. [HeavyMach 1 워커](https://github.com/gelb2/HeavyMach/blob/e3b54774a76823300e786e85fd0a1dc8e6097e44/Distribution/Web/pwa/sw.js) · [MachDefense 워커](https://github.com/gelb2/MachDefense/blob/3f38bd161d159f4a369fa1555a7a38e3ca4e8456/Distribution/Web/sw.js)

#### 4. 기존 화면 검사의 합격 범위를 넓게 읽었다

Mac Chrome의 1,280×800 설치 앱에서는 HUD 양옆의 지면 아래에 RGB가 모두 0인 73행이 관측됐다. 기존 `allMapEdges` 검사는 `lowerOverscan=0`인 카메라를 만들었다. 그 검사에 합격해도 실제 데스크톱 설정으로 열린 전장에서는 73행이 남았다. 카메라 하한으로 드러나는 지형 경계는 별도로 재현해야 한다. PWA 설치 갱신의 합격 결과는 이 카메라 결함의 판정을 바꾸지 않는다. 카메라 변경을 검사할 때는 실제 플랫폼의 카메라 설정으로 전장에 진입하고, HUD 바깥 하단의 픽셀과 포털 터치를 함께 확인한다. 로컬 기록은 `.local/evidence/pwa-field-bottom.IkD4iu/pwa-field-bottom-audit.md`에 있다.
