# 기본 줌 수정 계획 — 공통 C++ 모듈

## 결정

**줌 계산은 새 공통 C++ 모듈이 담당한다. iOS·Android 앱에는 줌 수식이나 기종별 분기를 넣지 않는다.**

모듈 위치는 `Sources/Core/Presentation/CameraPresentation.hpp/.cpp`다.

iPad의 현재 월드 배율1은 유지한다. 휴대폰의 대기 배율은 현재 약1.428에서 **1.0을 첫 수정 후보**로 낮춘다. 이 후보에서는 iPhone Air의 시야가 약639×294에서912×420으로 넓어진다. 원본과 동일하다고 확정한 숫자는 아니며, 구현 뒤 같은 조건의 표시·입력·경계를 검사해 채택한다. 이번 작업은 계획 수립·게시까지다. 게임 구현·새 설치는 하지 않았다.

**iPad의 기존 표시·입력·전투 동작 보존은 이번 변경의 필수 합격 조건이다.** 배율1만 유지하고 나머지가 달라지는 결과도 실패다. 기존 계획의 iPad 회귀 조건을 아래의 정책·상태 격리와 전후 대조 기준으로 구체화했다.

## iPad에 영향을 주지 않는 구조

- `CameraPresentation`은 공통 진입점이다. 내부의 regular 고정 정책과 compact 거리 기반 정책은 계산·상태를 분리한다. regular는 현재 배율1과 기존 viewport/offset 규칙을 반환하며 휴대폰용 정규화·최소 줌·보간을 실행하지 않는다.
- 현재/목표 줌 상태는 각 `CombatScene` 인스턴스가 소유한다. 전역 변수, `static` 가변 줌, 기기 종류별 공유 상태를 만들지 않는다. 치트의 휴대폰 세션이 iPad 세션의 카메라나 시간을 바꿀 수 없어야 한다.
- 두 정책은 같은 읽기 전용 결과 형식을 반환한다. `GameSession`과 호스트가 기기별로 수식을 다시 선택하지 않는다. `DisplayLayout`의 기존 regular 수식과 부동소수점 계산 순서를 유지해, 배율1이라는 이유로 좌표 연산을 임의로 재결합하지 않는다.
- HUD 배치·편집 저장, 게임 저장, 에셋 캐시, 원작 카메라 위치 추적, 게임 시간·RNG·음향은 휴대폰 줌 조정의 변경 대상에서 제외한다. 연결에 필요한 변경이 있으면 기존 iPad 결과가 같은지 별도로 증명한다.
- regular→compact→regular 전환에서는 휴대폰 줌 상태를 iPad로 가져가지 않는다. 화면 구성 변경 때 입력 취소·새 viewport의 경계 제한은 기존 순서를 유지한다. 매 draw·입력마다 정책을 초기화하지 않는다.

공통 코드라는 이유로 모든 화면 구성을 같은 가변 줌 분기로 통과시키지 않는다. 정책 선택도 공통 C++에서 처리하며 iOS/Android 앱에 옮기지 않는다.

## SOLID를 적용할 경계

| 원칙 | 이번 구현의 구체적인 제한 |
|---|---|
| 단일 책임 | 정책 선택은 화면 구성 해석, 고정/거리 정책은 줌 계산, Layout은 화면 변환/HUD, MapCamera는 위치/경계, MapPreview는 표시를 맡는다. `CameraPresentation`은 이 결과를 묶고 시간·저장·에셋·음향을 소유하지 않는다. |
| 개방·폐쇄 | 휴대폰 계수 조정이나 새 화면 정책 추가 때문에 regular 계산·HD 전투 로직을 수정하지 않는다. 공통 정책 선택부와 해당 정책의 값만 확장한다. |
| 리스코프 치환 | 두 정책 모두 같은 HD 단위, 유한한 양수 배율, 일치하는 viewport와 정·역변환을 반환한다. 같은 필드에 한쪽은 절대 배율, 다른 쪽은 상대 줌을 넣지 않는다. |
| 인터페이스 분리 | 호스트는 화면 정보만, 정책은 필요한 위치·경로 정보만, 출력/입력 소비자는 계산 결과만 받는다. 줌 사용을 위해 저장·오디오·UI 전체 객체를 요구하지 않는다. |
| 의존성 역전 | 게임 코어는 공통 입력/결과 계약에 의존한다. Core에서 UIKit·Android 클래스·브라우저 API를 참조하지 않는다. 플랫폼 어댑터가 공통 계약에 맞춘다. |

이를 위해 필요 없는 상속 계층이나 프레임별 객체 생성을 추가하지 않는다. 값 형식·작은 정책 함수로 같은 책임과 계약을 지킬 수 있으면 그 구성을 사용한다.

## iPad 전후 대조와 실패 처리

기준은 현재 카메라 변경 전의 `bfde129` 소스와 보존한 iPad 실행 근거다. 실제 설치 iPhone의 `bc3323a`와 혼동하지 않는다. 새 게임 코드를 고치기 전에 비교 입력·판정 기준을 고정한다. 이번 계획 보강을 새 검사 실행으로 보고하지 않는다.

| 비교 대상 | iPad 보존 조건 |
|---|---|
| 카메라 | 같은 맵·장비·좌표·표적/경로·seed·프레임에서 배율1, viewport, 중심/offset, 경계 제한, 배경 시차가 기존과 같다. |
| 그림·입력 | 공통 Frame의 정점·크기·레이어·clip과 월드/화면 변환 결과가 같다. HUD·선택·이동/경로·점프·공습의 터치 위치가 같다. Native GPU는 기존 검사 허용 오차를 유지하며 기준을 완화하지 않는다. |
| 전투·진행 | 동일한 iPad 조건에서 HP·표적·탄환/격파·아이템·BOT·진행·저장 결과와 tick/RNG 소비가 기존과 같다. 시야에 의존하는 기존 HD 조건도 유지한다. |
| 동시 세션 | 휴대폰 정책을 서로 다른 값으로 진행하는 동안 동일 입력의 iPad 세션 결과가 변하지 않는다. 반대 순서와 생성/파괴 순서도 검사한다. |
| 재구성 | 화면 크기·방향·안전 영역 변경과 regular→compact→regular 뒤에 기존 regular 결과가 복구된다. 폰의 보간 상태나 입력 소유자가 남지 않는다. |

기존에 기록한 실패는 새 회귀와 구분해 보존한다. **이번 카메라 변경으로 iPad에서 차이가 발생하면 완료·병합·설치 단계로 넘어가지 않고 원인을 수정한다.** iPhone 검사 통과로 iPad 실패를 덮거나 기대값을 새 결과에 맞춰 바꾸지 않는다. 원본·사용자 저장·기존 커밋을 되돌려 차이를 숨기지 않는다.

## 어디를 어떻게 바꿀 것인가

| 공통 코드 위치 | 구현할 책임 |
|---|---|
| 새 `Presentation/CameraPresentation.hpp/.cpp` | 화면 구성에 맞는 카메라 정책, 대기 배율, 표적/경로에 따른 목표 배율, 현재 배율의 점진 갱신, 최종 월드 배율·시야·출력 변환을 한곳에서 계산한다. |
| 기존 `Presentation/DisplayLayout.hpp/.cpp` | 화면 크기·안전 영역과 HUD 배치를 유지한다. 월드는 이미 결정한 최종 배율을 받는 `worldAtScale` 경로를 추가한다. 기존의 숨은0.5배 재적용을 제거한다. |
| 기존 `Simulation/CombatScene.hpp/.cpp` | 플레이어·선택한 표적·마지막 이동점을 공통 모듈에 전달한다. 현재 `updateDisplay`의 채움 배율×확대 계수 계산을 제거한다. 결과를 `MapCamera.viewport`와 HUD 보호 높이에 연결한다. |
| 기존 `Simulation/WorldNavigation.cpp` | 원작의 카메라 위치 추적을 유지한다. 새 시야에 맞춰 경계를 제한한다. 이곳에 두 번째 줌 계산을 넣지 않는다. |
| 기존 `Session/GameSession.cpp` | 월드 출력·좌표 변환·터치 역변환이 같은 카메라 결과를 사용하게 한다. `drawWorld`, `worldCanvasPoint`, `inputWorld`를 함께 바꾼다. |
| 기존 `Presentation/MapPreview.cpp` | 배율을 정하지 않는다. 전달받은 시야에서 원본 지형·배경을 그린다. 가장자리와 배경 시차를 확인하고 검은 테두리가 생기지 않게 한다. 지형·유닛을 임의로 늘리지 않는다. |

경로의 앞부분 `Sources/Core/`는 표에서 생략했다. 새 `.cpp`는 `CMakeLists.txt`의 공통 라이브러리와 Apple 프로젝트의 정식/치트 두 타깃에 같은 파일로 등록한다. 플랫폼별 복사본을 만들지 않는다.

## 모듈의 입력과 결과

앱은 화면 정보를 전달하고, 게임 세션은 전투 정보를 전달한다. 공통 모듈은 둘을 받아 표시 결과를 만든다.

| 항목 | 계약 |
|---|---|
| 화면 입력 | 논리 화면 크기, 안전 영역, 크기에서 정한 compact/regular 구성. 방향은 폭·높이로 반영한다. 픽셀 밀도는 호스트의 픽셀/논리 좌표 환산에만 쓰고 줌을 다시 곱하지 않는다. |
| 전투 입력 | 플레이어 위치, 유효한 표적 위치, 마지막 이동 경로점, 초기화/프레임 진행 여부. |
| 정책 | regular는 현재 iPad의 고정 월드 배율1. compact는 낮춘 대기 배율과 표적·경로 기반 줌 범위를 사용한다. 같은 창 조건이면 OS가 달라도 같은 정책을 선택한다. |
| 보관 상태 | 정책 이름, 현재/목표 focus 계수, 대기 기준 배율. 화면 채움 값을 focus 계수에 곱하지 않는다. |
| 읽기 전용 결과 | 최종 월드 배율, 보이는 월드 폭·높이, 월드 화면 변환, 현재/목표 계수. HUD 배율은 포함하지 않는다. |

계획상의 API 이름은 `configure(DisplayConfiguration)`, `advance(CameraFocus)`, `snapshot()`이다. 화면 변경은 configure, 프레임당 줌 갱신은 advance, 출력/입력은 같은 snapshot을 사용한다. draw나 터치 수신 때 배율을 한 번 더 갱신하지 않는다. 파일 쓰기·DB·RNG·사운드 처리를 추가하지 않는다.

## 배율을 정하는 방법

현재의 문제는 화면 채움 배율을 목표 확대에 곱한 것이다. [조사 결과](camera-baseline-investigation-20261114.md)의 약1.428을 그대로 정책 상수로 옮기지 않는다.

1. iPad regular 구성은 월드 배율1, 현재 HUD와 카메라 위치 추적을 유지한다.
2. compact의 **대기 기준 배율 후보는1.0**이다. 표적·경로가 없는 첫 상태도 이 값으로 초기화해, 아무 입력 없이 기다린다는 이유로1.428까지 확대되지 않게 한다.
3. 기존 거리 기반 focus 계수1..1.6은 무표적 최댓값1.6을 기준으로 정규화한다. 대기값은1, 먼 표적은 그보다 작아지는 방향이다. 원작의 목표 선택과 차이/100의 점진 변화는 유지하며 게임 시간·틱 주기는 바꾸지 않는다.
4. 필요한 유한 맵 경계 제한은 **최종 배율의 하한 검사**로 한 번 적용한다. 대기 배율 전체에 다시 곱하지 않는다. 912×420, 유효 맵 폭1022 기준의 하한은 약0.892다. 첫 후보의 일반적인 범위는 약0.892..1.0이며 기존1.428까지 확대하지 않는다. 실제 표적·경로 시야가 충분한지는 구현 뒤 확인한다.
5. 하한이 대기 배율보다 커지는 매우 넓고 낮은 창은 별도 경계 조건이다. 그 결과를 조용히 과확대해 처리하지 않는다. 원본 배경/경계 표시로 여백 없이 처리할 수 있는지 검사하고, 불가능한 화면 구성의 조정 기준을 공통 정책에서 결정한 뒤 지원 완료로 판정한다.

1.0은 원본과 같은 크기라는 선언이 아니다. 현재 iPad 단위를 보존하면서 휴대폰의 과확대를 줄일 첫 후보를 명시한 것이다. 신규 같은 조건 대조에서 원작 대비 표시 크기가 다르면 후보 배율을 공통 정책에서 조정하고 근거를 남긴다. 기존28×31·46×53 표본은 장비/방향/줌이 완전히 같지 않으므로 그 비율을 고정 상수로 넣지 않는다.

## 플랫폼 앱이 할 일

Apple `HM2SourceView::updateDisplay`는 현재처럼 bounds·안전 영역을 공통 `DisplayConfiguration`에 전달한다. `HM2GameRuntime`의 월드 입력 환산과 `HM2SourceView`/`HM2ConcurrentRuntime`의 검사 수치는 공통 카메라 결과를 읽도록 바꾼다. 이 읽기 연결은 플랫폼별 줌 구현이 아니다.

Android의 화면 픽셀/밀도 환산이나 웹의 CSS 크기 전달도 호스트 역할에 한정한다. 이후 Android·PWA·Tauri를 연결할 때 같은 C++ 결과를 사용한다. 현재 HM2 제품 소스의 실제 연결은 Apple이며 다른 플랫폼을 이미 구현·검증했다고 보고하지 않는다.

정식판과 치트판은 같은 공통 코드를 사용한다. OS 이름·기기 모델명으로 카메라를 선택하거나 iPhone용 게임 소스·별도 에셋·UIKit 인게임 UI를 추가하지 않는다. HD 충돌·사거리·속도·무기·저장 규칙은 바꾸지 않는다. 시야가 변하면 기존 HD의 화면 판정이 전투 후보에 영향을 줄 수 있으므로 경계 전투를 따로 검사한다.

## 구현과 검사의 순서

1. 위 iPad 기준 입력·결과를 먼저 고정하고 공통 모듈과 모든 출력/입력 소비자를 한 묶음으로 수정한다. regular 고정 정책을 보존하고 compact만 새 정책으로 바꾼다. `displayZoom()`의 기존 혼합 의미를 새 상태의 focus 계수/최종 배율로 구분하고 남은 호출을 검색한다. HUD와 저장 데이터는 기존 형식으로 유지한다.
2. `tests/DisplayLayoutTests.cpp`와 실제 `GameSession` 검사에서 진입·대기1,200tick·표적/경로 변경·정지/재개·회전을 검사한다. 기존 `fit..fit×1.6` 기대값을 통과 기준으로 재사용하지 않는다. 시야·그림 크기와 입력 왕복을 함께 확인한다.
3. `ConcurrentValidation.cpp/.hpp`의 기존120조건에 무표적 대기·근/원거리·경로 끝·경계 시나리오를 추가해 동시에 실행한다. 현재/목표 계수·최종 배율·시야·출력 영역·표적·저장/자원 계수를 수집한다. 여러 조건을 버튼 하나씩 누르는 검사로 대체하지 않는다.

## 작업 전에 실행한 빌드 정리

계획 작성 전에 오래된 생성물15경로·11,792파일, 합계3,295,729,199바이트를 삭제했다. 삭제 직전 사용 중인 파일이 없음을 확인했다. 여유 공간은 약2.65GB에서5.91GB가 됐다. 다른 세션의 작업에 따라 이후 여유 공간은 달라질 수 있다.
