# 게임오버와 랭킹 안내 복원

2026-11-11. 현재 범위는 iOS·iPadOS 정상 플레이와 동시 치트 검증이다. 다른 플랫폼 확장·빌드 설치/전달·배포·develop/main 릴리스는 제외한다.

## 바뀐 동작

실제 적 공격으로 Player HP가 0이 된 뒤 원본 crash 처리에서 state2→3을 소비한다. World는 gameState3과 전역 render 시각을 기록하고 `Destroy Your Mach.` 알림을 한 번 요청한다. 본문은 원본 한국어 `DestroyMach` 문구이며 OK 하나다. 이 단계에는 추가 저장·회복·강제 일시정지가 없다.

OK 응답은 현재 Session의 요청 token과 대조한다. 유효한 응답만 lastBase를 현재 장소로 복사하고 기존 문 전환으로 기지에 돌아간다. 회복과 BOT savedHP 초기화·저장은 기존 Base 진입에서 처리한다. 오래된 Session·슬롯·중복 응답은 게임과 저장을 바꾸지 않는다. token은 원본 alert 객체의 일치 검사를 현대 어댑터에서 보존하는 수단이며 원본 구현에 token이 있었다는 뜻은 아니다.

사용자 지시에 따라 랭킹5009는 `랭킹` 제목과 `현재 랭킹 서비스를 이용할 수 없습니다.`를 기존 OS 알림으로 표시한다. 기존 영문 저장을 위한 영어 표시도 준비했다. 서버·GameCenter 인증·점수 전송과 가짜 순위는 구현하지 않는다. 안내 뒤 원본 버튼 효과음0을 재생하며 화면·게임 값·저장은 그대로 둔다. SaveExit의 기존 저장→best 갱신 순서도 유지한다.

## 원본 근거와 수정한 차이

HD 실행 파일 SHA256은 `5feb7ae5f796cdfee5d650037923d338ce7b28de7f600c8548a7a5bbf7ef5090`이다. 로컬 REA의 Player.onDestroy·World.setGameOver·GameMain alert 응답·GuiBase 초기화 분석을 사용했다. 원본 소스를 확보했다는 뜻은 아니다. IPA와 실행 파일은 저장소·보고 사이트에 포함하지 않는다.

기존 구현은 실제 피해로 state2까지 도달해도 onDestroy 소비자가 없어 파괴 알림과 기지 복귀가 없었다. 동일 전투 probe에서 실제 사망 frame587, 수정 전 다음 tick에도 actor2/world0/알림0, 수정 후 actor3/world3/알림1을 확인했다. 원본은 피해와 Player tick 순서에 따라 같은 World pass에서 파괴 처리를 마칠 수도 있다. 임의 한 프레임 지연이나 사망 대기 시간을 추가하지 않았다.

독립 검토에서 문 전환으로 새 Scene을 만든 프레임의 Scene 시각이 Session 전역 시각보다 한 step 앞서는 차이를 발견했다. 이번 상태 기록은 Session 전역 시각을 공급받도록 고쳤다. 실제 title→slots→문→field 진입 검사에서 두 시각이 다른 조건을 만든 뒤 파괴 시각이 Session과 일치하는지 확인했다. 이 수정이 기존 Scene의 모든 시간 처리를 변경하거나 해결했다는 뜻은 아니다.

Base는 장소 앞 네 글자가 `Base`인지 검사한다. 정의된 맵인지 검사해 모든 미정의 Base 이름을 Base001로 바꾸는 규칙은 원본에 없다. 이전 계획의 “유효하지 않은 장소”는 이 접두 검사 범위로 해석한다.

## 시뮬레이터의 남은 성능 문제

기존15초 대기는 iPad에서 문 열림이 끝나기 직전 실패했다. 로그에는 실제 OK 수락·Base002 진입·HP256·저장과 phase2→3→5→7이 남았다. 전장7~8tick/s·기지18~20tick/s였으며, Debug O2도 이 벽시계 실패를 해결하지 못했다. 실행 샘플 main thread629개 중456개가 `glDrawArrays`와 `GLRendererFloat` 삼각형 그리기 경로였다. 이 결과를 실기기 성능으로 확대하지 않는다.

기능 검사의 외부 대기만60초로 두고 실제 confirm 수락부터 첫 phase8 관측까지166~300 tick을 요구했다. 원본 문 수식·게임 시간·렌더 결과는 변경하지 않았다. 독립 검토에서 발견한 시작 프레임 누락도 실제 callback 수락 marker로 수정했다. 최종 predicate 대기는 iPhone7.10초·iPad16.07초다. iPad의 기존15초 성능 기준은 실패로 유지한다. 300은 원본 전환 길이가 아니라 UI 관측 상한이며 원본 정확166 tick과 구분한다. 캡처 시간은 이 측정에서 제외했다.

Core는 Release, 동시 Native114는 Debug, 최종 Source OS UI와 iPhone 정상 Native4개는 Debug O2였다. iPad의 정상 Native4개도 실제 시계 기본 경로에서 통과했다. 빌드 설정이 다른 결과를 단일 정식 배포 검증으로 합치지 않는다. 원본 포팅판의 실제 GameOver 화면·알림 중 lifecycle 전체 대조는 아직 남는다.

이 단계로 전체 게임·전체 임무·원작 전체 화면 동등성이 검증된 것은 아니다. 다음 소비자는 Command 진입 시 완료 임무를 순서대로 찾아 창 생성 때 보상을 지급하는 경로와5007이다. 원본형식 시작 저장에서 M002010/M001010 두 임무의 조건과 수락 순서를 준비하고 실제 Command 진입을 검사했다. 첫 M002010의80Cr가 자동 지급돼야 하지만 현재500→500Cr이며 추가 저장은0회다. 실패 로그는 별도로 보존했다. 기존 Progression 보상 executor를 재사용하고 실제 GPU 팝업·저장0·중복 지급 방지를 검증한다.
