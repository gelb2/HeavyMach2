# iPhone 배경·기지 버튼·자원 수명 조사

일반판에는 가로480×320 배경이 별도로 있다. HD의 세로768×1024 배경과 같은 파일을 확대해 쓴 구성이 아니다. 기지 버튼의 위치도 각 판본의 테이블에 따로 들어 있다. 따라서 iPhone 원본 그림을 공통 표시 경로에서 선택하는 방안은 가능하지만, 그림만 바꾸거나 일반판 테이블 전체를 선택해서는 요구를 만족하지 못한다.

이 조사는 일반판2.0.1과 HD1.0.3의 원본 패키지·기존 REA 함수 export·현행 소비 코드를 읽었다. 원본2개의 IPA 해시가 조사 전후 일치했다. 원본 함수16개, 배경16개, 기지 테이블12개의 선택 계약/메타데이터를 대조했다. 앱·시뮬레이터·실기기는 실행하지 않았고 게임 코드를 수정하지 않았다. [근거 JSON](evidence/iphone-background-asset-research-20261114.json)에 해시·좌표·Evidence ID를 남겼다.

## 원본 그림 대응

|---|---|---|---|

| 맵 사이 로딩 가림 | `StageClearBG.png`,480×320,CgBI PNG | `StageClearBG.png`,768×1024,CgBI PNG | 일반판0x3b568, HD GuiMapLoading.init0x2da14. 불투명화→객체 비움→월드 타일 비움→맵 설정→투명화 순서. |
| 기지 바탕6개 | `Base001.jpg`..`Base006.jpg`,각480×320,JPEG | `Base001.png`..`Base006.png`,각768×1024,CgBI PNG | 기지별 `.tble`의 Image 행→동일 tile manager→QobImage. |
| 기지 선택 강조 | 기지별 CmdCenter/Shop/Maintenance PNG와 테이블 좌표 | 기지별 CmdCenter/Shop 등 PNG와 테이블 좌표 | Image ID11/12/13은 선택 상태의 별도 그림이다. 배경을 바꿀 때 이 그림도 함께 대응해야 한다. |

타이틀과 로딩은 양쪽 모두 **파일명과 공통 decoder의 RGBA 해시가 다르다**. “탭 투 스타트와 로딩이 같은 이미지”라는 설명을 현재 구현 계약으로 채택하지 않는다. 그림의 소재가 얼마나 비슷한지는 이번 메타데이터 검사로 판정하지 않았다. 문이 닫히는 `Loading_Left/Right/Top/Bottom/Center.png` 연출과 `StageClearBG`의 맵 로딩 가림도 별개다.

기존 여섯 판본의 패키지 메타데이터에서는 일반판4개 모두 Main_BG/StageClearBG/Base001이480×320이었다. HD1.0.0은 Main_BG.jpg/Base001.jpg, HD1.0.3은 Main_BG.png/Base001.png이며 양쪽768×1024다. 이번 상세 코드·좌표 대조의 기준은2.0.1/1.0.3이다. 판본 차이를 모두 기기 차이로 일반화하지 않는다.

## 건물·길과 버튼의 관계

일반판 기지 생성0x3575c는 `ImageFile`을 공통 tile manager0x520c0에 전달하고 `X/Y`로 위치, `Scale`로 양축 배율을 설정한다. Button 행은 같은 기지 부모의 자식이고 ID+2000·1×2 타일·눌림/해제 타일을 사용한다. HD0x246d4도 같은 테이블 역할을 사용한다. 배경·선택 강조·버튼의 위치가 한 장면의 데이터로 정의돼 있다는 근거다. 건물 그림 안의 정확한 클릭 지점은 원본 시각 대조도 필요하다.

일반판 테이블에는32개 버튼, HD에는27개가 있다. 일반판은6기지 모두 정비 ID3을 가지지만 HD는 Base004에만 있다. Base004 테이블이 존재한다는 사실은 정상 캠페인에서 그 기지에 도달했다는 뜻이 아니다. **일반판 테이블을 통째로 교체하면 HD의 기능 집합도 달라진다.** 현재 HD 버튼 ID·콜백·메뉴 기능은 유지하고 공통으로 존재하는 논리 ID의 표시 위치만 대응해야 한다.

일반판 Base002 테이블의 선택 강조는 Base005_* 이름을, Base005 테이블은 Base002_* 이름을 참조한다. 원본 참조를 파일명 규칙으로 추측해 수정하지 않는다. HD Base001의 선택 강조 ID12도 이름에 Maintenance가 들어 있으므로 이름만 보고 기능 ID를 다시 정하면 안 된다.

## 원본의 화면 확대 처리와 현대 iPhone의 한계

일반판 EAGL.init0x40fc는 UIScreen.bounds를 읽고 방향에 따라 폭/높이를 교환해 glOrthof에 전달한다. framebuffer 준비0x3ce8는 layer.bounds와 실제 저장 배율에서 viewport/scissor를 설정한다. 읽은 기지/타이틀 생성 경로에서는480×320 배경을 임의 cover/stretch하는 별도 단계를 확인하지 못했다. 이 범위만으로2011년 원본이 오늘의 초광폭 화면을 처리한다고 주장하지 않는다.

480×320 그림의 비율1.5와 실제 iPhone912×420의 비율약2.17은 다르다. 다음 세 조건을 단일 그림 변환으로 동시에 충족할 수 없다: 전체 그림 보존, 원본 종횡비 유지, 빈 영역 없이 화면 전체 채움. cover를 쓰면912×608이 돼 세로188point가 잘린다. 비례 유지 contain은630×420이고 좌우282point가 남는다. 다른 배율로 가로/세로를 늘리면 그림이 찌그러진다.

따라서 새 표시 정책은 이 선택을 명시해야 한다. 원본 그림을 선택했다는 이유만으로 레터박스 금지·버튼/건물 대응·읽기 크기까지 완료했다고 보고하지 않는다. 배경·선택 강조·시설 버튼 중심에는 하나의 장면 변환을 쓰고 같은 역변환을 hit 검사에 적용한다. EXIT·설명 패널 같은 고정 UI의 안전 영역 배치는 원본 장면 좌표와 구분한다. 자르기 때문에 시설/길이 사라지는 구성이면 실패로 남긴다. 프레임마다 그림을 잘라 새 비트맵을 만들지 않는다.

## 에셋 로딩·재사용·해제 절차

| 원본 경로 | 확인한 책임과 수명 |
|---|---|
| HD ResMgr_Tile.getTile0x3f56c / 일반판0x520c0 | 파일명 키로 캐시를 먼저 조회한다. miss에서 파일을 찾아 Tile2D를 생성해 캐시에 등록한다. deviceType3은 먼저@2x 파일을 탐색하고 실제 채택 여부를 forRetina로 표시한다. 패키지에 없는@2x를 임의 생성하지 않는다. |
| HD GuiBase.init0x246d4 / dealloc0x24664 | 화면 전용 ResMgr_Tile을 만들고 기지 테이블의 이미지를 읽는다. 기지 소멸 시 manager를 release한다. |
| HD GuiTitle.init0x32340 / dealloc0x322e8 | 타이틀 전용 manager를 만든다. 소멸에서 removeAllTiles 후 release한다. |
| HD GuiMapLoading.init0x2da14 / tick0x2d730 | shared manager에서 StageClearBG를 얻는다. 가림이 완료된 다음 clearAllObject, clearTileResMgr, setStage를 별도 단계로 호출한다. loading dealloc0x2d9cc는 linkMap을 release하며 shared manager를 해제하지 않는다. |
| HD ResMgr_Tile.dealloc0x3fabc | tile dictionary를 release한다. 모든 배경을 앱 전체 수명의 무제한 캐시에 넣는 규칙으로 해석하지 않는다. |

현행 `HM2Renderer::_textures`는 renderer 소멸 때 전체 해제하며 `GameRuntime`의 글자 캐시도 런타임 수명이다. 원본의 화면 전용/공유 manager 구분과 차이가 있다. 이 사실만으로 누수나 발열 원인을 확정하지 않는다. 전환 반복에서 자원 소유권·잔류 메모리·공유 자원의 유효성을 실제로 측정할 필요가 있다. 이 발견은 Apple 렌더링 감사 담당에게 전달했다.

또한 공통 `decodeImage`는 PNG/JPEG를 지원하지만 `PreparedTiles::prepare`가 부르는 `AssemblyPreview::pngSize`는 PNG만 읽는다. 일반판 기지 JPEG를 원본 그대로 쓰려면 공통 이미지 크기 읽기를 보강해야 한다. 확장자만PNG로 바꾸거나 JPEG를 임의PNG로 다시 저장하는 방법으로 우회하지 않는다.

## 권장 구조와 다음 구현 조건

1. HD 게임·아이템·인게임 UI는 그대로 공유한다. 타이틀/기지/맵 로딩의 **표시 자원 역할**에 한정한 프로필을 공통 Presentation/ResourceAccess 경계에 둔다. 파일 참조·reader·준비·캐시·GPU 제출은 기존 공통 경로를 사용한다.
2. 실제 기기 종류는 플랫폼 호스트가 전달하고, 창 크기·방향·안전 영역과 별도 값으로 취급한다. `compact`만으로 원본 iPhone 그림을 고르면 좁은 데스크톱 창/태블릿 분할 화면도 잘못 선택할 수 있다. 우선 작은 표시 프로필을 기존 `DisplayConfiguration`에 명시하는 방안으로 충분하다. 지금 근거만으로 독립적인 전역 기기 판별 서비스를 만들 이유는 없다.
3. 이름 충돌을 막는 프로필별 자원 매핑/명세가 필요하다. 원본 파일의 바이트·형식·확장자를 유지하고 선택된 프로필의 배경만 해당 수명에 준비한다. 두 판본의 모든 배경을 무조건 사전 업로드하지 않는다. 원본에서 사용하는 화면별/공유 소유권을 반영한다.
4. 일반판 기지 데이터에서는 그림/시설 좌표만 추출한 명시적 대응을 사용하고 HD의 버튼 집합·ID·콜백은 바꾸지 않는다. 저장/상점/인벤토리/임무 등 게임 데이터 전체를 일반판으로 전환하지 않는다. 일반판 전용 정비 버튼을 자동 추가하지 않는다.
5. 최종 시뮬레이터/치트 묶음에서6기지의 그림·선택 강조·버튼 중심/hit·설명/EXIT·게이트 이동, 타이틀 전체 연출과 맵 로딩 가림을 검사한다. iPad 기존 화면과 사용자 저장을 보존한다. 그림 파일 대응과 건물 위 버튼의 시각 적합성은 별도 결과로 남긴다.

이번에 확정한 것은 원본 자원 존재·메타데이터·선택한 코드 계약·구조 권고다. 초광폭 배경 구성, 기지 시설/길의 실제 가시성, 전체 수명 동등성·메모리/발열, 구현/실행 통과는 아직 남아 있다.
