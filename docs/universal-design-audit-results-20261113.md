# 일반판·HD판 차이 조사와 유니버설 설계 보강

## 이번에 확인한 범위

일반판 iPhone과 HD iPad의 차이를 확인해 같은 HD 자원·공통 게임 코어로 유니버설 앱을 만드는 계획을 보강했다. 사용자가 현재 iPad 플레이에서 크래시·보행 애니메이션 이상·무기 이상·BOT 불사 현상을 보지 못했다는 관측은 현재 iPad 기준으로 보존한다.

| 조사 | 확인한 범위 | 남은 범위 |
| --- | --- | --- |
| 패키지·정적 데이터 | 여섯 IPA의 ZIP 9,137항목·파일 9,123개, 해시 전후 일치, 형식 파싱 오류 0 | 원본 코드의 실제 자원·데이터 소비와 실행 결과 |
| 그림 디코딩 | PNG/JPEG 7,740항목·고유 인코딩2,029개를 기존 게임 reader로 디코딩, 오류0 | 조립·프레임별 표시·원본 GPU 출력·실물 크기 |
| 함수 목록·본문 보존 | 분석기가 식별한 일반판 1,077개·HD 1,300개 함수 몸체의 목록과 ASM·의사 코드 | 모든 함수의 의미 대응과 메타데이터 밖 진입점의 완전성 |
| 중요 로직 | 카메라·입력·선택·범위피해·적 AI 진입 등 실제 함수/호출부 조사 | [네이티브 비교의 미확정 표](standard-hd-logic-differences-20261113.md#남은-정확한-확인) |
| 현재 복원 코드 | 공유 자원·공유 코어와 화면/입력/판정 소비 20항목 확인 | 새 화면 구성 구현과 iPhone/iPad 실제 실행 |

이번에는 앱을 빌드하거나 원본 포팅판·시뮬레이터·실기기를 실행하지 않았다. 패키지 전수 비교와 함수 본문 보존을 전체 기능 실행 대조 완료로 표현하지 않는다.

네이티브 비교표의 16개 분야 중 같은 역할의 경로를 연결한 항목은 7개, 추가 분기 확인이 필요한 후보는 9개다. 대응점을 찾지 못한 분야는 0개지만, 모든 함수의 의미나 모든 기능이 확정됐다는 뜻은 아니다. 아래 결과로 조사 계획을 보강했으며, 화면·판정·입력에 영향을 주는 미확정은 유니버설 구현 전에 해소한다.

## 단순 해상도 차이로 처리할 수 없는 항목

주 비교는 일반판 2.0.1과 HD 1.0.3이다. 서로 다른 버전이므로 아래 차이의 원인을 모두 기기 차이라고 부르지 않는다.

| 항목 | 확인한 차이 | 유니버설 설계에 반영할 것 |
| --- | --- | --- |
| 원본 화면 | 일반판 480×320 가로, HD 768×1024 세로의 기존 포팅판 관측 | 화면비·월드 시야·HUD를 각각 계산 |
| 카메라 배율 | 일반판은 표적·경로와 연결된 목표 배율 계산·점진 갱신이 있음. HD의 확인한 `processCamera` 본문에는 같은 수식이 없음 | 캡처 한 장의 메크 크기를 고정 phone 배율로 채택하지 않음 |
| 원본 단위·선택 | 일반판 reader는 `Rad×0.5`를 정수로 저장한 뒤 선택에서×1.5. HD reader는 `Rad`를 그대로 사용. 일반판의 확인한 맵 적 좌표도×0.5 | 원본 단위·반올림·입력 배율까지 연결하고 실제 터치 경계를 단순1.5배로 보정하지 않음 |
| 화면 판정·피해 | HD도 피해 종류와 대상에 따라 `isInScreen` 사용 여부가 다름. 일반판 확인한 범위피해 본문에는 같은 화면 필터가 없음 | 모든 공격·적·BOT에 단일 화면 gate를 추가하지 않음 |
| 생성 | 일반판의 확인한 kind4 맵 경로는 적을 즉시 생성. HD는 시간·거리·카메라 조건의 스포너가 있음 | 초기 생성과 사망 뒤 재생성 전체를 구분해 HD 공통 규칙 유지 |
| 파츠·맵 데이터 | MCB 3개는 바이트 동일 | 같은 데이터라도 소비 로직·배율·입력이 같다고 단정하지 않음 |
| 그림 | 공통 PNG 839개 동일·357개 차이, 그중342개는 크기 차이 | HD 그림 한 벌을 공유하고 표시·조립 좌표와 텍스처 픽셀을 구분 |
| 하체 23종 | SP 최대량·회복량이 다름. 보행에 쓰는 `Param3`는 동일 | HD 능력값을 모든 기기에 공유. 별도 phone 보행 코드의 근거로 삼지 않음 |
| 무기 | 213개 정의 중126행 차이. 사거리113·조준86·피해4행 | HD 게임 규칙을 공유. 화면 배율로 사거리·피해를 보정하지 않음 |
| 저격 무기 | 일반판에서 주석 처리된4종이 HD에서 활성 | HD의110종 장착 무기를 공통으로 유지 |
| 임무 | KR60파일 동일. US49파일 차이는 이름·수락 문구이며 판본 간 조건·행동·보상 토큰 차이0 | 데이터 동일성과 실제 소비 동등성을 구분 |
| 원본 언어 | 모든 판본의 `M001220`에 KR/US 요구조건 차이 | 플랫폼 차이로 분류하지 않고 한국어 기준을 유지 |
| 음원 | WAV56·MP3 1개 동일, HD에 `STAGE3.wav` 추가 | 파일 동일성과 재생 순서·수명·출력 동등성을 구분 |
| 기지 UI | Base6개 차이. HD 내부 버전에서도 관련12개 표가 바뀜 | 모든 배치 차이를 기기 크기 탓으로 확정하지 않음 |
| 저장 | 일반26,344·HD28,204바이트. seed/XOR 시작 위치·난수 seed 생성·파일 쓰기 경로도 다름 | 원본 저장을 서로 복사하지 않고 복원판은 HD 저장 규칙 공유 |
| 시간 | 전역 프레임 시간의 float32 상수는 같지만 증가 순서가 다름. 별도의 월드 시간은 일반판float32·HD float64 | 같은 숫자만으로 시간 자료형·사건 순서를 같다고 판정하지 않음 |
| 입력·UI | 중심 기준/양수 화면 좌표, touch phase 값, 부모·자식 구조·버튼 영역·도움말 페이지가 다름 | 일반판 좌표를 HD 그림에 일괄 배율 적용하지 않고 HD 노드와 입력 계약을 공통으로 유지 |

숫자는 해당 비교의 분모와 함께 읽는다. 서로 다른 필드가 같은 행에서 바뀔 수 있으므로 무기 차이 필드 수를 더해 무기 수로 세지 않는다. 동일 데이터도 실행파일이 다른 순서·수식으로 소비할 수 있다.

## 그림의 바이트·픽셀·투명 영역 구분

패키지 헤더 비교에 이어 게임에서 사용하는 기존 `hm2::decodeImage`와 같은 `stb_image`를 그대로 호출했다. 여섯 원본의 PNG/JPEG 7,740항목은 고유 인코딩2,029개이며 모두 디코딩됐다. 원본 그림 파일이나 디코딩 픽셀을 새 이미지 파일로 저장하지 않았다. 준비된 premultiplied RGBA8의 해시·채널 수·크기·파일 전체 alpha 경계만 기록했다.

주 비교에서 공통 이미지1,234개는 다음과 같다.

| 공통 이미지의 결과 | 수 |
| --- | ---: |
| 크기와 준비된 픽셀 동일 | 872 |
| 크기 자체가 다름 | 347 |
| 크기는 같지만 준비된 픽셀이 다름 | 15 |
| 디코딩 실패 | 0 |

크기가 다른347개는 PNG342개와 JPEG5개다. 크기가 같은데 픽셀이 다른15개에는 닫기·기지/출구·임무·시스템 버튼, HP/SP 게이지, 타이틀 등이 있다. 파일 크기나 확장자가 같다는 이유로 같은 그림이라고 처리할 수 없다.

이 결과는 **현재 공통 decoder로 준비한 RGBA8**의 비교다. 원본 OS의 색 처리·GPU 필터·블렌딩을 실행 대조한 결과는 아니다. 파일 전체의 alpha 경계를 개별 애니메이션 프레임·조립된 메크·충돌 도형으로 쓰지 않는다. [픽셀 비교 메타데이터](evidence/universal-image-pixels-20261113.json)

## 현재 복원판에서 바꿔야 하는 연결

이미 같은 C++20 코어·HD 자원·Objective-C++ Apple 호스트를 사용하고, 앱 타깃도 iPhone·iPad를 함께 등록한다. 실제 화면 구성 입력을 공통 코어에 전달하는 경로는 아직 없다.

1. **화면 크기와 안전 영역 전달:** 호스트는 bounds·pixel scale·safeAreaInsets·방향을 전달하고 공통 C++에서 유효 영역·월드 표시·HUD/패널 배치를 계산한다.
2. **생성과 갱신의 배치 일치:** HUD를 만드는 좌표뿐 아니라 매 프레임 값을 갱신하는 좌표도 같은 배치를 사용한다. 생성부만 바꾸고 다음 갱신에서 HD 위치로 돌아가는 누락을 막는다.
3. **모든 입력 소비자 연결:** 버튼·도움말·전장 이동·수리·공습이 표시와 같은 변환을 역으로 사용한다. overlay→UI→world 순서와 취소 처리를 유지한다.
4. **상태와 그림 배치 분리:** 문 전환·맵 로딩·배너는 기존 phase/tick·음향·저장 시점을 보존하면서 다른 화면비를 덮는 geometry만 바꾼다.
5. **시나리오별 실제 화면 검사:** 치트 화면의 칸 배열 폭만 바꾸지 않고, 각 Session의 화면 구성과 자동 입력을 iPhone/iPad 조건으로 실행한다.

월드 프레임은 이미 camera.viewport의 크기를 전달받는다. 모든 Frame을 무조건768×1024 고정이라고 설명하는 것은 부정확하다. 현재 병목은 HD 기본값·고정 UI와 화면 구성 입력의 부재다. [소스별 20개 근거](evidence/universal-restored-layout-gaps-20261113.json)

## 채택할 공통 기준과 남은 설계 결정

**한 벌의 HD 에셋과 같은 게임 코어를 유지한다.** iPhone용 자원을 따로 가져오거나 별도 게임 코드를 만들지 않는다. 일반판은 원본 차이와 iPhone의 표시·조작 기준을 확인하는 비교 대상이다. 일반판과 HD의 서로 다른 무기·SP·카메라 규칙을 둘 다 원본 그대로 재현한다고 주장하지 않는다.

일반판에서 발견한 가변 줌 때문에, 기존 표본의28×31·46×53 같은 기체 크기만으로 기기별 배율을 확정할 수 없다. 동일 장비·방향·애니메이션·목표/경로·현재/목표 카메라 배율을 연결한 기준 장면이 필요하다.

넓어진 시야가 이동·충돌·선택 해제·재생성·난수 소비를 바꿀 수 있다. 원작 분기별 예외를 유지하는 공통 규칙을 설계하고, 같은 화면 안에서 보이는 적의 조작 가능성과 경계 사건을 검사한다. HD 전투 영역을 고정한 채 바깥의 적 그림만 추가로 보여주는 구성은 실제 선택·명중 문제를 확인해야 한다.

HD 도움말은768×1024 합성 그림이고 정비 배경은480×320인 등 자원 크기가 섞여 있다. 같은 파일을 사용하면서 iPhone 가로에서 글자·버튼·전체 화면 가림을 어떻게 표시할지도 확정해야 한다. 모든 그림을 같은 비율로 늘이거나 iPhone 전용 그림으로 다시 만들지 않는다.

## 다음 순서

1. 네이티브 비교표의 카메라·선택·화면 판정·충돌·생성·BOT·UI 필수 미확정을 주소·필드·호출부로 해소한다. 시간·저장·음향의 비교도 함께 기록한다.
2. 정적 근거만으로 결정할 수 없는 항목은 원작 일반판/iPhone과 HD/iPad에서 조건을 묶어 실행한다. 기능 하나를 구현할 때마다 포팅판으로 왕복하는 순서는 반복하지 않는다.
3. 그 결과로 공통 화면 구성 계약을 확정한다. 최초 목표는 iPhone 가로·iPad 세로이며, 현재 iPad 상태를 회귀 기준으로 보존한다.
4. 공통 배치·출력·입력을 구현하고 각 실제 화면 구성을 사용하는 동시 치트·일반 플레이·저장·음향을 검사한다. 시뮬레이터 통과 뒤 기기에서 확인한다.
5. 마지막 일괄 대조를 수행한다. 전체 임무·캠페인과 추가 방향·후속 플랫폼 검사는 기존 TODO와 함께 별도 범위로 유지한다.
